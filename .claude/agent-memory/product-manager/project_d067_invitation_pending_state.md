D-067 (2026-11-14): Option A confirmed functionally. No `memberships` row at invite time; `invitations` row (`PENDING` → `ACCEPTED` | `REVOKED` | `EXPIRED`) is the whole pending state; `POST /invitations/accept` creates the membership directly as `ACTIVE` (`created_by` = inviter, `invitation_id` set) and marks the invitation ACCEPTED in one transaction; DR-A14 `p_users__org_member_read` positive list drops `INVITED` → `IN ('ACTIVE','SUSPENDED')`; `INVITED` stays in the `membership_status` CHECK and DR-A05 as RESERVED, unused in M0/M1 (writer needs an ADR amendment). ALREADY_MEMBER 409 now covers ACTIVE or SUSPENDED (any non-removed) and is explicitly "not an oracle" (reveals only the inviter's own org). Pending-invitation list (invitee e-mail) = `org:member:invite` holders only, not `org:read` (matches api/README listInvitations row already). Edits: EPIC-03 US-083 (2 AC lines + Notes), US-084 (Accept, Expired token, Audit lines + Notes), US-085 (Notes only); REQUIREMENTS.md REQ-ORG-003/010 notes, REQ-ORG-011 shall-text "activating" → "creating the membership as ACTIVE" + note, DR-A05, EC-A16; version 1.10. Scenario counts unchanged (US-083 11+1 outline, US-084 8, US-085 10+1 outline). PRD/NFR/ASSUMPTIONS/traceability/DECISIONS/STATUS untouched (concurrent PM run on D-066 held the lock).

**Why:** DR-A14 made a user's profile row readable by an org the moment it wrote an INVITED membership — before consent — and `memberships.user_id NOT NULL` forced an e-mail → user-id resolution at invite time (account-existence oracle against REQ-AUTH-001). The data model already modelled Option A (invitations table, `memberships.invitation_id`, `p_organisations__member_read` already ACTIVE/SUSPENDED); the story wording was pre-data-model residue.

**How to apply:** Any future text that says "INVITED membership" is stale — point at the invitation row instead. Rows that move together on invitation changes: REQ-ORG-003/010/011, DR-A05, EC-A16, US-083/084/085, EPIC-14 US-268 (uses "an invitation is created" already — fine), api/README rows 705–712, openapi `filter[status]` and `MyMembership.status` enums (still list INVITED — api-designer's call to keep as reserved or drop), plan-data.mjs/WAVE-00/WAVE-01 TASK text on the users policy positive list (`('INVITED','ACTIVE','SUSPENDED')` must become `('ACTIVE','SUSPENDED')` — senior-developer/architect side).
