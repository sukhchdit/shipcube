- **D-PM-081 (code review m3).** REQ-AUDIT-010 shall-statement gained an exception: no audit entry for requests "refused by the idempotency-key protocol before the handler runs" — 409 `IDEMPOTENCY_IN_PROGRESS`, 422 `IDEMPOTENCY_KEY_REUSED`, and a retry whose stored response cannot be read back (500 + required ERROR-level operational event). They are logged with code and correlation ID, never the key value. **Not excepted:** a claim that fails on a new request (key store error) is a 5xx and writes the normal `FAILED` entry. REQ-API-009 note: 24 h is also the upper bound; product position hourly purge. A-117.

**Why:** a FAILED entry records an attempt at the business action; a duplicate or a mismatched reuse is not one, an entry per poll would misreport one action as many failures and let a client write to its audit chain at its request limit (the GAP-A-09 reason for excluding 400). The claim failure is a real attempt that the platform failed, so entry presence must not depend on the internal phase. The split: no production composition has a key store after 040-A, so "completes" would rest on a test composition.

**How to apply:**
- Rule of thumb for audit-exception questions: classify the refusal as "protocol, before the action" (400, 412, 428, 429, idempotency conflicts → logged only) or "the action was attempted" (handler 409/422, any 5xx of a new request → FAILED). Then check flooding (can the client produce it at will?) and whether the auditor loses information.
