**Follow-up D-ARCH-228..231 (2026-11-21, after D-QG-008 = PASS_WITH_CONDITIONS on item 6; rulings file section 10, risks 1.32):**
- The gatekeeper measured my cost sentence wrong ("120 in flight only when each takes more than a second"). Item 6 now says: the hold is a **bound on concurrency**. Room of an address on an instance = `limit − settled` (120 by default); what arrives beyond it at the same moment gets 429 `Retry-After: 1`, whatever the pace and whatever one authentication takes.
- **Decision: accepted, design unchanged.** No browser traffic of this run reaches the room; the answer is a retry of a request of which nothing ran. Two designs are on file for the cost: one unit per credential with later requests waiting for the first outcome (named for trigger (vii): API keys / partner at M3, a bulk action above 20 at once), and a pass for a recently verified credential. product-manager decides the product side (QG-041B-C3; my text is in D-ARCH-231); "not accepted" comes back to me with the per-credential design.
- I did **not** adopt the gatekeeper's "nothing is refused before TASK-052 because the slot is synchronous": with a store double that delivers replies per read, a synchronous slot refuses 15 or 16 of 300. The true reason nothing honest is affected yet: the stub accepts no credential.
- **Release contract (D-ARCH-230):** an outcome is `next` once, a throw or a rejection; an authenticator never starts or ends the response; a slot that has not reported when it returns returns a promise that stays pending. Security's remedy (b), release at `finish`, is **declined**: REQ-SEC-015's timer (TASK-108, not built) answers 503 while a slot runs, and my probe gave 10 authentications at once at limit 5 with no spend. Adopted instead, **change C-4**: the wrapper ends a slot that ends without an outcome (answered itself: release, no spend; nothing answered: 500). Nothing about the response releases an entered unit.
- Signal (D-ARCH-229): two alerts (refusals in five consecutive minutes; oldest held unit older than 60 s), one client rule for every `RATE_LIMITED` answer with a random delay of up to 1 s.

**Follow-up D-ARCH-233..234 (2026-11-21, after D-QG-009 closed QG-041B-C1/C2 and raised QG-041B-C7; rulings file section 11, risks 1.33):**
- **D-ARCH-233, the client rule (C7 (a)).** My "one rule for every `RATE_LIMITED` answer" (D-ARCH-229) made clients repeat after any `Retry-After`, against the UX flows (F10 R14, F01, F04 ...) and stories US-031, US-167, US-248, and it had silently dropped the "Retry-After 1" limit of card line 19. Now: the rule reads only the code and `Retry-After`. `Retry-After` 1 → the API client repeats by itself (1 s + random ≤ 1 s, same `Idempotency-Key`, at most three times, about 6 s without a message at worst). Longer or missing → nothing by itself; the flow's rate-limited state with the retry time, the user repeats. Never a sign-out; a refresh that ends as `RATE_LIMITED` is not repeated on a timer. Other 429 codes are never repeated. The query layer must not retry this code on its own. No file under `docs/02-ux` changes.
- **D-ARCH-234, the slot forms (C7 (b)).** Three forms: reports before it returns (the stub), returns a promise and reports before it fulfils (async authenticators), and the **callback form** (no promise, no report, nothing answered at the return; `next` later from a callback: the `slowSeam` of H1, H2, H4). The wrapper waits for the callback form without a limit and C-4 cannot end it: if it never reports, the unit is held until restart, no spend, no error line. That is what remains of PR041-SEC-16. Product authenticators may not have it (card line 21 clause NO CALLBACK FORM + a unit row). Refusing the form in the wrapper is on file (triggers: a rating above LOW, or a product authenticator found in that form).
- **Form:** amended in place, two sentences of item 6 replaced by name and the reading of item 5 fixed; no superseding ADR by my reading, gatekeeper verifies with QG-041B-C4.

**Lessons:**
- Before I write what a client does with an answer, open `docs/02-ux` flows and grep the stories for that code. A client rule is a UX rule; D-ARCH-229 was written from the API side only and contradicted three stories.
- A text that replaces a card line is compared clause by clause with the line it replaces. I dropped a limit ("Retry-After 1") without noticing that it was one.
- A contract sentence about "every slot" is checked against the stub and every test seam before it becomes Accepted text. The delayed seam broke my own "must return a promise", and the stub is synchronous, so "every authenticator is an async function" would have been wrong too.
- When a dispatch says "consult X (spawn it)" and the run has no tool for it: apply the stated default, write the questions with defaults where X will find them, report the consult as not done. Do not start another agent through the shell.
- A worktree can go from "uncommitted work" to a commit while I write (`214ec79b`). Re-run `git log` on the branch before the entry says which state I read.
- More than one Edit to the same file in one tool block worked here (four in one block), but verify with a grep afterwards.
- A hold is filled by what is there at one moment. A ceiling per minute does not limit a burst, so "arrival ceiling × hold time" prices paced traffic only. Ask two questions: how many requests can be in the hold at one instant, and which honest client sends that many at once.
- A probe on an in-memory store hides batching. A store that answers over a socket delivers the replies of one read together, and all their continuations run before any request moves on. Use a store double that delivers per read (wrap the branch's `FakeValkey`: run the script at call time, queue the resolve, flush the queue in one step on `setImmediate`).
- Before I accept a release (or any control) keyed on a response event, list every writer of the response, including one that a requirement demands and no task has built yet. Remedy (b) was validated correctly against today's pipeline and is broken by the timer of REQ-SEC-015.
- Comparing candidate rules is cheap: copy one compiled `dist` file to the scratchpad, rewrite its imports to absolute file URLs, patch it, and select the build with an environment variable in one harness. Say in the record that the copies are patched compiled files, not the branch.
- A load probe whose clients and server share one process groups arrivals more than separate clients would. State it as a limit of the numbers.
- A bound a developer reports ("slack 0") is a claim. For a hold or a reservation, list every release path and ask of each: is the work it guards still running? The close-of-response "safety net" released while the authentication ran.
- A clean worktree with a current `dist` can be probed read-only without Jest or Docker: a scratchpad `.mjs` that takes express through `createRequire(<worktree>/apps/api/package.json)` and imports the compiled modules (and `packages/shared/dist/index.js` for `AppError`) by `pathToFileURL`; raw `net` sockets give the disconnect and slow-body shapes. Check `git status` clean and dist newer than src first.
- Run `git log` once more right before the commit, not only before writing: a parallel review of the same head landed while I wrote and offered two closures. Say which option the ruling takes and where it differs from the review's routing, so the orchestrator does not have to reconcile two records.
- For an accepted cost of a concurrency hold, read what runs between the hold and its release (the first lesson above replaces my earlier "arrival ceiling × hold time", which D-QG-008 measured wrong); then check which counter label and event the new refusal path really produces, because the residual's trigger depends on that signal. Word an alert and a trigger so that one honest burst does not fire them.
- `__Host-rt_web` is `Path=/` on the app's host: any rule keyed on "a credential is present" catches every returning browser, sign-in included. Check passive credentials before writing "requests without a credential still pass".
- When a ruling is a trade between a security bound and user-visible availability, read the latest D-PM and D-SEC entries first: here both owners had already taken a position (and committed requirement text) while I was still weighing alternatives. Rule with them unless the architecture forbids it, and record my own estimate plus the reopen trigger.
- Before accepting a library deviation, grep `shipping-platform-brief.md` §3 for the library: a §3.2 item is a SHOULD that needs an ADR, and the fixed-stack rule is the user's, so the entry must name both and the orchestrator must put it to the user.
- A user approval relayed by another agent is recorded with its provenance, never as something I verified.
- When comparing a new control with an existing one ("already true of X"), check the scopes are the same; the gatekeeper caught an understated comparison.
- The coordinator can add scope mid-task (the security record arrived after the code review); re-read `git log` and DECISIONS for new records before writing, and re-check the next free D-ARCH number (168..172 were taken while I read).
- Do not copy a factual claim from another agent's record into an ADR without opening the source: "DHL shared origin" was cited as a carrier penalty and is not one.
- Requirements (DR-A08 etc.) can restate an ADR clause; when an implementation deviates, grep the requirement files too and route the wording to product-manager.
- Guarded DECISIONS append worked under concurrent commits: check the file has no uncommitted diff, append from a scratch file, `git commit -- <paths>`, then verify numstat is insert-only.
