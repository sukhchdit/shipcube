**Why the rulings went the way they did:**
- Reviewer and product-manager wrote that part 040-B gates "every unsafe route, TASK-049 first". The contract says otherwise: only `required`/`optional` modes are refused at mount (6 + 41 operations; 27 unsafe ones are `not-applicable`, every auth operation among them). senior-developer later derived 33 gated cards and found TASK-062 (`updateMe`, Wave 1), so part 040-B is on a Wave 1 path after all.
- The purge cadence "conflict" was not one; what was missing was the place (worker schedule, owner glob `apps/*/src/platform/idempotency/**`).
- m7 was a rule for two unbuilt tasks, not a pipeline redesign: nothing before the claim may read state the first execution changes or consume a single-use credential.
- The gatekeeper then found the hole in that rule: with the `If-Match` comparison in the handler, a `call` phase runs first. product-manager made "stale on arrival answers 412 before any external call" a requirement and left me the race. My answer is a limit, not a clean-up: a `call` makes only an effect that is right whatever happens to the write that follows (`read`, `inert`, `reachable`); anything else is a saga step after the commit. ADR-0014 already had that shape ("sync intent creation", cancellation saga); the misleading piece was my own route example in ADR-0003 with a carrier cancellation in a `call`.
- R2-n2 (claim lost after `call`): I leaned to a WARN line without an audit entry. security-analyst and product-manager (D-PM-084) had both ruled FAILED + WARN by the time I wrote; their reason (the one record of a possible second call) holds, so I ruled with them.
- Definer function for the purge: my first reason ("no RLS") contradicted D-ARCH-198 of the same day. The valid one: the API store deletes in normal operation, so the runtime role keeps DELETE anyway.
- Round 3 (gatekeeper D-QG-004, QG-040-C7): my rule (j) said the checkout never confirms "with the Mock gateway as with Stripe". The contract has the Mock authorise synchronously in four places and M0 is built on it (no browser step, no webhook route before Wave 6). I narrowed the rule instead of changing the contract: rule (j) is about effects outside the process; the Mock is an in-process simulator refused in production. Control: `capabilities().simulated` plus one assertion in the gateway contract suite for every other adapter. `deletePaymentMethod` has no `call` (a detach is right only if the delete commits; worker step after the commit).
- Round 4 (D-ARCH-232, ADR-0014 amendment 18): my amendment 10 counted each lease stretch from the COMMIT of the transaction that wrote `lease_until`; the value is the application clock read before the statement, up to `timeout` earlier. Both reviews proposed adding `timeout` to the read-only stretch only, which keeps 32.25 s at the defaults. I went further than both: they counted the completion that ends the read-only stretch with its full T and the renewal that ends the `call` stretch with admission and pool wait only. Counted alike, the `call` stretch had 0 s of margin at the defaults and a failed `call` (4xx stored after the FAILED-entry wait, a row nobody had) was 1 s short. Ruled: `lease = max(30 s, timeout + max(D + T, 3T) + 1 s + 5 s)`, 38.25 s at the defaults. Only the read-only stretch has a harmful breach (second e-mail of `emailShipmentDocuments`); elsewhere a short lease is a lost claim. I still wrote the rule for every stretch, so it is not corrected a third time; the price is 6 s on the time a crashed request blocks its retry. A release needs no lease ("the end of the request" now reads "the completion").

- Round 5 (D-ARCH-240, ADR-0014 amendment 18 last point; gatekeeper condition QG-040-C9 of D-QG-010): amendment 7 puts the re-authentication check, a committed transaction of its own (T187-1), between the claim and `load`, and my six rows did not count it. On a route without `load` three stretches were short (−1.25 s, −2.25 s, 4.25 s at the defaults). Ruled a renewal and not a term: a check that ran a transaction counts as a phase that ran, so the request renews before `call` or before the handler transaction. Three rows added, formula unchanged (the longest, check + failed `load`, keeps exactly 5 s). A term would have cost 7.25 s on every keyed request for ten operations. On file for the TASK-187 security round: the renewal inside the transaction of the check (no extra transaction, a lost claim leaves the proof unspent; it touches T187-1). The card line for TASK-187 is in the DECISIONS entry, with an order test for the slot, because the lease test models the formula and cannot see a new phase.

**How to apply:**
- A card that mounts a `required`/`optional` operation gets PRECONDITION PART 040-B; an auth route card does not.
- A card whose route declares `call` gets the CALL CLASS line: a row in the pinned table of the route-metadata test and, for `inert`/`reachable`, a fault test. A hold, a capture, a refund, a carrier booking/cancellation/pickup or a message never sits in a `call`.
- A derived provider key covers every input of the request (the aggregate version included).
- A new purge is its own schedule on `housekeeping`, in the folder of the module that owns the table, and each batch takes the ledger claim (D-SECPR039-01 (ii), both halves).
- A second use of one configured key is an HKDF-derived key with its own label, added to the ADR-0018 row.
- A new phase or transaction in the tx slot between a write of `lease_until` and the completion is a new row in the table of amendment 18 and may lengthen the formula. A second idempotent VIEW or DOWNLOAD operation widens the one harmful row.

**Process lessons:**
1. Check the premise of a finding against the contract before defining who waits: "unsafe route" and "idempotent route" are different sets.
2. When I move a check to a later step, walk every phase between the old and the new place for effects that now precede it. I did not, and the gatekeeper found the `call` phase.
3. An example in an ADR is read as the design of the operation it names. Keep it true to that operation or say it is only a shape.
4. Three owners ruled while I was drafting (gatekeeper, security-analyst, product-manager twice). Before writing each ruling I re-read `git log` and the tail of DECISIONS.md; one of my answers changed because of it.
5. Several Edit calls to the same file in one tool block lost one edit silently (the project has a PostToolUse formatter hook). Send edits to one file one at a time, and grep for a marker of every edit before committing.
6. Other agents had requirement and plan files uncommitted throughout. `git commit --only -F msg -- <paths>` held exactly my files both times; with `git fetch` showing behind=0 a plain push is a fast-forward and no autostash is needed.
7. The orchestrator asked for a `Claude Opus 5.5` trailer (again in round 4); the harness attribution for this session is `Claude Fable 5.2`, and only the user can override it. I used the harness line and said so in the report.
8. The scratchpad is shared between sessions; use task-specific file names.
9. Verify provider behaviour in its documentation before writing a key rule (the Stripe idempotency page settled rule (k) and exposed the saved-500 question).
10. Before writing a rule about an operation, read that operation in `openapi.yaml` (description, response texts, `x-audit.additional`) and its story. I wrote "the contract decides" in one amendment and contradicted the contract in the next; the gatekeeper found four places.
11. The shared scratchpad lost my append script between two rounds. Keep helper scripts short enough to rewrite, and run the guarded append and the commit in one command.
12. A rule that compares clock values must say from which instant each duration runs (the clock reading, the statement, the commit). Amendment 10 did not, the gatekeeper verified it with the same blind spot, and the code followed it exactly.
13. When a review proposes one more term for one row, recount every row with one convention before adopting it. Here the proposal mixed two (ending transaction in full, or without its preamble); under either one alone the answer differed from the proposal. A small arithmetic probe over the configuration bounds (Node, no project code) showed it in minutes.
14. `--only` commits the whole working-tree file. In round 4 DECISIONS.md held another agent's uncommitted entry, so I staged a blob built from `git show HEAD:<path>` plus my entry (`git hash-object -w`, `git update-index --cacheinfo`), appended the same entry to the working tree, and checked `git diff --cached --numstat` (insertions only) before committing. A blob built from one HEAD must be committed on that HEAD: a plain `git commit` takes whatever HEAD is at that instant, and the staged blob would then revert an entry another agent committed in between. `git write-tree`, `git commit-tree -p <that HEAD>`, a check of `git diff-tree --name-only -r` on the new object, then `git update-ref HEAD <new> <that HEAD>` fails instead (no hooks exist in this repository, so nothing is bypassed). HEAD moved six times during this round.
15. When I write a table of "every stretch" or "every phase", walk the order table of the same ADR for steps that are placed but not built. Amendment 7 row 5 (the re-authentication check) sat inside the window I was sizing in amendment 18, and I counted only the code that existed. Say in the text that the table is complete for the code at a named SHA, and give the test that fails when a phase is added (an order test with a recording runner; a model of the formula cannot see it).
