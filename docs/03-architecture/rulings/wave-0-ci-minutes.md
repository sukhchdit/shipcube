## 2. Ruling in one paragraph

Lane A is scoped by **what the push changed**, not by what the PR changed: a push whose diff is docs-only runs lane A in **light mode** (every base-ref gate still runs on the exact head — evidence verifier, security record, gitleaks, workflow policy, install flags, migration immutability — while the head-code checks are **inherited** from a proven run on a commit whose code tree is byte-identical to the head's). `security-integration` runs **once per code tree**, on heads that are merge candidates (the security record is present and valid, or not required), and later docs pushes inherit its result. `ci-gate` decides merge-readiness from base-ref classification and the GitHub jobs API, so inheritance is verified, never assumed; a head whose code tree lacks a proof is red. Dependabot runs are excluded from the billed total; the guards act on the month **forecast**. The job topology then folds `scans` into `ci-gate` (two-step, policy first), and the planned incremental fast lane lands as its own task. Together with two process levers for the orchestrator (unions only when needed; one docs push per review round) the steady-state forecast at the Wave-0 rate with all six security suites is **≈ 1,280–1,430 min/month (64–72 %)**; the mechanisms alone give ≈ 1,690 (84 %). Every merged head is still proven by the same checks, on the same runner class, against the same base-ref tooling — the proof is reused only when the code tree is identical, and the reuse is checked by the gate.

### Why inheritance is as strong as re-running

- The inherited checks are exactly the head-code checks (lint, format, type-check, unit, build, porcelain, licences, signatures, audit, lockfile, dep-age, lint fixtures, Semgrep, oasdiff). Their inputs are the code tree plus the base-ref tooling. On a docs-only push the code tree is byte-identical (tree diff, so unions are handled), and the base-ref tooling that *decides* (policy, install flags, migration immutability, evidence verifier, record check, gitleaks, classification, proof lookup) **re-runs on every push**.
- A proof is a set of **step conclusions** read from the jobs API, not a job colour. A light `fast-lane` job concludes `success` but its CODE-gated steps are `skipped`, so it can never serve as a proof; the first push of any code-identical range necessarily ran full (its `before` lies outside the range, or there was no `before`).
- Time-dependent gates (`check-dep-age`, `npm audit`/osv) are inherited for the hours between the proof run and the merge; today the same exposure exists for any PR merged without a re-push after an advisory. Lane C `wave-end` and `nightly` re-audit `main`. Residual accepted; security-analyst confirms in the PR #46 record.
- A gate change on `main` after the proof run: light mode re-runs every base-ref gate with the *current* base; the head-code checks keep the older base's tooling — the same exposure as a PR not re-pushed after the change, which P1 (union when `main` moved under tooling paths) closes for the paths that matter.

## 6. Process levers proposed to the orchestrator (D-ORCH; not architecture)

- **P1 — unions only when needed.** Push a merge of `main` into a branch only when GitHub reports the PR not mergeable, or when `main` moved under `package-lock.json`, `prisma/**`, `tools/ci/**`, `tools/quality/**`, `.github/**`, `.npmrc`, `.semgrep/**` or `.gitleaks.toml` since the PR's last full run. Otherwise squash-merge directly (GitHub computes the squash against the current `main`; nothing lane A proves today about the squash result changes). ≈ 21 of 64 code pushes were unions; halving them saves ≈ 23 code runs and ≈ 8 `security-integration` runs a month (≈ 200 min at stage 2).
- **P2 — one docs push per review round.** Commit lane B evidence and the security record together where the timing allows, and never push a docs-only commit while the PR's full run is still in progress (it now queues instead of cancelling, so it only costs wall-clock). The record push is the merge candidate. ≈ 30 fewer docs runs a month (≈ 60 min at stage 2, ≈ 110 at stage 1).
- **P3 — Dependabot.** Six Dependabot PRs produced 7 runs in 13 days although the interval is monthly: a closed group PR is recreated at the next check. Merge or `@dependabot ignore` rather than close; `open-pull-requests-limit: 1` for the npm group. ≈ 40 min a month.
- **P4 — weekly `ci:minutes --forecast`** at every wave-exit checklist and every Monday, recorded in STATUS; the guard actions of D-ARCH-129 follow the printed level.
