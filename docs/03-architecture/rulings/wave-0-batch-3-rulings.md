## Item 1 — SPK-02 (TASK-009, PR #6): ADR-0010 amendment request

**Ruling: ACCEPTED — all seven requests of SPK-02 §4 are decided in ADR-0010 amendment 11.** D-ARCH-057.

- **Verdict stands.** UPS GO; FedEx and DHL FALLBACK for the named operations; the PLAN §9 fallback applies (fixtures `synthesised`, live sandbox opt-in, COND-SANDBOX-DEMO as the closing proof). "Confirmed (secondary)" labelling is enough for TASK-135/139/140 to **start**; a human diff is not a precondition for them to **close** either (see item 1.4), but it is a release condition.
- **1.1 Authoritative status.** SPK-02 §1 and the READMEs' "ADR-0010 re-verify items: result" sections supersede the ADR's "To re-verify" column; the 13 corrections of SPK-02 §2 are adopted (UPS void `DELETE`, label recovery, API versions, string token fields and the token path outside `/api`, DHL two tracking forms, FedEx 200-with-`errors[]`, FedEx limits and 10-minute 403 penalty, capability seeds `pushTracking=false`, `maxTrackingNumbersPerCall` 1/30/200).
- **1.2 DHL `cancelShipment` → `CAPABILITY_NOT_SUPPORTED` (option a).** The interface keeps the method (brief §4.3 is fixed); `capabilities().operations.cancelShipment` becomes a boolean and the REQ-CARR-003 guard (no network I/O) covers it. Cancellation semantics when the carrier cannot void: shipment `CANCELLED`, pickup cancelled where one exists, `carrier_void = UNSUPPORTED` recorded (terminal, not a failure, no retry, never `EXCEPTION`), label `VOIDED` Platform-side at once, refund proceeds (D-017 unchanged). Contract case `cancel-capability-not-supported-no-io`. **Demo-critical scope is not affected**: US-196, US-216, US-229, US-261 are Should / non-DC; US-237 (Must, non-DC) keeps working because DHL pickup cancellation exists. Why (a) and not (b) "keep and prove live": there is no sandbox access in this run, so (b) would ship an operation nobody can exercise and the saga would retry a path that does not exist.
- **1.3 UPS PDF labels through the official Label Recovery API; new optional operation `recoverLabel`; no PDF code in `packages/carriers`.** *This supersedes the first draft of this item (GIF → PDF with an in-house decoder inside the adapter), which the PR #6 code review (M1) showed to rest on two errors: `pdfkit` embeds JPEG/PNG only and belongs to the `documents` module (ADR-0003/0019), and the official spec documents a PDF path.* Verified in the pinned spec (`UPS-API/api-documentation@fd57ca9`, downloaded to the scratchpad): Ship `LabelImageFormat.Code` = `GIF | ZPL | EPL | SPL` (`Shipping.yaml:11251-11263`); Label Recovery `LabelImageFormat.Code` = `GIF | PDF | ZPL | EPL | SPL` ("PDF -- label is in PDF format", `:13479-13496`). Design: `CarrierAdapter` gains optional `recoverLabel(ref, formats, ctx)` (idempotent, retryable, `transactional` pool, capability flag; UPS and Mock `true`, FedEx and DHL `false`); the UPS adapter ships with `GIF`/`ZPL`, returns `labels: []` for PDF (the GIF is only a raw-payload `$blob`, never a document), declares `labelFormats = [PDF_4X6, ZPL]` (Label Recovery renders 4 × 6; REQ-DOC-002 "only that format is offered"); the saga's document step (ADR-0014 step 4, retry-only) calls `recoverLabel` for every offered format missing from the create result; failures follow step 4's retry/exception path, never a second `createShipment`. Cost: one extra transactional call per UPS booking in the worker. **Unverified in CIE** (fixtures `synthesised`, COND-SANDBOX-DEMO). **Contingency** (R-ARCH-25): a raster → PDF converter in the `documents` module with an in-house GIF decoder (no npm decoder passes the 18-month rule: `omggif`/`gifwrap` 2022-06, `@jimp/gif` 2024-02, `gifuct-js` 2025-01; `jimp` drags those; `sharp` ships `optionalDependencies` binaries that `--omit=optional` drops); last resort `ZPL` only with a product-manager re-scope. Rejected: GIF → PDF in the adapter (module boundary, decoder); GIF-only declaration (fails REQ-DOC-002); the converter as the primary path (hand-written bit-level code where an official API exists).

## Item 4 — TASK-013 (PR #8) D-T013-08: roles seeded by a versioned generated migration vs the reference seed

**Ruling: ACCEPTED — the migration is the mechanism; data-model §3.3/§9.2 aligned (data-architect's half done here).** D-ARCH-060.

- **Why the code is right.** US-073 is literally "Role definitions change only via versioned migration"; REQ-RBAC-013 says "versioned seed or migration"; REQ-RBAC-002's "never widens a role without a migration" is only provable if the migration is the sole writer. A `db:seed` upsert path would be a second writer with its own idempotency logic — one source is better. Applied migrations are immutable, so a grant change is a new `authz_seed_v<N>` migration after a `CATALOGUE_VERSION` bump.
- **What the reference seed does instead** (data-model §9.2 row rewritten): never writes the three tables. **TASK-221 (US-073)** runs a **post-migrate reconciler** as `SYSTEM_JOB` (the PR8-SEC-09 mechanism): digest of the three tables as read from the database vs the last audited digest in `reference_dataset_versions('authz_matrix')`; one `CONFIG_CHANGE` entry per changed version (role, old → new set), baseline back-fill ∅ → current on the first run, nothing written when unchanged (AT-US-073-04 by construction); it also fails on catalogue ⇔ database drift; a migration never inserts into `audit_entries` (hash chain, rule-12 lane). TASK-221 gains the dependency on TASK-023 (`seedfw`). If TASK-221 is cut, the G3 report names the guard tests and CODEOWNERS as the residual controls.
- **Released seeds are pinned (PR8-SEC-01, code review M2).** `SEED_MIGRATIONS = { 1: { dir, sha256: { up, down } } }`; a pinned version whose rendered content differs fails `--check` and the unit test ("bump `CATALOGUE_VERSION` and add a seed migration"); write mode refuses to overwrite a pinned directory; `artefacts()` throws for `CATALOGUE_VERSION > 1` until a delta renderer exists (a full re-render's `down.sql` would delete v1 rows). Generic migration-immutability check → TASK-016 linter or TASK-007 lane A. `ON CONFLICT ("id") DO NOTHING` so a key collision raises (PR8-SEC-08 b, D-SEC-PR8-01).
- **Linter rule 10 (the PR's "data-changing: no" question).** Clarified in §8.3: an insert-only generated seed into GLOBAL tables created earlier is `data-changing: no` (no existing row touched, backup guardrail not triggered); a narrowing migration (`DELETE FROM role_permissions`), an `UPDATE`, an upsert (`ON CONFLICT … DO UPDATE`) or `MERGE` is `yes` (PR8-SEC-03: the linter's `DATA_CHANGING` pattern gains the upsert/`MERGE` forms with a fixture). D-SEC-PR8-01 says the same.
- **Database backstops (PR8-SEC-08, optional before the M2 role editor):** `ck_permissions__operator_only_rule` CHECK mirroring DR-A07; a database-side assertion that no non-OPERATOR role links to an `operator_only` permission and no role links to `webhook:*`.
- **Also aligned:** §3.3 (flags are catalogue metadata, not columns); §1.7 `role_scope` source note (D-T013-11); §7.3 covering-index note (D-T013-09: `INCLUDE` is raw SQL, `migrate diff` reports it, the drift check compares migrations against the database and names the tolerated indexes); §12 A17.
