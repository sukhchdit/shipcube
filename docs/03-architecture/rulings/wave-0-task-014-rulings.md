## 3. Rules that follow from D-ARCH-116 (the runtime base)

1. **Two digest-pinned `FROM`s per Node service image, same Debian codename.** `node:<exact>-<codename>-slim@sha256` (`base`, used by the build stages) and `debian:<codename>-slim@sha256` (`runtime`). The official binary is portable across Debian ≥ bookworm (glibc ≥ 2.28), so parity is not an ABI necessity; it exists so that one Debian release is in the image (one OS to reason about for Trivy and CVE response) and so the `base` stages and `runtime` share a security baseline. Static check in `tools/ci/check-dockerfiles.mjs` (R3); build-time fail-fast is the existing `RUN … node --version` and the preflight.
2. **Binary-only copy.** The only artefact taken from the node image is `/usr/local/bin/node`. No npm, npx, corepack, yarn, `docker-entrypoint.sh`, `nodejs` symlink or `/usr/local/include/node` in `runtime` (the V8 headers are what needed the secret-scan allow-list D-TASK014-13; they are gone from api/worker). The runtime has no package manager of any kind.
3. **CVE response = two Dependabot lines, no in-place patching.** Node security releases arrive as a bump of the `node:` tag + digest (Dependabot `docker` ecosystem; the Node binary is not a dpkg package in the official image either, so Trivy's OS inventory never saw it — no regression); Debian point updates (glibc, libstdc++, dash, coreutils) arrive as a digest-only bump of `debian:trixie-slim`. `.github/dependabot.yml` must therefore carry the `docker` ecosystem for the five Dockerfiles and `docker-compose` for `compose.yaml` (GA 2025-02-25), 7-day cooldown, monthly, grouped (R2). Images are rebuilt, never patched in place (read-only root filesystem, no apt).
4. **No system CA store.** Outbound TLS (carriers, Stripe, SES/SMTP, OTLP) uses Node's bundled Mozilla store (the nodejs.org build default). The PostgreSQL CA (`sslrootcert`) is a file under `DATABASE_CA_DIRECTORIES` (`/etc/ssl/platform`; `/etc/ssl/certs` does not exist in the image and is inert until a system store is installed). At M5 the RDS global bundle is baked into `/etc/ssl/platform/` by the release task (public certificate; refreshed by PR). Consequence for the entrypoint allow-list: `--use-openssl-ca` selects a store that is absent, so every TLS connection fails closed — drop it from the allow-list or comment the trap (R4).
5. **The shell is load-bearing.** `tools/docker/entrypoint.sh` strips `NODE_OPTIONS` before the first Node process starts (PR3-SEC-13, D-TASK014-03). Any base without `sh` and `env` (distroless `nodejs24-debian12`, `cc-debian13`) removes that control, and `nodejs24-debian12` additionally replaces the ADR-0001 pinned official Node build with Google's. Distroless is therefore **not** the next step when the budget bites; see §4 item 3 for the recorded lever.

## 4. Headroom: the budget, the unit and the prune plan (D-ARCH-118)

1. **Budget and method.** api and worker ≤ **300 MiB = 314,572,800 bytes**, measured as the sum of `docker history --human=false --format '{{.Size}}'` layer sizes of the final image; Nginx images ≤ 60 MiB the same way. The stack suite already compares bytes against `300 * 1024 * 1024`; it gains a `WARN` line at ≥ 90 % (270 MiB / 54 MiB) so growth is visible per PR (R5). The tooling image is **reported, not gated** (as cold build time is under A-039): it is a one-shot with no inbound traffic; its size is governed by the closure invariant of D-ARCH-117, not by a number.
2. **Why MiB and why it is not a free pass.** NFR-OPS-002 says "≤ 300 MB (default)" with no unit rigour (A-039 default, set before anyone measured a Node 24 binary); OI-08 asked for the definition. Docker's CLI prints decimal MB, ECS and Node count MiB; the purpose of the budget (pull time, cold start, attack surface) is served at either reading and the two differ by 4.9 %. The binary reading is adopted because the measurement is a byte count and every other byte budget in this architecture is binary; product-manager is asked to write "300 MiB" into NFR-OPS-002 and A-039 so the gatekeeper has one rule. The price of that reading is honesty about the worker: 98.7 % of budget with the whole of M1 still to land.
3. **Prune plan, measured in the worker image, in order of yield/risk** (owner: a new late task `imgheadroom`, devops-engineer, S, lock `infra-compose`, deps TASK-014; the next sheet fold creates it — proposed block in §5; exit: worker ≤ 270 MiB and api ≤ 255 MiB with the preflight and stack suite green):
   - (a) `pdfkit/js`: ship one bundle (`pdfkit.js` or `pdfkit.node.mjs`, whichever the ESM app resolves); `pdfkit.standalone.js` (1.4 MB), `pdfkit.browser*.{js,mjs}` (1.1 MB), `*.old.js` (0.5 MB), `vitest.config.js`, `rollup.config.mjs`, `tools/` → ≈ 3 MiB.
   - (b) `zod`: `src/` (2 MiB of TypeScript sources) and the entry trees `@platform/config` does not import (`v3`, `mini`, `v4-mini`, `locales` ≈ 2 MiB) → ≈ 3–4 MiB; the preflight proves the remaining entry loads.
   - (c) `stripe`: one of `cjs/` or `esm/` is dead for a given consumer (`exports["."]` resolves `cjs/stripe.cjs.node.js` for `require`, the ESM twin for `import`) → ≈ 2 MiB after the preflight confirms which is loaded.
   - (d) `bcrypt/prebuilds`: keep `linux-x64/bcrypt.glibc.node`; nine foreign prebuilds → ≈ 0.9 MiB. `@prisma/client/runtime` CJS twins (`client.js`, `wasm-compiler-edge.js`) → ≈ 0.4 MiB.
   - (e) **Structural, code change, owner = the telemetry task:** `@opentelemetry/sdk-node` pulls every exporter (gRPC, HTTP, proto, Zipkin) and thereby `@grpc/grpc-js` (4 MiB) and `protobufjs` (2 MiB); the platform exports OTLP/HTTP to `:4318` and Prometheus on `/metrics`. Assembling the SDK from `sdk-trace-node` / `sdk-metrics` with the two exporters used drops ≈ 8 MiB from both images. Requires a telemetry ADR note, not a prune script.
   - (f) **Not pruned, by design:** `swagger-ui-dist` (5 MiB) reaches the worker through `@platform/api`; splitting the api package's docs entry is not worth 5 MiB. `test`/`tests` folders inside `node_modules` stay (runtime code lives there in some packages).
   Expected: worker ≈ 278–280 MiB after (a)–(d), ≈ 270 after (e); api ≈ 258 / 250.
4. **The fixed-cost lever, recorded, not scheduled.** If M1 growth exhausts the prune plan, the only lever left is the 83.6 MiB Debian layer: `gcr.io/distroless/cc-debian13` (glibc + libstdc++, ≈ 25 MiB, GA 2025) **plus** a static `busybox` `sh`/`env` for the entrypoint preflight (≈ 1 MiB) would cut ≈ 58 MiB, keeping the official Node binary and the preflight control. It costs a spike (busybox provenance and pinning, `useradd` replacement, Trivy coverage of the busybox binary, hadolint rules) and a superseding amendment to ADR-0001/this ruling. Raising the budget is the alternative and is product-manager's call, made with these numbers in hand (risks R-ARCH-31). Neither is done in this run unless the WARN threshold is crossed.
