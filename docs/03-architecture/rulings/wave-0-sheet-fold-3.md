## 3. Why — notes for conformance reviews

1. **The guard was checked against the data model before it was adopted, and two sketches failed.** The §6.4 `number_sequences` allocation and the §6.2 `idempotency_keys` takeover/complete statements left `version` unchanged. The §4.4 grant for `number_sequences` already lists `UPDATE (next_value, updated_at, updated_by, version)`, so the sketch, not the design, was wrong. Both are corrected; the outbox relay (§6.1) and the guest claim (§4.3) already stamp. Every other raw writer on an STD table finds the rule in its own integration test, loudly, in its own PR — that is the intended fail-fast behaviour, not a regression. One consequence to remember: the outbox relay's `updated_by = $system` is accepted only if the relay transaction context carries `SYSTEM_ACTOR_ID`; the relay test of TASK-043 fails loudly otherwise.
2. **Assert, don't fill.** A `BEFORE` trigger could fill a missing `created_by` (NOT NULL is checked after BEFORE triggers). It must not: `catalog-std` pins "NOT NULL, no default, inserts fail loudly", and a filling guard would turn a repository defect into a silently correct row.
3. **Why a lint is the weaker half.** All raw SQL is a tagged template, so its text is statically visible — but definer functions, migrations and any later writer are not, a lint needs a reviewed-writers manifest to govern, and the ESLint lock is held by TASK-020. The guard is one function and a rendered line per table.
4. **`ENABLE`, not `ALWAYS`.** The audit triggers are `ALWAYS` because they are the immutability control. The standard-columns guard is an integrity assertion for application writes; making it `ALWAYS` would break logical-replication apply and `pg_restore --disable-triggers`. A superuser bypass is the same boundary as RLS.
5. **The sketch was executed, not only argued.** The function in data-model §7.6 was extracted verbatim from the document and run on PGlite 0.4.3 (PostgreSQL 17.5; semantics only, not a benchmark): 32 checks pass. Correct insert and update stamps; forged `created_by`, `updated_by` and `version` on INSERT; no bump, `version + 2`, reset to 1, forged `updated_by` and changed `created_by` / `id` / `created_at` on UPDATE each raise `P0001` with the documented message (column and table, no value); the ANONYMOUS and SYSTEM contexts (an anonymous context cannot claim SYSTEM; an `app.actor_id` never set behaves as anonymous); `ON CONFLICT DO UPDATE` with and without the update stamps; a multi-row INSERT with one forged row; the migrator exemption; a back-dated `updated_at` is tolerated; RLS order (wrong stamps and foreign organisation: the guard fires first; right stamps and foreign organisation: the policy rejects); the number-allocation statement fails before the §6.4 fix and passes after it; `session_replication_role = replica` bypasses the origin-enabled trigger (the accepted residual); `prosecdef = false`, `proconfig` pinned, trigger `tgenabled = 'O'`. One defect was found and fixed in the process: the first draft's comment contained the token `current_setting(` and would have failed the C15 (b) body scan. TASK-024 should lift these cases into C15 (d).
6. **The IAM correction is not scope creep.** The hourly verifier (data-model §5.6 step (i)) reads the sink records inside the worker. "Worker `s3:PutObject` only" could never have held, with or without the writer's compare. Read on one prefix of an Object-Lock bucket gives no way to alter or remove an anchor.
