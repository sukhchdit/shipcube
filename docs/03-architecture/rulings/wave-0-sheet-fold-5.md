## 3. Why — notes for conformance reviews

1. **The contradiction was between two sentences of my own amendment.** ADR-0008 am. 4 item 4 begins "only the kinds the route declares are considered" and ends with a stub clause and a cache rule that count any credential. The first sentence is the design (and ADR-0006 R-06); the rest was written for a stub that cannot verify anything and therefore cannot tell a stale credential from a current one. Reading it per route set, with the three foreign kinds, removes the ambiguity for the bearer and the guest-token authenticators as well, before they exist.
2. **Why the cookie's reach is three routes and not "everywhere it is sent".** A `Path=/` `SameSite=Strict` cookie is sent on every request of the host; what matters for CSRF is which routes accept it as authentication. With the declared-kinds rule that is `getCsrfToken` (safe) and the non-`GET` routes with `csrf: true`, enforced by the binding rule `CSRF_COOKIE`. A `[session]` route that accepted the cookie as an alternative would be a CSRF target with no token check.
3. **Why `private, no-store` does not follow presence.** Marking a response because a credential header arrived protects nothing when the route ignored the header: the body cannot vary by it. It costs the HTTP cache of every reference list for every signed-in user. The conservative generic test remains exactly where the route is unknown, at no cost because problem documents are `no-store`.
4. **Why a TASK-020 follow-up rather than PR #32 fix cycle 2.** Fix cycle 2 is light and evidence-bound; the follow-up touches `authenticate.ts`, `problem-handler.ts`, `credentials.ts`, `authorise.ts` and the helper, and the security round-3 delta is scoped to `define-route.ts`. Part 020-B is the next TASK-020 PR, due before TASK-027 (batch 0.8), which is the first consumer.
5. **The gate, not the principal (PR32-SEC-14).** `tenantContextOf`'s rule "authenticated if and only if an actor is present" and the audit attribution of webhook writes both depend on providers having no actor. A provider that is "authenticated" would need an invented actor, and the audit trail would then name a user who does not exist. One branch on an existing catalogue flag fixes the 401.
6. **Report what is unresolvable in the file, not what is imported (T-83).** The review's wording would reject `handler: controller.cancel` and every imported handler, which is the layering of ADR-0003 (the controller is injected into the routes by the module index). The lint is lexical and per file by design; R6 at the service plus the idle-in-transaction runtime twin cover the cross-file case. The rule now refuses the shapes that hide a handler inside the file (a spec in a variable passed by parameter, a handler that is a parameter) and states in its header what it does not see.
7. **SEC-TC-14 as a cross-verify.** Bcrypt salts every hash, so "two hashes differ" is true for the same password twice. The property that matters is that a password changed after byte 72 no longer verifies; that is what truncation would break and what the pre-hash fixes.
8. **The `generated` edit is not manifest-only.** D-TASK276-02 said activation is manifest-only, D-TASK276-01 said the runner PR edits `heavy.mjs`; both can hold only if the `heavy.mjs` change is its own small PR (or part of a task that already owns tools/quality changes) before the activation PR. TASK-033 is the last Wave-0 generated suite and the code review named it, so it is the default owner with devops-engineer as the fallback; the plan-order first suite (TASK-024) does not run on lane B before the Wave-0-exit activation anyway.
9. **TASK-015 lines have deadlines, not dates.** 015-B and 015-C are due before G3; the merged-coverage hook is due before TASK-025 merges because TASK-025 is the first task whose critical code (the audit writer) is covered only by integration tests, and a coverage gate that counts unit coverage alone would pass it by construction.
