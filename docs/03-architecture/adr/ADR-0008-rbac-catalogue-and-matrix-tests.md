# ADR-0008: RBAC permission catalogue, roles as data and generated matrix tests

- **Status:** Accepted
- **Date:** 2026-11-12
- **Deciders:** principal-architect
- **Related:** brief §4.2, §11; REQ-RBAC-001..014, DR-A07, DR-A08; NFR-TENANT-002, NFR-SEC-011; ADR-0003 (route metadata), ADR-0005 (RLS)

## Context

Permissions are fine-grained strings declared once in `packages/authz`; roles are named sets editable by administrators (M2) and seeded now (operator 8, customer 5, partner 4); every route declares its permission; a generated test asserts allow/deny for every route × role plus unauthenticated and cross-tenant cases; permissions must be resolved server-side per request so changes apply within 5 s.

## Decision

1. **Catalogue.** `packages/authz/src/permissions.ts` (*2026-11-12: `permissions/<context>.ts` aggregated by `permissions/index.ts`, amendment 2*) exports `PERMISSIONS` as a readonly tuple of `{ key: 'resource:action[:qualifier]', description, category, operatorOnly: boolean }` (*plus the optional flags `reserved`, `signatureOnly`, `selfService`, amendment 2*) and the type `Permission = typeof PERMISSIONS[number]['key']`. Every reference in code (`defineRoute`, UI gating helper) is typed against `Permission`, so an unknown string fails type-check (REQ-RBAC-001). Format test: `^[a-z_]+:[a-z_]+(:[a-z_]+)?$`, uniqueness. Operator-only permissions: any `:any_org` qualifier, `audit:*`, `featureflag:manage`, `carrier:status:read` (DR-A07). Special markers `public` and `authenticated` are not permissions; they live in route metadata with a justification.
2. **Roles as data.** `roles(id, org_type, key, name, is_system)` and `role_permissions(role_id, permission_key)` (GLOBAL tables) seeded idempotently from `packages/authz/src/roles.seed.ts` (single source; the role–permission matrix document `docs/03-architecture/rbac-matrix.md` is generated from it in P5). *2026-11-12 (amendment 2): the tables are `permissions`, `roles(key, name_key, scope, is_system, description)` and `role_permissions(role_id, permission_id)` as in data-model §3.3; the source is `packages/authz/src/roles.ts`; the document is `docs/03-architecture/generated/role-permission-matrix.md`; seeding is a generated versioned migration, not `db:seed`.* Role changes in this run happen only by seed/migration and are audited as `CONFIG_CHANGE` by the system actor (REQ-RBAC-013). Partner roles are seeded without users (REQ-RBAC-003).
3. **Invariants test (build-time, REQ-RBAC-004):** Super Admin = full catalogue; Compliance Auditor ⊆ `*:read ∪ audit:*`; customer Viewer has no create/update/delete/manage; no customer/partner role holds an operator-only permission; every permission referenced by any route exists; every catalogue permission is held by at least one role or is explicitly marked `reserved` (seams such as `refund:approve`, `audit:export`, `shipment:create:on_behalf`). *2026-11-12 (amendment 2, REQ-RBAC-004 as reworded by D-058): "full catalogue" = every **role-assignable** permission (the `signatureOnly` webhook permissions are held by no role); the Compliance Auditor and Viewer invariants carve out the `selfService` set; every seeded role holds that set; every non-reserved, non-signature permission is held by at least one role **besides** Super Admin.*
4. **Resolution per request (REQ-RBAC-008).** `authorise()` loads the actor's ACTIVE membership in the token's active org and its roles → permission set; cached in Redis `authz:perms:<membership_id>` with TTL 5 s and invalidated on membership change. Order: authenticate → MFA gate → authorise → rate-limit → validate (DR-A08), so denied callers learn nothing about schemas. Denial → 403 `AUTHZ_DENIED` + audit `PERMISSION_DENIED` (route template, required permission) + security event `permission_denied`. `GET /me` returns the effective permission list for UI gating (REQ-RBAC-009); the UI helper `can(permission)` hides controls from the accessibility tree; route guards show the permission-denied state without fetching (REQ-RBAC-010). Download/export routes carry their own `*:download`/`*:export` permission checked before any URL is issued (REQ-RBAC-012).
5. **Matrix generator (REQ-RBAC-011).** `packages/authz/src/testing/matrix.ts` reads the route registry + role seed and emits Jest cases: for each route × seeded role → expect 2xx/other (allow) or 403 `AUTHZ_DENIED` (deny); for each protected route → 401 `AUTH_REQUIRED` unauthenticated; for each route with a tenant-owned `:id` → 404 for a foreign ID; staff routes → 403 `MFA_ENROLMENT_REQUIRED` for an un-enrolled staff session. Routes supply a `fixture` factory in metadata (`matrixFixture`) that creates a minimal valid request per role/tenant; a route without a fixture fails the generator ("not covered"). Run in CI; coverage count reported (NFR-TENANT-002).
6. **Seam for M2/M3.** Role editor and signed role changes (`reasonRequired`), API-key scopes (`API_KEY` actor with a permission subset), on-behalf (`shipment:create:on_behalf` + `on_behalf_of_org_id`) are catalogue entries now and features later.

## Alternatives considered

- **Permissions in the JWT.** Faster but violates REQ-RBAC-008 (5 s propagation) and bloats tokens.
- **Attribute-based policies (OPA/Cedar).** More expressive than needed for M1; the string catalogue + RLS covers tenant scoping; revisit if partner sub-account rules (M3) outgrow role sets.
- **Hand-written authz tests per route.** Rejected: the generated matrix is the brief's requirement and guarantees coverage as routes are added.

## Consequences

- Positive: a single typed catalogue; roles are data; coverage is mechanical; denial is audited.
- Negative: every route needs a matrix fixture (small, but mandatory — included in the task DoD); the 5 s cache means a revoked member keeps access for up to 5 s (accepted by REQ-RBAC-008).

## Amendment 3 (2026-11-12, TASK-013 PR #8 round 2 @498e3a5; code review R2-m1/R2-n1/R2-n2/R2-n3, security review PR8-SEC-05/06/07/10/13/14; `rulings/wave-0-batch-3-rulings.md` Part 2; D-ARCH-069)

1. **Compliance Auditor narrowed to read ∪ {`audit:export`} ∪ selfService (R2-n1).** §3 and amendment 2 allowed "any `audit:*`", so a future destructive audit verb (`audit:purge`, `audit:anchor:rotate`, …) granted to the Compliance Auditor would pass the guard (probe P4). ## Amendment 4 (2026-11-13, PR #32 security review PR32-SEC-02 (condition C2) and PR32-SEC-09, code review m7; D-ARCH-107)

1. **`auth` is a closed set of credential kinds.** The kinds are `anonymous`, `session` (the bearer access token; the name is kept), `refresh-cookie` (`__Host-rt_web` or `__Host-rt_admin`), `quote-token` (`X-Quote-Token`) and `signature` (webhook and push signatures). A route declares one kind (`auth: 'session'`, unchanged) or a set; `defineRoute` normalises both to a frozen array in the order of the list above. The accepted sets are exactly `[anonymous]`, `[session]`, `[refresh-cookie]`, `[signature]`, `[anonymous, session]` (optional bearer: `createQuote`) and `[session, quote-token]` (bearer or guest token: `getQuote`, `streamQuoteResults`); any other combination fails `defineRoute` and the boot check. The set is the operation's `security` list read one to one (`{}` = anonymous, `bearerAuth` = session, `refreshCookieWeb`/`refreshCookieAdmin` = refresh-cookie, `quoteToken` = quote-token, `*Signature` = signature), so the parity test compares sets. **`refresh-cookie` is its own kind** because `refreshSession`, `logoutSession` and `getCsrfToken` are called with an expired or absent access token: a generic bearer authenticator in front of them would make refresh impossible. A companion credential on a session route (`claimQuote`, `saveQuote`, `createShipment` also take `X-Quote-Token`) is not an alternative: the route is `[session]`, the token is a declared header the handler checks against the quote.
2. **Dual-mode permission.** `RouteSpec.permissionAuthenticated` carries the contract's `x-permission-authenticated`. It is required exactly when the permission is the `public` marker and the set is `[anonymous, session]` or `[session, quote-token]`, and it must then be a catalogued permission that is neither `selfService` nor `signatureOnly` (`quote:create`, `quote:read`); it is refused everywhere else. A catalogued permission or the `authenticated` marker requires the set `[session]`; a `signatureOnly` permission requires `[signature]`; a signature route declares a signature-only permission or `public` (PR8-SEC-05 (c) and D-TASK020-03 unchanged); a non-`GET` `refresh-cookie` route requires `csrf: true`. These are four new rules of `findRouteBindingViolations` (`AUTH_SET`, `PERMISSION_AUTH`, `DUAL_MODE`, `CSRF_COOKIE`) beside the four of amendment 3, with one negative test each; they replace m7's one-line refusal of `auth: 'anonymous'` with a non-`public` permission.
3. **The principal records the credential.** `Principal.credential` is one of the kinds (the anonymous principal carries `anonymous`). `Principal.authenticated` keeps its meaning, "a user actor is authenticated", so the context builder's rule "authenticated if and only if an actor is present" stays and needs no change: a `quote-token` principal is a guest (`authenticated: false`, no actor, `guestTokenHash` set) and a `signature` principal is a provider (`authenticated: false`, no actor, permissions limited to the route's own signature-only permission). This settles code-review n3 and the principal-kind remark of PR32-SEC-02. `principalOf` treats a principal without a known `credential` as anonymous.
4. **The authn slot (the real authenticators are TASK-052, TASK-055, TASK-091 and the webhook tasks).** Only the kinds the route declares are considered. (a) A bearer token that is present must be valid, and a failure is 401 (`ACCESS_TOKEN_EXPIRED`, `SESSION_REVOKED` or `AUTH_REQUIRED`); it is never replaced by another alternative. (b) When a bearer token and `X-Quote-Token` both arrive, the bearer decides and the guest token is not consulted. (c) With no usable credential: `anonymous` in the set gives the anonymous principal; otherwise `quote-token` in the set gives 404 `NOT_FOUND` (A-078: a wrong, malformed or missing guest token never reveals that a quote exists), and everything else gives 401 `AUTH_REQUIRED`. (d) A well-formed `X-Quote-Token` yields the guest principal with `guestTokenHash` = lowercase hex SHA-256 (ADR-0005 am. 10 item 8); its verification is the RLS policy and the quote lookup, not the slot. (e) `Cache-Control: private, no-store` is set from this step on when the set has no `anonymous` member and on any request that presented a credential, error responses included (SEC-TC-29). The PR #32 stub keeps failing closed: the anonymous principal when `anonymous` is in the set and no `Authorization` header, refresh cookie or `X-Quote-Token` is present, and 401 `AUTH_REQUIRED` with `private, no-store` otherwise.
5. **Authorisation is a credential gate, then a permission gate (this is condition C2).** (a) The credential gate runs for every permission value, `public` included: the principal's `credential` must be a member of `route.auth`, otherwise 401 `AUTH_REQUIRED`. The `public` marker therefore waives the permission and never the authentication the route declares, and a leaky or replaced authenticator cannot expose a refresh, a logout, a guest quote or a carrier push. (b) The permission gate: `public` passes, except that a `session` principal on a route with `permissionAuthenticated` must hold that permission in the active organisation (403 `AUTHZ_DENIED`); `authenticated` needs the user actor; a catalogued permission must be held (403 `AUTHZ_DENIED`), which a guest or provider principal can never satisfy except the provider principal's own signature-only permission.
6. **Verification.** The route-metadata test's `contractAuth` returns the set and compares sets; `x-permission-authenticated` equals `permissionAuthenticated` (api/README §15 row 12); seeded defects: a dropped `quote-token` alternative, a refresh route declared `session`, a missing `permissionAuthenticated`, one on a non-dual route, an unlisted combination. The generated RBAC matrix (TASK-027) reads the set and `permissionAuthenticated` and tests both branches of a dual-mode route plus a credential outside the set. The leaky-authn seam of PR32-SEC-02 runs on `public` + `signature`, `public` + `refresh-cookie`, `[session, quote-token]` and `[session]`. The SEC-TC-29 helper requires `private, no-store` when the operation's `security` has no empty alternative or the request it sent carried a credential (PR32-SEC-06 (a)). Owners: PR #32 fix cycle (metadata, rules, principal, stub, authorise, parity); TASK-052 (bearer), TASK-055 (refresh cookie, `csrf`), TASK-091 (guest token), TASK-171 and TASK-261 (signatures).

## Reversibility

High (data + generator).
