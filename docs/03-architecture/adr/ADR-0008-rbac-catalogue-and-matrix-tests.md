# ADR-0008: RBAC permission catalogue, roles as data and generated matrix tests

- **Status:** Accepted
- **Date:** 2026-11-12
- **Deciders:** principal-architect
- **Related:** brief §4.2, §11; REQ-RBAC-001..014, DR-A07, DR-A08; NFR-TENANT-002, NFR-SEC-011; ADR-0003 (route metadata), ADR-0005 (RLS)

## Context

Permissions are fine-grained strings declared once in `packages/authz`; roles are named sets editable by administrators (M2) and seeded now (operator 8, customer 5, partner 4); every route declares its permission; a generated test asserts allow/deny for every route × role plus unauthenticated and cross-tenant cases; permissions must be resolved server-side per request so changes apply within 5 s.

## Decision

1. **Catalogue.** `packages/authz/src/permissions.ts` (*2026-11-12: `permissions/<context>.ts` aggregated by `permissions/index.ts`, amendment 2*) exports `PERMISSIONS` as a readonly tuple of `{ key: 'resource:action[:qualifier]', description, category, operatorOnly: boolean }` (*plus the optional flags `reserved`, `signatureOnly`, `selfService`, amendment 2*) and the type `Permission = typeof PERMISSIONS[number]['key']`. Every reference in code (`defineRoute`, UI gating helper) is typed against `Permission`, so an unknown string fails type-check (REQ-RBAC-001). Format test: `^[a-z_]+:[a-z_]+(:[a-z_]+)?$`, uniqueness. Operator-only permissions: any `:any_org` qualifier, `audit:*`, `featureflag:manage`, `carrier:status:read` (DR-A07). Special markers `public` and `authenticated` are not permissions; they live in route metadata with a justification.
2. **Roles as data.** `roles(id, org_type, key, name, is_system)` and `role_permissions(role_id, permission_key)` (GLOBAL tables) seeded idempotently from `packages/authz/src/roles.seed.ts` (single source; the role–permission matrix document `docs/03-architecture/rbac-matrix.md` is generated from it in P5). *2026-11-12 (amendment 2): the tables are `permissions`, `roles(key, name_key, scope, is_system, description)` and `role_permissions(role_id, permission_id)` as in data-model §3.3; the source is `packages/authz/src/roles.ts`; the document is `docs/03-architecture/generated/role-permission-matrix.md`; seeding is a generated versioned migration, not `db:seed`.* Role changes in this run happen only by seed/migration and are audited as `CONFIG_CHANGE` by the system actor (REQ-RBAC-013). Partner roles are seeded without users (REQ-RBAC-003).
3. **Invariants test (build-time, REQ-RBAC-004):** Super Admin = full catalogue; Compliance Auditor ⊆ `*:read ∪ audit:*`; customer Viewer has no create/update/delete/manage; no customer/partner role holds an operator-only permission; every permission referenced by any route exists; every catalogue permission is held by at least one role or is explicitly marked `reserved` (seams such as `refund:approve`, `audit:export`, `shipment:create:on_behalf`). *2026-11-12 (amendment 2, REQ-RBAC-004 as reworded by D-058): "full catalogue" = every **role-assignable** permission (the `signatureOnly` webhook permissions are held by no role); the Compliance Auditor and Viewer invariants carve out the `selfService` set; every seeded role holds that set; every non-reserved, non-signature permission is held by at least one role **besides** Super Admin.*
4. **Resolution per request (REQ-RBAC-008).** `authorise()` loads the actor's ACTIVE membership in the token's active org and its roles → permission set; cached in Redis `authz:perms:<membership_id>` with TTL 5 s and invalidated on membership change. Order: authenticate → MFA gate → authorise → rate-limit → validate (DR-A08), so denied callers learn nothing about schemas. Denial → 403 `AUTHZ_DENIED` + audit `PERMISSION_DENIED` (route template, required permission) + security event `permission_denied`. `GET /me` returns the effective permission list for UI gating (REQ-RBAC-009); the UI helper `can(permission)` hides controls from the accessibility tree; route guards show the permission-denied state without fetching (REQ-RBAC-010). Download/export routes carry their own `*:download`/`*:export` permission checked before any URL is issued (REQ-RBAC-012).
5. **Matrix generator (REQ-RBAC-011).** `packages/authz/src/testing/matrix.ts` reads the route registry + role seed and emits Jest cases: for each route × seeded role → expect 2xx/other (allow) or 403 `AUTHZ_DENIED` (deny); for each protected route → 401 `AUTH_REQUIRED` unauthenticated; for each route with a tenant-owned `:id` → 404 for a foreign ID; staff routes → 403 `MFA_ENROLMENT_REQUIRED` for an un-enrolled staff session. Routes supply a `fixture` factory in metadata (`matrixFixture`) that creates a minimal valid request per role/tenant; a route without a fixture fails the generator ("not covered"). Run in CI; coverage count reported (NFR-TENANT-002).
6. **Seam for M2/M3.** Role editor and signed role changes (`reasonRequired`), API-key scopes (`API_KEY` actor with a permission subset), on-behalf (`shipment:create:on_behalf` + `on_behalf_of_org_id`) are catalogue entries now and features later.

## Alternatives considered

- **Permissions in the JWT.** Faster but violates REQ-RBAC-008 (5 s propagation) and bloats tokens.
- **Attribute-based policies (OPA/Cedar).** More expressive than needed for M1; the string catalogue + RLS covers tenant scoping; revisit if partner sub-account rules (M3) outgrow role sets.
- **Hand-written authz tests per route.** Rejected: the generated matrix is the brief's requirement and guarantees coverage as routes are added.

## Consequences

- Positive: a single typed catalogue; roles are data; coverage is mechanical; denial is audited.
- Negative: every route needs a matrix fixture (small, but mandatory — included in the task DoD); the 5 s cache means a revoked member keeps access for up to 5 s (accepted by REQ-RBAC-008).

Both are seeded: `carrier:status:read` to Super Admin, Admin, Operations, Support, Compliance Auditor; webhook permissions are held by no role (signature actor).

## Amendment 2 (2026-11-12, TASK-013 PR #8 @efe23df; D-T013-01..12 in D-TASK013-01; product-manager D-058; `rulings/wave-0-batch-3-rulings.md` items 3–5; D-ARCH-059)

The catalogue and role seed are implemented; the implementation is the specification where it deviated from §Decision for evidenced reasons.

1. **Layout and names (D-T013-01, D-T013-12).** `packages/authz/src/permissions/{quoting,booking,payments,organisation,account,platform}.ts` (one module per bounded context; every entry keeps its resource `category`) aggregated by `permissions/index.ts` (`PERMISSIONS`, `Permission`, `isPermission`, `ROUTE_MARKERS = ['public','authenticated']` kept out of `Permission`, `OPERATOR_ONLY_PERMISSIONS`, `permissionVerb`, `isReadPermission`); `roles.ts` (17 roles, `CATALOGUE_VERSION`, `ASSIGNABLE_CUSTOMER_ROLES`); `guard.ts` (`checkCatalogue`, `checkRoleInvariants` → typed `Violation[]` naming role and permission); `authorise.ts` (`authorise`, `effectivePermissions`); `routes.ts` (`assertRoutePermissions`, used by TASK-020's router enumeration); `matrix-doc.ts` and `seed-sql.ts` (renderers); `tools/authz/generate.ts` (`npm run authz:generate [-- --check]`) writes **`docs/03-architecture/generated/role-permission-matrix.md`** and the seed migration. The §Decision names `permissions.ts`, `roles.seed.ts` and `rbac-matrix.md` are withdrawn; `packages/authz/src/testing/matrix.ts` (§5, TASK-027) is unchanged.
2. **Flags and invariants (D-T013-02, D-T013-03, D-T013-04, D-T013-06; D-058).** Each entry carries `{ key, description, category, operatorOnly, reserved?, signatureOnly?, selfService? }`. **Super Admin holds every role-assignable permission** — the catalogue minus the two `signatureOnly` webhook permissions (`webhook:stripe:receive`, `webhook:mock_gateway:receive`), which are held by **no role** (the caller is the gateway's signature, not a user); REQ-RBAC-004 says the same since D-058. `reserved` seams (`shipment:create:on_behalf`, `refund:approve`, `audit:export`, and the new operator-only `shipment:read:any_org` and `org:read:any_org`, which give DR-A07's "any `:any_org`" rule concrete subjects) are held by Super Admin only. **Dead-permission rule:** every non-reserved, non-signature permission is held by at least one role besides Super Admin (otherwise the plain "held by some role" rule is trivially true) — hence `featureflag:manage` is granted to Operator Admin. **Verb rule:** a permission's verb is its last segment unless that segment is a scope qualifier (`any_org`, `on_behalf`), in which case it is the action segment; the only read-only verb is `read`. **"Audit permission" is keyed on the key, not the category** (PR #8 code review M1): `isAuditPermission(key) = key.split(':')[0] === 'audit'`, the same predicate `isOperatorOnlyKey` uses, and `checkCatalogue` enforces `category === resource` except through an explicit map (`payment_method → payment`, `notification_pref → notification`), so a free-text `category: 'audit'` can never widen the Compliance Auditor. The guard also asserts that `operatorOnly` equals the DR-A07 rule for every key and that `signatureOnly` is set only on `webhook:*` keys (PR8-SEC-02). The implied grant `shipment:create ⇒ tracking:read` (amendment 1) stands. **Self-service carve-out (D-058):** `session:manage`, `notification_pref:manage` and `notification:read` are flagged `selfService`, guard only `user`-tenancy `/me/*` routes (USER_OWNED rows, policy `user_id = app_actor_id()`, ADR-0005 am. 4) and are held by **all 17 roles**; the Compliance Auditor invariant reads "⊆ read ∪ audit ∪ selfService" and the Viewer invariant "no create/update/delete/manage **except** selfService, and none of `document:download`, `document:email`, `privacy:export`, `privacy:delete`"; a positive invariant asserts the set on every role. Cross-user session or preference management is M2 under distinct operator-only qualifiers. **`privacy:export` scoping (D-058 follow-up) is confirmed by construction:** the export runs inside `withTenantTx` with the requester's active organisation and actor, so shipments and quotes are RLS-bound to that organisation and user-owned rows to `app_actor_id()`; switching to the personal organisation exports personal-organisation data only, and the Viewer exclusion cannot be bypassed to exfiltrate business data (REQ-ACCT-016 is Could; its task adds the RLS test).
3. **Seeding by versioned generated migration (D-T013-07, D-T013-08; US-073, REQ-RBAC-013; PR8-SEC-01/03/08/09, PR #8 code review M2, D-SEC-PR8-01).** Roles and permissions are inserted by `prisma/migrations/<ts>_authz_seed_v<N>/{migration.sql,down.sql}`, rendered by `seed-sql.ts` from the catalogue with deterministic UUIDv7 ids (fixed timestamp + SHA-256 of `platform:authz:<kind>:<key>`), `INSERT … ON CONFLICT ("id") DO NOTHING` (the conflict target is the id, so a key collision with a foreign row raises instead of being swallowed), `created_by`/`updated_by` = the SYSTEM actor, header `data-changing: no` (new rows into tables created by the preceding migration; any `DELETE`, `UPDATE`, `ON CONFLICT … DO UPDATE` or `MERGE` makes a seed migration `data-changing: yes`, data-model §8.3 rule 10). **Released seed migrations are pinned:** `SEED_MIGRATIONS` in `tools/authz/generate.ts` records `{ dir, sha256: { up, down } }` per released version; when the rendered content of a pinned version differs, `--check` and the unit test fail with "catalogue changed: bump `CATALOGUE_VERSION` and add a seed migration", and write mode refuses to overwrite a pinned directory; until a **delta renderer** exists (v≥2 = only the new links and explicit revocations, never a full re-render whose `down.sql` would delete v1 rows), `artefacts()` throws for `CATALOGUE_VERSION > 1`. A generic immutability check (files under a merged `prisma/migrations/<dir>` never change against the base ref) belongs to TASK-016's linter or TASK-007's lane A. The reference seed (`db:seed`, TASK-023) does **not** write these tables. The REQ-RBAC-013 `CONFIG_CHANGE` entry is written by a **post-migrate reconciler** run as `SYSTEM_JOB` (TASK-221, US-073): it computes a digest of the three tables as read from the database, compares it with the last audited digest kept in `reference_dataset_versions('authz_matrix')`, writes one `CONFIG_CHANGE` entry (role, old → new permission set) per changed version — the first run back-fills the baseline ∅ → current — and writes nothing when the digest is unchanged (AT-US-073-04 by construction); a migration never inserts into `audit_entries` (hash chain, rule-12 lane). If TASK-221 is cut, the guard tests and CODEOWNERS on `packages/authz` + `prisma/migrations` are the residual controls and the G3 report says so. Database backstops before the M2 role editor (PR8-SEC-08, optional now): `ck_permissions__operator_only_rule` CHECK mirroring DR-A07, and a database-side assertion (integration test now, C-series later) that no non-OPERATOR role links to an `operator_only` permission and no role links to a `webhook:*` permission. `npm run authz:generate -- --check` and the AT-US-066-02 drift tests keep the document and the migration equal to the source. Prisma's `@@index([roleId], map: "ix_role_permissions__role_id")` cannot express `INCLUDE (permission_id)` (D-T013-09): the raw-SQL index is authoritative and the schema-drift check tolerates that single definition difference (data-model §7.3).
4. **`RoleScope` (D-T013-11)** lives in `packages/authz` until the shared enum module of data-model §1.7 exists, then moves.
5. **Required change to PR #8 before merge (D-058 b, confirmed here):** CUSTOMER_VIEWER + `session:manage`, `notification_pref:manage`; CUSTOMER_FINANCE + `notification_pref:manage`, `order:read`; CUSTOMER_ADMIN + `privacy:delete`; OPERATOR_COMPLIANCE_AUDITOR + `session:manage`, `notification_pref:manage`; the `selfService` flag on the three account permissions; the guard carve-outs and the positive self-service invariant (`SELF_SERVICE_MISSING`); regenerated matrix document and v1 seed migration (the v1 seed is unmerged, so no v2). Super Admin stays at 38.
