# ADR-0005: Tenancy model and PostgreSQL row-level security

- **Status:** Accepted
- **Date:** 2026-11-12
- **Deciders:** principal-architect, data-architect
- **Related:** brief §3.3 (RLS applicable), §4.2, §4.10; REQ-RLS-001..013, REQ-ORG, DR-A06, DR-A14, DR-A15, DR-A17; NFR-TENANT-001/002, NFR-SEC-011; A-042, A-055; ADR-0007 (audit), ADR-0008 (RBAC)

## Context

Every tenant-owned row carries `org_id`; the API must set `app.org_id`/`app.actor_id` with `SET LOCAL` inside each request transaction via a Prisma client extension; operator staff reach other tenants through an explicit audited policy; guest quotes exist before an account does (D-009) and must be reachable only by an unguessable token (A-055); integration tests must prove zero cross-tenant reads/writes. The official Prisma RLS example (github.com/prisma/prisma-client-extensions/row-level-security, checked 2026-11-12) wraps every query in a batch transaction with `SELECT set_config('app.current_company_id', $1, TRUE)`, and warns that explicit `$transaction` calls inside such an extension behave unexpectedly. Prisma 7 removed the Rust engine and uses driver adapters (`@prisma/adapter-pg`); interactive transactions remain available.

## Decision

### Tenant model

- `organisations.type ∈ {OPERATOR, BUSINESS_CUSTOMER, PARTNER, INDIVIDUAL}`; exactly one OPERATOR org; each user owns one INDIVIDUAL org; memberships carry roles (ADR-0008). Every authenticated request has exactly one **active organisation** (claim `org` in the access token; switch via `POST /auth/switch-organisation`, which re-issues tokens after checking an ACTIVE membership).
- Table classes: `TENANT` (`org_id NOT NULL`), `GUEST_CAPABLE` (`org_id NULL` allowed: `quotes`, `quote_packages`, `quote_options`, `quote_shares`), `USER_OWNED` (`users`, `sessions`, `refresh_tokens`, `mfa_*`, `notification_preferences` keyed by `user_id`), `GLOBAL` (reference data, roles/permissions, compliance packs, FX, feature flags, number sequences — read-only at runtime, no RLS), `SYSTEM` (`outbox_events`, `processed_events`, `idempotency_keys`, `audit_*` — no RLS; access only through platform code with explicit scoping columns).

### Transaction-scoped context (replaces "SET LOCAL" literally with its `set_config` equivalent)

All database access of a request or job runs inside `withTenantTx(ctx, fn)`:

```sql
SELECT set_config('app.org_id',          $1, true),   -- '' when none (guest/public)
       set_config('app.actor_id',        $2, true),   -- user id | system user id | '' anonymous
       set_config('app.actor_scope',     $3, true),   -- 'TENANT' | 'OPERATOR'
       set_config('app.guest_token_hash',$4, true);   -- hex sha256 of guest quote token, or ''
```

`set_config(..., true)` is transaction-local (equivalent to `SET LOCAL`), so pooled connections cannot leak context (REQ-RLS-003). The wrapper opens a Prisma **interactive transaction**, runs the statement above first, then passes the transaction client to repositories. Repositories receive only this handle (type `TenantDb`); the root `PrismaClient` is not exported outside `apps/api/src/platform/db` (lint rule). The Prisma client extension is used for soft-delete filtering and standard-column stamping, **not** for RLS (avoids the documented nested-transaction caveat). Workers set the same context from job payloads and fail non-retryably without a valid `org_id` when touching tenant data (REQ-RLS-008).

### Policies (templates; full SQL in data-model.md)

```sql
ALTER TABLE t ENABLE ROW LEVEL SECURITY; ALTER TABLE t FORCE ROW LEVEL SECURITY;
-- TENANT tables
CREATE POLICY t_tenant ON t FOR ALL TO platform_app
  USING (org_id = app_org_id())            -- app_org_id() = NULLIF(current_setting('app.org_id', true),'')::uuid
  WITH CHECK (org_id = app_org_id());
CREATE POLICY t_operator ON t FOR ALL TO platform_app
  USING (current_setting('app.actor_scope', true) = 'OPERATOR')
  WITH CHECK (current_setting('app.actor_scope', true) = 'OPERATOR');
-- GUEST_CAPABLE tables add:
CREATE POLICY t_guest ON t FOR ALL TO platform_app
  USING (org_id IS NULL AND guest_token_hash = app_guest_token_hash())
  WITH CHECK (org_id IS NULL AND guest_token_hash = app_guest_token_hash());
```

Permissive policies OR together. An unset or invalid `app.org_id` yields NULL comparisons → zero rows and rejected writes (REQ-RLS-004). `WITH CHECK` prevents writing a foreign `org_id` even if the application is buggy (mass assignment defence, NFR-SEC-011).

**Operator cross-tenant scope (DR-A15).** `app.actor_scope = 'OPERATOR'` is set by the server only when (a) the actor has an ACTIVE membership in the OPERATOR org and (b) the route's metadata declares `tenancy: 'operator-cross-tenant'` (in M1: the audit viewer only). The audit entry stores `target_org_id` (REQ-RLS-006). Client input can never set it (it is not a header or body field; a test asserts a customer member never obtains it).

**Guest rows (A-055, REQ-RLS-013).** `POST /quotes` as a guest creates the row with `org_id NULL` and `guest_token_hash = sha256(token)`; the 256-bit token is returned once and sent back as `X-Quote-Token`. Claiming (first `POST /quotes/{id}/claim` or booking by an authenticated account) runs, with both `app.org_id` and `app.guest_token_hash` set: `UPDATE quotes SET org_id = app_org_id(), claimed_by_user_id = app_actor_id(), claimed_at = now(), guest_token_hash = NULL WHERE id = $1 AND org_id IS NULL`. The guest policy admits the row for `USING`; the tenant policy admits the new values for `WITH CHECK`. Zero rows → the service re-reads under its own org scope: visible → already claimed by this org (idempotent 200); not visible → 409 `QUOTE_ALREADY_CLAIMED` if the quote exists for another org (detected via a SECURITY DEFINER helper `quote_claim_state(id)` returning only `CLAIMED_ELSEWHERE | UNKNOWN`), else 404. Share links use `quote_shares.share_token_hash` with the same branch pattern and a projection view that strips personal data (DR-B31 analogue).

**USER_OWNED tables (DR-A14).** Policy `user_id = app_actor_id()` OR operator scope; memberships additionally readable by members of the same org (`org_id = app_org_id()`).

### Roles

`platform_app` (runtime): `NOSUPERUSER NOBYPASSRLS NOCREATEDB`, not the owner; `SELECT/INSERT/UPDATE` on tenant tables, **no `DELETE`** on soft-deletable tables, `INSERT/SELECT` only on audit tables, `DELETE` only on the hard-delete allow-list. `platform_migrator`: owner, runs migrations and seed only; never used by api/worker (REQ-RLS-005). Tests read `pg_roles`/`pg_class.relrowsecurity`/`relforcerowsecurity` and `information_schema.role_table_grants`.

### Cross-tenant 404 (A-042)

A crafted foreign ID is invisible under RLS, so the API answers 404 `NOT_FOUND`; no `PERMISSION_DENIED` audit entry can be written for an invisible row. The platform counts 404s per actor per minute and emits `cross_tenant_probe` (security log) above 20/min (REQ-SEC-012).

## Alternatives considered

- **Schema-per-tenant or database-per-tenant.** Strong isolation but thousands of INDIVIDUAL orgs make it unmanageable with Prisma migrations; rejected.
- **Application-level filtering only.** One missed `where` leaks data; brief §3.3 makes RLS mandatory.
- **RLS via Prisma query extension wrapping every call in a batch transaction** (official example). Rejected for the nested-transaction caveat and because the audit entry and outbox must share the business transaction anyway; the explicit `withTenantTx` makes the transaction boundary visible.
- **`BYPASSRLS` role for operator staff.** Rejected by brief §4.10 ("not by bypassing RLS globally"); the explicit policy branch is audited per route.
- **Guest quotes stored outside the tenant tables (Redis only).** Rejected: quotes must survive 24 h, be shareable and be claimed atomically; A-055's nullable-`org_id` pattern keeps one table.

## Consequences

- Positive: defence in depth (RLS + authz + validation); operator access is explicit and audited; one transaction per request simplifies audit atomicity.
- Negative: every repository call needs the transaction handle (enforced by types); ~~`set_config` adds ~0.2 ms per transaction~~ the context statement costs one extra database round trip per transaction plus ~0.1 ms server-side (*reworded 2026-11-12, SPK-03 §4, amendment 10 W-1*); policies must be re-generated for every new tenant table (data-model.md provides the template and a catalog test fails on omissions).
- Verification: generated RLS tests per table and per route (REQ-RLS-007, NFR-TENANT-001), raw-connection fail-closed test (REQ-RLS-004), guest/claim race test, operator-scope negative test, role attribute test.

## Amendments after the threat model (2026-11-12, threat-model.md R-01..R-04, T-32, T-37)

1. **Pre-authentication and cross-tenant lookups have an explicit, narrow access path (R-01).** Code paths that must read rows before a tenant/actor context exists — login by e-mail, refresh-token and one-time-token redemption (verify, reset, invitation, MFA challenge), public tracking lookups, shared-quote resolution, gateway-reference lookup for webhooks, carrier push matching, the payment sweeper and the tracking poll planner — never use the migrator role, `BYPASSRLS` or broad policies. Two mechanisms only:
   - **Allow-listed `SECURITY DEFINER` functions** owned by `platform_migrator`, each returning a fixed, minimal column set and taking a hashed/opaque key (`auth_lookup_user_by_email(email) → (user_id, status)`, `auth_lookup_credential(user_id)`, `auth_lookup_refresh_token(token_hash) → (token_id, family_id, session_id, user_id, status, expires_at)`, `auth_lookup_one_time_token(purpose, token_hash)`, `invitation_lookup(token_hash)`, `payment_lookup_by_gateway_ref(gateway, ref) → (payment_id, org_id)`, `quote_share_resolve(share_token_hash) → projection without personal data`). Each function is listed in `data-model.md §4.5`, has a dedicated test, and `platform_app` has `EXECUTE` on these only. After the lookup resolves the actor/org, the same transaction sets `app.actor_id`/`app.org_id` and continues under normal policies.
   - **Global index tables without personal data** (`tracking_index(tracking_number, order_number, shipment_id, org_id, carrier_code)`, `gateway_refs(gateway, gateway_ref, payment_id, org_id)`, `tracking_poll_schedule(shipment_id, org_id, next_poll_at, interval_class)`), maintained in the same transaction as their source rows; the worker iterates `org_id`s from them and then sets tenant context per organisation (REQ-RLS-008).
2. **Operator branch is read-only in M0/M1 and checks membership in the database (R-02).** `t_operator` policies are `FOR SELECT` only this run (the only cross-tenant route is the audit viewer); `USING (current_setting('app.actor_scope', true) = 'OPERATOR' AND app_is_operator())`, where `app_is_operator()` is a `STABLE SECURITY DEFINER` function verifying an `ACTIVE` membership of `app_actor_id()` in the OPERATOR organisation. Write-capable operator branches arrive with M2 features through superseding migrations.
3. **Tenant context comes only from the token (R-03, T-32).** `app.org_id` is always the access token's active organisation; a path `{orgId}` that differs from it yields 404 `NOT_FOUND` before any query (operator cross-tenant routes carry the target organisation explicitly and are audited). A user who is Admin in A and Viewer in B must switch organisation (new token) to act in B.
4. **Guest claim re-scopes child rows; per-user policies for user-private data (R-04).** The claim transaction updates `quotes`, `quote_packages`, `quote_options` and `quote_shares` (`org_id`, `guest_token_hash = NULL`) atomically. `saved_payment_methods`, `notification_preferences`, `notification_log` and `sessions` are `USER_OWNED` (policy `user_id = app_actor_id()` within the org) so organisation members cannot read each other's private data.
5. **Operator scope only in the admin app (R-08 part).** The OPERATOR organisation can be the active organisation only for tokens with `app = admin`; the customer app never obtains operator scope.
6. **Roles refined (data-model.md §12, 2026-11-12).** The SECURITY DEFINER lookup functions are owned by a dedicated `NOLOGIN` role **`platform_definer`** (no table ownership, no DDL) that holds only the narrow policies and grants those functions need (SELECT on the tables they read; DELETE with an expiry predicate on token tables for `purge_expired_tokens()`); `platform_migrator` has no runtime policies; `platform_app` has EXECUTE on the functions only. Vault and erasure-scoped hard deletes belong to a separate **`platform_erasure`** role used only by the M4/M5 erasure job. `app_org_id()` returns NULL (zero rows) on a malformed setting instead of raising. `quote_claim_state(id, guest_token_hash)` requires the guest token hash so claim state cannot be probed by ID. Revoking another user's sessions writes the Redis revocation set synchronously (≤ 5 s, REQ-AUTH-009) and updates `sessions` in a worker job scoped to that user.

(c) A fourth database role, `platform_audit_owner` (`NOLOGIN NOINHERIT`), owns the audit module (ADR-0007 amendment 7); `platform_migrator` is not a member of it, so the role set is `platform_app` (RLS-bound), `platform_definer` (allow-listed lookups), `platform_erasure` (vault deletes), `platform_audit_owner` (audit objects, DDL only via `ensure_audit_partitions`) and `platform_migrator` (everything else), with the cluster-admin bootstrap credential used once per environment.

## Amendment after the remediation verification (2026-11-12, review §14.4 SEC-P3-27; ADR-0007 amendment 8; D-ARCH-033)

8. **Uniform search path for definer functions; schema ownership by a no-member role.** (a) Every `SECURITY DEFINER` function — the amendment 1/7 allow-list, `app_is_operator()` and `platform.job_context()` — declares exactly `SET search_path = pg_catalog, pg_temp` (`pg_temp` last, `public` absent) and schema-qualifies every relation it reads (`public.sessions`, …) and every built-in it calls (`pg_catalog.current_setting`, `pg_catalog.format`, …); the previous `pg_catalog, public` is withdrawn because a better-matching overload in `public` wins resolution regardless of path order (CWE-426, CVE-2018-1058 class). Catalog test C11 asserts exactly one `proconfig` entry `search_path=pg_catalog, pg_temp` on every definer function; migration-linter rule 13 flags any definer function without it (data-model.md §4.2, §4.5, §4.6, §8.3). (b) Schemas `public` and `platform` are owned by a sixth role, **`platform_schema_owner`** (`NOLOGIN NOINHERIT`, no members, created in `00-roles.sql` before the database owner is changed); `platform_migrator` holds `USAGE, CREATE` on both (all Prisma Migrate needs), and `platform_definer` holds `USAGE, CREATE` on `platform` because `ALTER FUNCTION … OWNER TO platform_definer` requires the new owner to hold `CREATE` on the schema (a grant the definer migrations needed and lacked). The role set is therefore `platform_app`, `platform_definer`, `platform_erasure`, `platform_audit_owner`, `platform_schema_owner` and `platform_migrator`, plus the once-per-environment bootstrap credential. C13 covers both no-member roles (on RDS, exactly one ADMIN-only `pg_auth_members` row per role for the bootstrap master is allowed and treated as break-glass; SPK-08). The shadow-database initialisation renders the bootstrap SQL with `AUTHORIZATION` stripped (data-model.md §7.3). Effect: schema rename, `DROP SCHEMA … CASCADE` and `DROP TABLE`/`DROP FUNCTION` by schema ownership are closed by privilege, which is what lets ADR-0007 amendment 7 say that audit tampering needs the cluster superuser.

## Amendment after the batch-0.2 implementation rulings (2026-11-12, `docs/03-architecture/rulings/batch-0.2-rulings.md` items 1–2; security review SEC-P3-34 item 5, SEC-P3-37 item 1; D-ARCH-045, D-ARCH-046)

9. **The migrator owns nothing above the table level.** Amendment 8 (b) still said the schema owner is created "before the database owner is changed". That transfer is withdrawn: `platform_migrator` does **not** own the database. The database stays owned by the bootstrap role (the Compose superuser locally; the RDS master at M5), and the migrator holds exactly `CONNECT` on the database plus `USAGE, CREATE` on `public` and `platform`. Reasons: (a) a database owner can run `ALTER DATABASE … SET search_path`, a database-wide default that every session without a role-level setting inherits and that no event trigger can see (SEC-P3-34); (b) a database owner can `CREATE SCHEMA` and install trusted extensions, neither of which Prisma Migrate needs — TASK-003 verified on Prisma 7.10.1 / PostgreSQL 18 that `migrate deploy`, `migrate status` and `db execute` need neither database ownership nor `CREATE` on the database (`prisma/README.md`, SPK-08 record 3). Consequences: the trusted extensions (`pg_trgm`, `btree_gin`, `btree_gist`) are installed by the bootstrap role in `prisma/bootstrap/01-schemas.sql`; a new extension is a new bootstrap file; the shadow-database init rendering keeps the `CREATE EXTENSION IF NOT EXISTS` lines because the migrator owns the shadow database; migration-linter rule 14 rejects `CREATE SCHEMA`, `CREATE EXTENSION`, `ALTER DATABASE` and role DDL in `prisma/migrations/**`, since each would fail at deploy with `42501` (PostgreSQL checks `CREATE` on the database before the `IF NOT EXISTS` short-circuit of `CREATE SCHEMA`). SEC-P3-34 items 1–3 (role-in-database `search_path` for the bootstrap role, harness connections with `options=-c search_path=pg_catalog,pg_temp`, `pg_db_role_setting` catalog assertion) are implemented in TASK-003 rather than deferred to M5; C13 carries the assertions (data-model.md §4.6). **Default privileges** are global per creating role — `ALTER DEFAULT PRIVILEGES FOR ROLE platform_migrator | platform_definer | platform_audit_owner REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` in `01-schemas.sql` — because a per-schema `REVOKE` cannot remove a global built-in default (PostgreSQL *ALTER DEFAULT PRIVILEGES*: "you cannot revoke privileges per-schema if they are granted globally"); every `EXECUTE` for `platform_app` stays an explicit grant, and C11 asserts the three `pg_default_acl` rows. The role set and the trust model of amendments 7–8 are otherwise unchanged.

## Amendment after SPK-03 (2026-11-12, TASK-008 PR #7 @985a552; `docs/04-plan/spikes/SPK-03.md` §4, §5 F-01..F-13, §7 W-1/W-2; `rulings/wave-0-batch-3-rulings.md` item 2; D-ARCH-058)

10. **`withTenantTx` is confirmed as designed (verdict GO); wording corrected; spike findings made binding.** The spike proved exit items (a) context isolation across pooled connections, (b) fail-closed on unset or malformed context and (c) the guest claim under both policies on PostgreSQL 18.6 with Prisma 7.10.1 over `@prisma/adapter-pg`; the raw-`pg` fallback wrapper of PLAN §9 is not needed.

    - **W-2 (Transaction-scoped context).** The "nested-transaction caveat" cited in §Decision and §Alternatives belongs to the **RLS-by-query-extension** pattern, not to `withTenantTx`. In Prisma 7.10.1 a nested `tx.$transaction(…)` inside an interactive transaction is a **SAVEPOINT on the same connection** (`prisma_sp_<n>` through the adapter) and keeps the context; an inner throw rolls back only the inner work (F-01). The real hazard is calling the **root** `PrismaClient` — or a nested `withTenantTx` — inside the callback: it silently runs on another pooled connection **without context** (0 rows, no error; absence-based checks fail open; SYSTEM-table writes land outside the business transaction; a nested `withTenantTx` splits atomicity and can self-deadlock) and, under pool pressure, stalls until `maxWait` and fails with `P2028` (F-02, PR7-SEC-01).
    - **Binding for TASK-016 (`withTenantTx`, `TenantDb`, factory), TASK-051 and every definer migration, TASK-276 (RLS test helpers); items 11–14 fold in the PR #7 security review §4a (PR7-SEC-01..07, -09, -10):**
      1. `TenantDb = Omit<Prisma.TransactionClient, '$transaction' | '$queryRawUnsafe' | '$executeRawUnsafe'>` **at compile time and a run-time `Proxy` that throws on those members** (PR7-SEC-05); savepoints are not exposed until a use case appears, and then only as an explicit `savepoint(fn)` helper (F-01). The tokens `set_config`, `app.org_id`, `app.actor_id`, `app.actor_scope`, `app.guest_token_hash` are banned outside `apps/api/src/platform/db/with-tenant-tx.ts` (lint with exact-file test exemptions). **The database-side scan is by form, not by schema** *(corrected 2026-11-12, PR7-SEC-11, D-ARCH-065; the earlier "non-platform functions" exemption excluded exactly the schema that holds every `SECURITY DEFINER` function)*: catalog test C-series reads `pg_proc.prosrc` of every function in every non-system namespace (`public`, `platform` and any later schema) and (i) rejects any **write form** — `set_config(`, `SET`/`SET SESSION`/`SET LOCAL` followed by `app.`, `RESET`, `DISCARD`; (ii) allows a **read** of the four security keys (`current_setting('app.org_id'`, `'app.actor_id'`, `'app.actor_scope'`, `'app.guest_token_hash'`) only in the §4.2 helper allow-list, matched by `regprocedure`; reads of `app.correlation_id` (trigger messages) stay allowed everywhere. Migration-linter rule 16 (data-model §8.3) applies the same rule to `prisma/migrations/**`. Three negative fixtures: a `platform` function calling `set_config('app.org_id', …, true)`, a `public` function running `SET app.org_id = …`, and a non-helper reading `current_setting('app.org_id', true)` — each fails C-series and the linter; the current catalogue passes.
      2. The root client stays private to `apps/api/src/platform/db` (lint rule **added by TASK-016** — no such rule exists on `main`: `eslint.config.mjs` confines Prisma imports to the repository/db-platform/prisma/tools-db/test categories and nothing stops a repository from importing `platform/db/client.ts`; *corrected 2026-11-12, PR #7 round 2 R2-n1 / PR7-SEC-12 (a), D-ARCH-063*) **and the guard is run-time, not lint-only** (PR7-SEC-01, AT-US-075-04): an `AsyncLocalStorage` re-entrance guard throws `NESTED_TENANT_TX` when `withTenantTx` is entered inside a tenant transaction; no client is exported; SYSTEM-table writers (outbox, audit store, idempotency) are typed on `TenantDb` so they join the business transaction; a unit/lint check asserts that no repository imports the client module (F-02).
      3. `transactionOptions` are set explicitly in the factory: `maxWait` = the pool-checkout budget (default 2 000 ms, ≤ the pool `connectionTimeoutMillis`), `timeout` ≥ the `statement_timeout` set in the same context statement (data-model §4.1); `P2028` (checkout timeout or expired transaction) maps to a **retryable 503**, never 500; the role settings `lock_timeout = 2s` and `idle_in_transaction_session_timeout = 15s` also apply (F-03) — see item 12 for their drift protection.

## Amendment after the TASK-020 reviews (2026-11-13, security review PR32-SEC-01 and threat model T-83, code review PR #32 m4; D-ARCH-106)

17. **A tenant transaction holds database work only (T-83; binding).** Between `BEGIN` and `COMMIT` of a `withTenantTx` (an API request or a worker job step) the code runs database statements and bounded in-memory work. It makes no HTTP call, performs no queue, Valkey or object-storage operation, sends no mail and never sleeps. Two reasons: the transaction pins a pooled connection and a tenant context, and D-ARCH-086 caps a tenant at half the pool, so a held transaction is a noisy-neighbour lever bounded only by the 10 s Prisma timeout and the 15 s idle-in-transaction setting; and an effect performed before a failed `COMMIT` cannot be undone, which is the shape of the guardrails "captured payment without a booked shipment" and "duplicate label". Password hashing and verification (tens to hundreds of milliseconds of CPU) belong outside the transaction as well (recommended, not lint-enforced): a burst of anonymous logins would otherwise fill the `anonymous` admission key. The worker follows the same rule: a saga step is `withTenantTx` (persist the client reference), the carrier call with no transaction open, `withTenantTx` (record the outcome) (ADR-0014).
18. **Three sanctioned homes for a side effect, in order of preference.** (a) **The outbox** (ADR-0004): `outbox.publish(db, event)` in the handler's own transaction; the relay and the worker perform the effect. This is the default for notifications, saga steps, carrier booking, void and pickup, tracking polls, documents, and Valkey writes that must follow a commit (session revocation, cache invalidation). The route answers `202` with a pollable resource where the result is asynchronous. (b) **The `call` phase** when the response needs the external result (the Stripe client secret, carrier address suggestions, service points, pickup availability): a short read-only transaction (`load`), the call with no transaction open (`call`), then the write and the audit in a second transaction (`handler`). (c) **The `afterCommit` phase**: in-process continuation after `COMMIT` and after the response, best-effort and never needed for correctness (the start of the rate-shopping fan-out; a cache purge that also has a TTL). The route shape is the ADR-0003 amendment of the same date; the implementation is TASK-020 part 020-C.
19. **A database-less `prepare` phase is rejected.** Every synchronous external call in M1 needs a tenant-scoped read first: the addressed shipment, order or payment must resolve under RLS (a miss is a 404 before any carrier or gateway call, otherwise a foreign id spends carrier quota and leaks existence), amounts come from stored price snapshots, and the attempt counter lives in the database. A phase without database access would serve only CPU work. `transaction: 'none'` stays what it is: a route with no database handle at all.
20. **T-83 lint scope (`platform/no-external-calls-in-tenant-tx`; PR #32 fix cycle, security condition C1).** The rule reports a source (the global `fetch`; a call or `new` on a value import from `undici`, `node:http(s)`, `http(s)`, `bullmq`, `ioredis`, `@aws-sdk/*`, `stripe` or `nodemailer`, including same-file variables initialised from them; a member call on a name of the `names` option; a `setTimeout` sleep) when it sits lexically, closures included, inside a **tenant-transaction root**: (R1) a function passed to `withTenantTx(` or `.withTenantTx(` (as before); (R2) the `handler` of the object literal that is the first argument of `defineRoute(`, in any form (arrow, function expression, `handler() {}`, `async handler() {}`), unless that literal contains `transaction: 'none'` as a string literal; a `transaction` value that is not that literal, or a spread element in the literal, counts as `tenant`; `fixtureRoute(` (a test helper whose default is `none`) is a root only when its literal says `transaction: 'tenant'`; (R3) `handler: name` where `name` resolves, by scope analysis, to a function declaration or to a `const`/`let` initialised with a function or arrow in the same file: that function is a root; (R4) the `load` property of the same literal once it exists (a read transaction is a transaction); (R5) whole-file roots for code that only ever runs inside the caller's transaction, option `txFiles`, default `apps/api/src/platform/audit/**`, `apps/api/src/platform/outbox/writer.ts` and `packages/audit/src/store/**` (non-test files: the audit hook and the writers take a `TenantDb` and nothing else, item 2 of amendment 10); (R6) **any function, in any file, that takes the transaction handle as a typed parameter**: a parameter whose type annotation names a type of the option `txHandleTypes` (default `TenantDb`, `AppDb`, `AppTransactionClient`; generics and wrappers such as `Readonly<…>` are looked through) makes the function a root, because it runs inside the caller's transaction by construction. R6 is what reaches the real layering (`routes -> controller -> service -> repository`, the controller injected into the routes by the module index, so `handler: controller.cancel` cannot be resolved, but the service method `create(db: AppDb, …)` it ends in is checked in its own file) without resolving imports. It is type-name based on purpose: a parameter that merely happens to be called `db` or `ctx` (a readiness check taking the database runtime, a carrier adapter taking its `CarrierContext`) is not a root. **Not roots:** `call`, `afterCommit`, the handler of a `transaction: 'none'` route and everything else; a function in another file that takes no handle is not checked in itself (it reaches the transaction only through a caller). Calls from a root into a function that takes no handle stay a review item, narrowed by layering (modules reach carriers, the payment gateway, storage and mail only through ports, and the task that introduces a port adds its binding names to `names` with one fixture) and by the runtime twin of item 21. `outbox.publish(db, event)` is database work and stays legal: a positive fixture pins it, and `outbox` is never added to `names`.
21. **The escape hatch, the ratchets and the runtime twin.** The only hatch is `transaction: 'none'` on the route, which `defineRoute` allows only on `public`-tenancy routes whose `audit.action` is `NONE` (PR32-SEC-05 (d)); such a route has no database handle at all. The route-metadata test pins the set of `transaction: 'none'` operationIds (today the health operations), so a new one is a visible, reviewed change, and a unit test fails when a file under `apps/*/src` or `packages/*/src` contains an `eslint-disable` directive that names this rule. **Runtime twin (detective; it catches the cross-file case the lint cannot):** the API test lanes run with `DB_TX_IDLE_IN_TRANSACTION_TIMEOUT_MS=1000` (the key exists, minimum 1 000 ms; production keeps 15 000), so a Mock-carrier `latency` scenario of 1 500 ms or more driven through a route that keeps a transaction open across the carrier call ends with the session killed and a failed test; one integration test proves it with a service in another file and shows the same route passing once it uses `call`. Verification of this amendment: the TASK-020 negative fixtures and ratchets (fix cycle), the TASK-020 part 020-C suites, `[T-83]` in the security test plan.

22. **Lexical residuals of the rule, closed in TASK-020 part 020-C (round-2 reviews: security PR32-SEC-12, code review R2-m3; D-ARCH-111).** Roots R1-R6 and the sources of item 20 do not change. What changes is how much of the code the rule can resolve and what it does with the rest: it fails closed on what it cannot resolve **in the file**, and it states what stays out of reach. One negative fixture per form (under `tests/fixtures/lint/rules/no-external-calls-in-tenant-tx/` and `tools/lint/negative-fixtures.test.ts`); the positive controls of item 20 stay green.
    - **Roots.** (a) `defineRoute(` and `fixtureRoute(` are recognised through import aliases (`import { defineRoute as route }`). Their first argument is walked as R2 when it is an object literal or an identifier that resolves to a same-file `const` object literal (`const spec = { …, handler }; defineRoute(spec)`); any other first argument (a parameter, an import, a call result) is reported: *declare route specs as an inline literal or a same-file const literal*. (b) A `handler` value is a root when it is a function expression, a same-file function name (R3), or a call with a function expression or a same-file function name among its arguments (the decorator `timed(async () => …)` is walked through those arguments). It is reported, with *declare route handlers inline or as same-file const functions*, when it is a function parameter, a `let` or `var` binding, or a call with no function argument (`makeHandler(deps)`); a route-building helper whose handler arrives as a parameter is therefore reported at its `defineRoute` call. It is **not** reported when it is a member expression (`controller.cancel`) or an imported binding: those are the injected-controller and cross-file shapes that R6 reaches at the service (item 20; a rule that rejected them would reject the layering of ADR-0003). (c) The methods of a class whose constructor has a parameter property typed with a `txHandleTypes` name (`constructor(private readonly db: TenantDb)`) are roots: the handle outlives the call otherwise.
    - **Sources.** (d) A member call whose receiver chain **ends** in a `names` entry matches at any depth (`ctx.deps.queue.add()`, `services.queue.add()`, `a.b.queue.add()`), and one same-function `const` alias of such a chain matches (`const q = deps.queue; q.add()`); the holders `deps` and `this` are no longer special. (e) `scheduler.wait` from `node:timers/promises` (any local name) and `Atomics.wait` join the sleeps (`setTimeout` from `node:timers/promises` already is one). (f) A literal `import('x')` (string or no-substitution template) of an `EXTERNAL_MODULES` entry inside a root is external I/O, like the static import.
    - **Import controls** (in `tools/eslint-rules/module-sources.mjs` and `eslint.config.mjs`, with `static-module-specifier`): `createRequire` is resolved through import aliases and namespace members (`import { createRequire as mk }`, `import * as m from 'node:module'`), and the core rule `no-eval` is enabled for `apps/*/src` and `packages/*/src`. Both are deliberate-evasion shapes in reviewed code, so they get a fixture each and nothing more.
    - **What stays out of reach (stated, not hidden).** A root that calls an imported function which takes no handle and performs I/O; dynamic dispatch (`obj[name]()`); a handler produced by a build step. The answers are R6 at the service, the `names` option for ports (every task that introduces a port adds its names, item 20) and the runtime twin of item 21. Once the rule is on `main` its fixtures are pinned by the base-ref no-weakening step.
