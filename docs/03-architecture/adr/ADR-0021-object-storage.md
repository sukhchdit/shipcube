# ADR-0021: Object storage — S3 API, RustFS locally (MinIO retired), SHA-256 integrity, pre-signed URLs, virus-scanning seam

- **Status:** Accepted
- **Date:** 2026-11-12
- **Deciders:** principal-architect, platform-architect
- **Related:** brief §4.10 files, §4.3 raw payloads, §4.9 archive, §10 (S3 buckets); REQ-DOC-*, REQ-CARR-018, REQ-AUDIT-018, REQ-RBAC-012; D-025; NFR-SEC-013, NFR-REC-003, NFR-AUDIT-007; ADR-0019

## Context

Files (labels, invoices, customs documents, raw carrier payloads, exports, future uploads) live in S3 with versioning, SSE-KMS, a stored SHA-256, virus scanning on upload (no uploads in M1, D-025) and short-lived pre-signed URLs after a permission check; every download is audited. Brief §10 asks for "S3-compatible storage" in Compose. Verified 2026-11-12: **MinIO's community edition is archived** (no Docker images/binaries since 2025-10, repository archived 2026) and **LocalStack now requires an account/auth token** (release 2026.03.0), so neither is an acceptable zero-friction local store under the maintained-dependency guardrail. **RustFS** (Apache-2.0, S3-compatible, 1.0 GA 2026-09-16, Docker image, maintained) is the chosen local server; SeaweedFS (Apache-2.0) is the fallback.

## Decision

1. **Port** `ObjectStorage { put(bucket, key, bytes|stream, { contentType, sha256, metadata }), get(bucket, key), head, presignGet(bucket, key, ttlSeconds ≤ 300), delete (allow-listed callers only) }` implemented once with `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner` against any S3 endpoint (`STORAGE_ENDPOINT`, `STORAGE_FORCE_PATH_STYLE=true` locally). No other code imports the AWS SDK for S3.
2. **Buckets** (names from config; per environment): `documents` (labels, invoices, customs docs), `raw-carrier-payloads` (redacted request/response JSON, ADR-0010), `exports` (M2+), `audit-archive` (M5, Object Lock compliance mode), `inbound-mail` (M4). Keys: `org/<org_id>/shipment/<shipment_id>/<doc_type>/v<version>/<uuid>.<ext>`; raw payloads `carrier/<code>/<shipment_id>/<op>/<uuid>.json`. Server-side encryption SSE-KMS in AWS; bucket versioning on for `documents`; local RustFS has versioning enabled where supported (spike confirms feature coverage — risk R-ARCH-05).
3. **Integrity**: SHA-256 computed while streaming on write, stored on the `documents`/`carrier_raw_payloads` row and as object metadata `x-amz-meta-sha256`; the restore rehearsal re-hashes a sample (NFR-REC-003); `documents` download responses include the hash for client verification.
4. **Downloads**: `GET /documents/{id}/download` → permission `document:download` (REQ-RBAC-012) → `DOWNLOAD` audit entry (SENSITIVE, fail-closed) → pre-signed GET URL with TTL **300 s** (D-025), `response-content-disposition` set, returned as JSON `{ url, expires_at, sha256 }` (no redirect, so the audit entry precedes the URL). Expired URL use → 410 `DOWNLOAD_EXPIRED` semantics on the Platform side (the store itself returns 403; the UI re-requests). Raw payload objects are never exposed to customers.
5. **Uploads**: none in M1. Seam: `UploadScanner { scan(bucket, key) → CLEAN | INFECTED | ERROR }` port with a `NoopScanner` that is **refused** in production config (fails start-up if an upload route exists without a real scanner); AWS implementation at M4 = S3 event → Lambda (ClamAV layer or GuardDuty Malware Protection for S3) → tag + quarantine bucket.
6. **Local/CI**: Compose service `rustfs` with a one-shot bucket-creation job; Testcontainers `GenericContainer('rustfs/rustfs:<pinned>')` for integration tests of the storage adapter (contract test also runnable against real S3 when credentials exist).
7. **Retention/erasure**: object lifecycle rules per bucket are M4/M5 (retention periods recorded in compliance packs); documents of erased subjects are deleted by the erasure job (hard delete allow-list).

## Alternatives considered

- **MinIO** — archived/no images (verified); a community fork (`pgsty/minio`) exists but is AGPL and young. **LocalStack** — account/token now mandatory; also AGPL-free but heavy. **SeaweedFS** — mature, Apache-2.0, S3 gateway; kept as fallback if the RustFS spike fails on pre-signed URLs or versioning. **Filesystem storage locally** — would diverge from the S3 code path and hide signing bugs.

## Consequences

- Positive: one S3 code path everywhere; audited, short-lived downloads; hashes for integrity and restore checks.
- Negative: RustFS is young (1.0 in 2026-09) — a Wave-0 spike validates pre-signed URLs, versioning, path-style access and `HEAD` metadata; fallback documented.

## Amendment after the P3 security review (2026-11-12, `docs/05-quality/security/P3-architecture-security-review.md` SEC-P3-03 item 7, SEC-P3-09, SEC-P3-21 item 5; D-ARCH-019, D-ARCH-028)

1. **`audit-anchors` sink (SEC-P3-03; amends §2 buckets).** New bucket `audit-anchors` holds the hourly signed anchor records of ADR-0007 amendment 7 (`anchors/<yyyy>/<mm>/<anchor_seq>.json`). Locally the sink is a file on a dedicated volume (`AUDIT_ANCHOR_SINK=file:…`); at M5 it is this bucket with **Object Lock in compliance mode** (retention ≥ 7 years), the worker task role holding `s3:PutObject` only (no delete, no `s3:BypassGovernanceRetention`) *(amended 2026-11-13, D-ARCH-094: plus read on the `anchors/` prefix — amendment 2 item 1)*, or a retention-locked CloudWatch Logs group. Providing the locked sink is a **G4 precondition for any production release** (risks.md R-ARCH-18). The `ObjectStorage` port gains `putIfAbsent` (conditional `If-None-Match: *`) so an anchor key is never overwritten.
2. **Carrier label and document bytes are validated at put time (SEC-P3-21 item 5, T-59; amends §3).** Bytes returned by a carrier (`createShipment` labels, paperless documents) are accepted only if the magic bytes match the declared format (`%PDF-`, PNG signature, ZPL `^XA`), the size is ≤ 5 MB and the content type is set explicitly from the detected format (never from carrier metadata); otherwise the saga records `LABEL_INVALID`, keeps the shipment `BOOKED` with documents pending and raises an alert. Downloads keep `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`. *(Read with amendment 3 item 1, D-ARCH-097: `nosniff` is added by a response-headers layer where one fronts the store; the control is the forced content type plus `attachment`.)*
3. **`SENSITIVE` documents (SEC-P3-09; amends §4).** Documents classified `SENSITIVE` (ADR-0019 amendment 1) are stored with SSE (SSE-KMS at M5), are never attached to e-mails and are downloadable only through the audited pre-signed path by holders of `document:download` (the customer Viewer is not one).

## Amendment 2 (2026-11-13, PR #30 / TASK-019 code review R1-m4 and R1-m6, security review PR30-SEC-06; D-ARCH-093, D-ARCH-094; `docs/03-architecture/rulings/wave-0-sheet-fold-3.md`)

Conditions on the `audit-anchors` sink of amendment 1; consumer TASK-116 (the anchor writer and the hourly verifier).

1. **IAM wording corrected.** "Worker role `s3:PutObject` only" (amendment 1; ADR-0007 amendment 7 item 7; data-model §5.5 "Sink") cannot hold: the hourly verifier reads the sink records every run (data-model §5.6 step (i)), and the writer's retry rule (item 3) reads the object it lost the race to. The worker role on the anchors bucket holds `s3:PutObject`, plus `s3:GetObject` and `s3:ListBucket` restricted to the `anchors/` prefix (`ListBucket` so that a missing key, 404, is told from an access error, 403), and nothing else: no delete, no `s3:BypassGovernanceRetention`, no `s3:PutObjectRetention` or legal-hold permission, no versioning change. The API role holds no anchor-bucket permission (it reads `audit_anchors`, not the sink). Tamper evidence is Object Lock plus the absence of delete and overwrite rights, never the port.
2. **Own credential and bucket.** The anchor sink is built from its own secret references and the `audit-anchors` bucket — never from the documents `RuntimeServices.storage` — and is typed `Pick<ObjectStorage, 'putIfAbsent' | 'head' | 'get'>`: no `put`, no `delete`. On RustFS the same credential's `put()` overwrote and `delete()` removed an anchor written by `putIfAbsent` (PR30-SEC-06 b). In Compose the values may coincide; the configuration keys, the type and (at M5) the IAM roles do not.
3. **Retry semantics belong to the writer, not the port (R1-m6).** *(Replaced 2026-11-13, D-ARCH-096, after PR #30 security r2 R2.5 and D-SEC-PR30-02: the first wording compared `head().sha256`, which is an unverified metadata claim.)* The sink line is a pure function of the `audit_anchors` row (JCS, data-model §5.5), so a retry re-sends identical bytes. The writer passes the digest of its line as `sha256` to `putIfAbsent`, so the store verifies it on receipt (`ChecksumSHA256`). `created: true`: done. `created: false` — the normal result of a retry whose first attempt succeeded but whose response was lost (412 `PreconditionFailed` on `If-None-Match: *`), and of a concurrent writer — says only that the key is taken. The writer then asks the sink wrapper `isWritten(key, digest)`, which decides from bytes the store vouches for and never from a metadata claim:
   - **(a)** `head()`: when `checksumSha256` (the SHA-256 the store verified when the object was written through the port; lowercase hex; present for single-PUT objects) is present, it is compared with `digest`.
   - **(b)** When it is absent (the object was not written through the port, or it carries a composite checksum, which the adapter drops), `get()` is called and the `sha256` the adapter **recomputed over the bytes** is compared with `digest`.
   - **(c)** `head().sha256` is never read. It is set by whoever wrote the object. Proven on the pinned RustFS with a key an attacker pre-seeded with other bytes and a metadata claim equal to the writer's digest: `head().sha256` equals the digest (the claim), `head().checksumSha256` does not, `get()` throws `INTEGRITY_MISMATCH`; with an object written without a SHA-256 checksum `checksumSha256` is `undefined` and `get()` still throws.
   - **Outcomes.** Equal: written (idempotent success). Different, absent after the 412, or `get()` throwing `INTEGRITY_MISMATCH` or `TOO_LARGE`: `ANCHOR_SINK_MISMATCH` (data-model §5.6) — alert, never an overwrite, never retried as transient. `UNAVAILABLE` from either call is transient and retried inside the sink window.
   - **Shape.** The wrapper that the anchor writer receives has exactly `putIfAbsent` and `isWritten(key, digest)`; the one the hourly verifier receives has exactly `read(key)` returning bytes. No `head` and no member that returns a hash is reachable from either, so no caller can read the claim. The verifier's byte-exact table/sink comparison (A-1, A-6) remains the control; this rule only decides whether the writer stops retrying.
4. **AWS 409 `ConditionalRequestConflict` (threat note).** *(Replaced 2026-11-13, D-ARCH-096: "until that lands it is `UNEXPECTED`" is withdrawn, it landed.)* S3 answers a conditional `PutObject` with HTTP **409** and code `ConditionalRequestConflict` while another conditional write to the same key is in flight, and says the request may be retried. RustFS never returns it, so the local suite cannot show it (R-ARCH-05). Ruling: it is **retryable**. The adapter maps it — and 400 `RequestTimeout` — to `UNAVAILABLE`, `BadDigest` to `INTEGRITY_MISMATCH` and `ExpiredToken` to `ACCESS_DENIED` (PR #30 head `5f45a8b`; code review r2 error-map probe; security r2 R2.3 row 4: a 409 gives `UNAVAILABLE` after one request, never `created: false`; merge pending). The writer retries `putIfAbsent` with jittered backoff inside the 15-minute sink retry window, ending in `created: true` or in `created: false` plus item 3. It is never success and never `created: false` without the item 3 check. `ACCESS_DENIED`, `INTEGRITY_MISMATCH` and `INVALID_ARGUMENT` are not retried: they fail the run closed with an alert, and the next hourly run starts again. The contract suite runs against real S3 before G4-production (Decision 6; SPK-05 section 4); the AWS-only shapes stay unit-tested until then.
5. **Exposure.** `RuntimeServices` exposes `storage: ObjectStorage` (the existing single client, documents) and `@platform/api/runtime` re-exports the port types once a consumer needs them — two lines, in PR #30's fix cycle, else in TASK-147 (the first documents consumer); the anchor writer is not that consumer. TASK-116 adds a separate worker-only `anchorSink` member built per item 2. *(Done in PR #30's fix cycle, head `5f45a8b`.)*
6. **Fail-closed credentials for the sink (added 2026-11-13, D-ARCH-096; PR #30 code review r2 flag 3, security r2 R2.7).** The documents client refuses a half-written credential pair before any client or pool exists (`StorageConfigError`, key names only; PR #30). The anchor sink takes the same posture. When `AUDIT_ANCHOR_SINK` is an `s3:` URL, its two secret references `AUDIT_ANCHOR_SINK_ACCESS_KEY_ID_REF` and `AUDIT_ANCHOR_SINK_SECRET_ACCESS_KEY_REF` (worker only) must both resolve or both be unset; exactly one is a start-up refusal that names the keys and never a value, raised by the configuration guard (exit 78; TASK-014 `CREDENTIAL_PAIRS`) and again, as defence in depth, by the worker composition before any client, pool or queue is created. Unset anchor references **never** fall back to the `STORAGE_*` references. In staging and production both anchor references are refused (the IAM task role is the identity, item 1), and the anchor bucket differs from `STORAGE_BUCKET_DOCUMENTS`. The `file:` sink of Compose and local needs no credentials, so the rule governs the `s3:` form that the integration tests run against RustFS and that M5 uses.

## Amendment 3 (2026-11-13, PR #30 / TASK-019 security review r2 PR30-SEC-02, -07, -09, -10 and R2.9, code review r1 n2; D-ARCH-097; `docs/03-architecture/rulings/wave-0-sheet-fold-4.md`)

Conditions on the download path. Consumers: TASK-147 (the documents core: the only module that touches `RuntimeServices.storage`), TASK-162 (the download route), TASK-155 (label put) and TASK-014 (Compose store vhost).

1. **What protects a pre-signed download (replaces the `nosniff` promise of amendment 1 item 2 and of the header list in Decision 4).** The browser fetches a pre-signed URL from the store, not from the Platform, so the Platform cannot add a response header to it and RustFS sends no `X-Content-Type-Options` (PR #30 security r2 R2.4). The controls are, in this order: **(a)** the forced `response-content-type` — the type stored at put time from the detected format (amendment 1 item 2), never request, carrier or user text — so a browser is told the declared type; **(b)** `Content-Disposition: attachment`, forced, with no way to ask for `inline` except item 2; **(c)** the store's public host is not the web or admin host — a regional S3 endpoint, or a dedicated host name behind CloudFront at M5 — and the app's `__Host-` cookies are host-only (ADR-0006), so a deployed store host never receives them and a document opened there has no ambient authority; in Compose the store shares the host name `localhost` with the apps (cookies ignore ports) and holds synthetic data only, which is accepted and is one more reason item 2 closes inline rendering; **(d)** `X-Content-Type-Options: nosniff` is added by a response-headers layer in front of `STORAGE_PUBLIC_ENDPOINT` wherever one exists — the Compose `edge` store vhost (TASK-014) and a CloudFront response-headers policy at M5 (platform.md) — as defence in depth, not as the control. A store reached directly (the RustFS port in local development) sends no such header, and that is accepted. Verification: the TASK-014 edge test fetches a pre-signed URL through the `edge` host and asserts 200, the forced type, `attachment` and `nosniff`; TASK-162 asserts the presign input and the download SEC-TC (expiry, tamper, method restriction, audit entry; AC-37).
2. **`allowInline` is closed by default and has no M1 caller.** `allowInline: true` together with an active content type (`text/html`, `image/svg+xml`, `application/xhtml+xml`, any `+xml` type, `application/xml`, a script type) serves a document as a page from the store origin — XSS by document (T-59). Rules: **(a)** the documents module owns one facade, `presignDownload(document, ttl)`, which is the only code in `apps/**` and `packages/**` that calls `presignGet`; it reads the bucket, key, `versionId` and `responseContentType` from the RLS-visible document row, builds the disposition (item 3) and never sets `allowInline`; **(b)** a repository test fails when `allowInline` appears in source outside `apps/api/src/platform/storage/**` and its tests; **(c)** an inline preview in a later milestone needs an amendment of this ADR that names the use, a facade method restricted to an allow-list of passive types (starting set `application/pdf`, `image/png`, `image/jpeg`; never `text/*`, `image/svg+xml`, a `+xml` type or a script type) and a security record; the type is still read from the row.
3. **One disposition builder, from server-held text.** The port takes `contentDisposition` as text (PR30-SEC-09: Unicode `trim()` admits U+00A0 before `attachment`, and the tail after `;` is unchecked). Rule: one pure function `attachmentDisposition(name)` exported by `platform/storage` returns `attachment; filename="<ASCII fallback>"; filename*=UTF-8''<RFC 5987 percent-encoding>`; the name is composed only from server-held parts (document type, shipment reference, version, an extension from a closed set) — never from carrier-supplied, customer-supplied or request text; the ASCII fallback keeps letters, digits, dot, underscore and hyphen; the port check is anchored on ASCII (`^(attachment|inline)[ \t]*(;|$)`, no Unicode `trim`) and refuses an `inline` token anywhere after the type.
4. **Keys, metadata and buckets (PR30-SEC-07, code review r1 n2).** One typed key builder in the documents module is the only code that constructs a key string: UUID-typed parts and closed enums, the grammar of Decision 2 (`org/<org_id>/shipment/<shipment_id>/<doc_type>/v<version>/<uuid>.<ext>`; raw payloads `carrier/<code>/<shipment_id>/<op>/<uuid>.json`), the organisation id from the tenant context and never from request input. The port additionally rejects a `.` segment, an empty segment (`a//b`) and a trailing `/` (RustFS answers 400 to two of them; a browser normalises dot segments and breaks the signature), caps the total user-metadata bytes (names plus values) at 2048 with `INVALID_ARGUMENT` before any I/O (instead of an S3 `MetadataTooLarge` reported as `UNEXPECTED`), and has one definition of the bucket predicate (the config `S3_BUCKET`). `presignGet` is called only with a locator read from the RLS-visible row, including its `versionId`, so the store serves exactly the audited object.

## Reversibility

High (port + S3 API).
