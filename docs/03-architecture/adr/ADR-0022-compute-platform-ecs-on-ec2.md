# ADR-0022: Compute platform — ECS on EC2 (capacity provider) vs plain Auto Scaling Group; Terraform written, validated and policy-checked, not applied

- **Status:** Accepted
- **Date:** 2026-11-12
- **Deciders:** principal-architect, platform-architect
- **Related:** brief §3.1/§3.3 ("EC2 (App Hosting) with Docker" → ECS on EC2 default, ASG alternative, decide in an ADR), §10; CLAUDE.md §3 (CLOUD_BUDGET 0, no prod target), §5 (IaC only via pipeline); D-002, D-007 #6; NFR-SCALE-003, NFR-AVAIL-001, NFR-OPS-004; platform.md §4–§6

## Context

Containers must run on EC2 instances in an Auto Scaling Group behind an ALB with autoscaling on CPU, request count and queue depth, with rolling and canary deploys and automatic rollback (CANARY_STEPS, ROLLBACK_TRIGGERS). Two deployables (`api`, `worker`) with different scaling signals; frontends are static. No AWS account or budget exists in this run: Terraform is written, `fmt`/`validate`/Checkov-checked, never planned against a real account or applied.

## Options analysis

| Driver (weight) | ECS on EC2 with capacity provider | Plain ASG + launch template (docker/systemd per instance) |
|---|---|---|
| Progressive delivery with automated rollback (5) | Native: ECS deployment circuit breaker; CodeDeploy blue/green with canary/linear traffic shifting and CloudWatch-alarm rollback | Build your own: instance refresh with weighted target groups, custom health analysis scripts |
| Independent scaling of api vs worker (4) | Two services on one cluster; service autoscaling per metric (ALB request count, CPU, custom queue depth); capacity provider scales the ASG to fit tasks | Two ASGs (double the instances at minimum) or co-located processes with coupled scaling |
| Bin-packing and cost at launch (3) | api + worker tasks share instances; 2–3 small instances suffice | One process type per instance → more instances |
| Operational burden (3) | ECS agent + task definitions; AWS-managed scheduler; no control plane cost | AMI/userdata lifecycle, process supervision, log shipping per instance |
| Secrets/config injection (3) | Task definition `secrets` from Secrets Manager; IAM task roles (least privilege per service) | Instance profile shared by all processes; custom secret fetch |
| Observability (2) | awslogs driver, ADOT sidecar/daemon, Container Insights | CloudWatch agent per instance; custom metrics |
| Lock-in / portability (2) | Images are standard OCI; task definitions are AWS-specific but thin; same images run in Compose | Lowest lock-in |
| Fit with brief (3) | Brief's stated default | Brief's named alternative |
| **Weighted result** | **≈ 4.6 / 5** | ≈ 2.7 / 5 |

## Decision

**ECS on EC2** with an EC2 **capacity provider** (managed scaling + managed termination protection) over an ASG of `t3`/`m7i`-class instances in private subnets (3 AZ). Services: `api` (behind ALB target group, service autoscaling on ALB `RequestCountPerTarget` and CPU), `worker` (no load balancer; autoscaling on CPU and a custom CloudWatch metric `queue_depth_total` published from `/metrics` via ADOT). Task roles per service (api: Secrets Manager read, S3 documents/raw buckets, SES send; worker: + KMS decrypt for envelope keys; neither has RDS/IAM admin). Deployments: `api` via **CodeDeploy blue/green** with a `Linear`/`Canary` config matching CANARY_STEPS (5 → 25 → 50 → 100 %, 10 min bakes) and auto-rollback on CloudWatch alarms (5xx > 2× baseline, p95 > budget, fast-burn SLO, unhealthy targets) — the ROLLBACK_TRIGGERS; `worker` via ECS rolling update with deployment circuit breaker (min healthy 100 %, max 200 %) and SIGTERM drain (ADR-0013). Frontends: static assets in S3 behind CloudFront (WAF attached) — platform-architect's decision (platform.md §4) — with the Nginx images retained for Compose and as a fallback target. Images: published to GHCR by CI (D-005); at M5 the ECS task pulls from GHCR via Secrets Manager registry credentials or a mirror to ECR (platform.md decides). **Terraform** modules + `dev/staging/prod` overlays, remote state S3 (locking per current Terraform guidance), tagging, least-privilege IAM, Checkov in CI; `plan`/`apply` jobs exist but are disabled until `DEPLOY_TARGET_*` and credentials (GitHub OIDC role) are configured; `destroy` never outside ephemeral environments. Terraform itself is BUSL-1.1 (a build tool, not a shipped dependency; HCL kept OpenTofu-compatible — D-ARCH-003).

## Alternatives considered

- **ECS on Fargate.** Simplest operations, but the brief fixes EC2-hosted containers; Fargate remains a one-line task-definition change if the constraint is relaxed.
- **EKS.** Over-engineered for two services; control-plane cost; not in the stack.
- **Plain ASG** — see table.

## Consequences

- Positive: canary + automated rollback is native; two services scale independently; images identical to Compose.
- Negative: ECS concepts (capacity providers, CodeDeploy for ECS) add Terraform surface; nothing can be exercised before an AWS account exists (NFR-SCALE-003/AVAIL-001/OPS-004 DEFERRED/PARTIAL).
- Verification now: `terraform fmt -check`, `validate -backend=false`, Checkov 0 failed (or suppressed with reason); workflow lint. At M5: staging apply from CI, canary drill, rollback drill.

## Amendments after the platform review (2026-11-12, platform.md PD-01..PD-10, verified sources listed there)

1. **Edge (PD-01).** One CloudFront distribution per app (web, admin) with WAF; `/api/*` on the same host routes to the ALB → `api`, keeping `__Host-` cookies host-only and CORS minimal; HTML served by the same Nginx images used locally (parity), hashed `/assets/*` from a versioned S3 bucket via OAC so old chunks keep loading during deploys; the ALB accepts only CloudFront traffic carrying an `X-Origin-Verify` secret header. Staging may use the CloudFront free flat-rate plan.
2. **Images to ECS (PD-02).** `cd.yml` copies the released image **digest** from GHCR (read with `GITHUB_TOKEN`) to ECR via OIDC; ECS pulls by digest. Direct GHCR pulls and the ECR pull-through cache were rejected because both require a long-lived GitHub personal token.
3. **Terraform state (PD-03).** S3 backend with native lockfile (`use_lockfile = true`, Terraform ≥ 1.11); no DynamoDB lock table (deprecated).
4. **Canary mechanics (PD-04).** Neither ECS built-in `CANARY`/`LINEAR` strategies nor CodeDeploy custom configs express unequal steps 5 → 25 → 50 → 100 (CodeDeploy offers one canary step or equal linear increments; ECS built-in offers one canary percentage or linear). The `api` service therefore runs as blue/green ECS services (`api-blue`, `api-green`) behind **ALB weighted target groups**, with the CD pipeline shifting weights 5/25/50/100 with 10-minute bakes and evaluating the ROLLBACK_TRIGGERS as CloudWatch alarms (5xx rate > 2× the stable colour, app-reported non-carrier p95 > budget — ALB latency includes SSE streams and is not used — SLO fast-burn, unhealthy hosts); an EventBridge → Lambda guard resets weights to the stable colour if the runner dies mid-bake. Fallback if this is judged too custom at M5: ECS built-in `CANARY` at 5 % (changes CANARY_STEPS; needs a logged decision by the orchestrator). `worker` and frontends use ECS rolling deployments with the deployment circuit breaker and alarms.
5. **Health checks (PD-05).** ALB target health uses `/health/live` so a database failover does not replace every task; `/health/ready` gates deployments and is scraped for alarms.
6. **Migrations (PD-07).** A separate `shipcube-migrate` image (Prisma CLI + seeds, migrator role) runs as a pre-deploy ECS task; runtime images carry no DDL tooling.
7. **Observability sidecar (PD-06).** ADOT collector per task: traces → X-Ray OTLP endpoint (X-Ray SDK/daemon are in maintenance since 2026-02-25; OTel is the path), `/metrics` → CloudWatch EMF with a restricted metric allow-list for cost.
8. **Local edge (PD-08).** A `edge` reverse proxy in Compose mirrors the CloudFront + ALB routing (TLS with a local certificate so `__Host-`/`Secure` cookies work) and is the scale-out balancer for `--scale api=2`.
9. **Scanners as pinned containers (PD-09).** Trivy, Semgrep, Checkov and Gitleaks run as digest-pinned container images (the `trivy-action` tags were hijacked on 2026-03-19/20, CVE-2026-33634).
10. **CI minutes (PD-10, OI-04 — high-impact, for the orchestrator).** The repository is private; GitHub Free includes ≈ 2 000 Linux minutes/month on 2-vCPU runners while P5 was estimated at ≈ 22 000 min/month. The default first applied here (a self-hosted `heavy` runner on the dev host plus a hosted PR fast lane) **was superseded on 2026-11-12 by the human's decision D-ORCH-001**: hosted PR fast lane, heavy suites run locally by test-runner with evidence committed under `docs/05-quality/`, and a dispatch-only hosted full lane at wave ends and gates — no self-hosted runner, no paid minutes (ADR-0023 amendment A–D; the label switch `HEAVY_RUNNER_LABELS` keeps the self-hosted option available). The A-029 reference host becomes the developer machine for k6 gates; hosted 2-vCPU numbers are reported, not gated.

## Amendment (2026-11-12, SPK-01): runtime image closure — `--omit=dev --omit=optional`, Studio-free migrate image, preflight (SPK-01 §3 F-13/F-14; D-ARCH-038; detail in ADR-0023 amendment I and platform.md §3.2)

11. **Runtime images (`api`, `worker`) install with `npm ci --ignore-scripts --omit=dev --omit=optional --workspace=apps/<app>`.** `--omit=dev` alone is not enough: the Prisma CLI (`prisma`), `@prisma/studio-core` (→ `elkjs`, `EPL-2.0` — *corrected 2026-11-12, PR1-SEC-05* — off the allow-list), `@visx/*` 4.0.x-alpha pre-releases and `typescript` are flagged `devOptional` in the lockfile — dev dependencies that are also optional peers of production packages (`@prisma/client` → `peerOptional prisma`; `react-router` → optional `typescript`) — and npm removes them only when both `dev` and `optional` are omitted. This keeps DDL tooling, Studio and the compiler out of the images that run as ECS services (least privilege, PD-07 intent) and keeps the production closure inside D-ARCH-003 rev 2 item 1 and item 5. bcrypt 6 is unaffected (its N-API prebuilds ship inside the package, not as optional dependencies), so `deps:rebuild` stays a conditional fallback.
12. **The `migrate` image is the only image with the Prisma CLI, and it carries no Studio.** `prisma` 7.10.1 declares `@prisma/studio-core` as a *regular* dependency (verified `npm view`, 2026-11-12), so `--omit=optional` does not remove it there. The `migrate` stage therefore runs an explicit, allow-listed prune (`tools/docker/prune-migrate-image.mjs`, Node) that deletes `node_modules/@prisma/studio-core` and `node_modules/@prisma/dev` with their exclusive subtrees (`elkjs`, `@visx/*`, `d3-*`) after the install, and the image test proves `prisma migrate status`/`migrate deploy` and the seed CLI still work against a Testcontainers PostgreSQL 18 (TASK-014 with TASK-003). Fallback if the CLI loads Studio eagerly: an in-image stub package `@prisma/studio-core` whose `index.js` throws "Prisma Studio is not available in this image". Invariants, asserted by the image tests and the Trivy licence scan (D-ARCH-003 rev 2 item 5): `node_modules/prisma` is absent from `api`/`worker`; `node_modules/@prisma/studio-core`, `elkjs` and any `*-alpha.*` version are absent from **every** image; no image contains `typescript` or `src/*.ts` of workspace packages.
13. **Preflight and test stripping.** Runtime stages end with `RUN node dist/preflight.js` (imports every production module and every `@platform/*` package, exits 0) so an omitted optional dependency fails the image build rather than the ECS task; compiled tests (`**/*.test.*`, `**/__fixtures__/**`, present in `dist/` because `tsc -b` compiles source and tests together, ADR-0002 amendment item 2) are stripped from the copied `dist/` by `tools/docker/prune-dist.mjs`. ECS task definitions and compose commands pass no `--conditions` flag (ADR-0002 amendment item 3), so the images resolve `@platform/*` to `dist/`.

## Amendment (2026-11-12, PR1-SEC): image rules from the PR #1 security review (`docs/05-quality/security/PR-0001-TASK-001-security-review.md` PR1-SEC-01/02/03/04/08/09; D-ARCH-040, D-ARCH-041, D-ARCH-044; extends amendments 11–13)

14. **Image invariants added.** (a) *Installs from the root only (PR1-SEC-01):* every image stage installs from the repository root with the root `package.json`, `package-lock.json` and `.npmrc` (`npm ci --ignore-scripts --omit=dev --omit=optional --workspace=apps/<app>`); no stage copies a per-app `package.json` alone, because `@platform/*` would then be resolved from a registry — the `.npmrc` pin makes that fail closed (ADR-0023 am. J item 1), and `check-install-flags` fails an install in a stage that has not `COPY`-ed `package-lock.json` and `.npmrc`. (b) *Schema engine (PR1-SEC-02):* the `migrate` image fetches and verifies `schema-engine-debian-openssl-3.0.x` against `tools/deps/prisma-engines.json` in its **build** stage (`deps:rebuild`), copies the verified file into the runtime stage, sets `ENV PRISMA_SCHEMA_ENGINE_BINARY=/app/node_modules/@prisma/engines/schema-engine-debian-openssl-3.0.x` and runs `tools/deps/prisma-cli.mjs --verify-only` in its entrypoint before `migrate deploy`/`migrate status`; the runtime stage has no egress to `binaries.prisma.sh`. `api`/`worker` contain no `node_modules/@prisma/engines` directory and no `schema-engine*` file (the Prisma 7 client is engine-free). Image tests: `docker run --network none <migrate> prisma --version` exits 0; the `api`/`worker` assertions above. (c) *Telemetry off (PR1-SEC-08):* every image sets `ENV CHECKPOINT_DISABLE=1 SCARF_ANALYTICS=false`. (d) *Static app builds (PR1-SEC-03 (d)):* the `web`/`admin` `build` stages run `npm run build -w apps/<app>` with `NPM_CONFIG_OFFLINE=true` and fail if the SHA-256 of `package.json` or `package-lock.json` differs before and after the build (the BuildKit counterpart of the lane A tree check, ADR-0023 am. I item 4). (e) *No rebuild fallback in images (PR1-SEC-09):* runtime stages carry no compiler toolchain; if the pinned `bcrypt` prebuild failed to load, `dist/preflight.js` fails the build — `npm rebuild bcrypt --ignore-scripts=false` is never run inside a Dockerfile, and `check-install-flags` rejects `npm rebuild` there. (f) *Studio prune caveat (PR1-SEC-04 (b)):* `prisma/build/cli.js` `require`s `@prisma/studio-core/data/*` at module level, so amendment 12's prune is expected to need its stub fallback (or the narrower prune of `elkjs` and `@visx/*` only); either way the image test must prove `prisma migrate deploy` and `migrate status`. The `elkjs` SPDX in amendment 11 is `EPL-2.0` (D-ARCH-003 rev 4).

## Amendment (2026-11-14, TASK-014 / PR #39 rulings): one tooling image for the bootstrap, migrate and seed one-shots; closure invariant; probe paths (`rulings/wave-0-task-014-rulings.md`; D-ARCH-116, D-ARCH-117, D-ARCH-118; amends amendments 6, 12, 13 and 14 (b); platform.md PD-07, §2.2, §2.4, §3.1, §3.2, §3.4, §5.2, §7.4)

15. **Tooling image.** (a) *One image, three one-shots (amends 6 and 12).* The "separate `shipcube-migrate` image" is **`shipcube-tooling`**, built from **`prisma/Dockerfile`** (final stage `tooling`), not from a `migrate` target of `apps/api/Dockerfile`: the DDL tooling shares no build graph with the api image, and one image is one digest to scan, SBOM and promote. It runs `tools/docker/tooling-entrypoint.sh bootstrap|migrate|seed|prisma-version`; Compose runs it as the services `bootstrap → migrate → seed` (`service_completed_successfully` chain) and ECS as three task definitions with `containerOverrides.command` (`bootstrap` reads `db/bootstrap`, once per environment, from `cd.yml`; `migrate` and `seed` read `db/migrator`). Least privilege is carried by the credential each one-shot receives (per-service env files, PR13-SEC-08), not by image identity. The seed runs from TypeScript sources through `tsx` with the `@platform/source` condition, exactly as `npm run db:seed` (sheet line 533 allowed tsx + sources or a built dist); amendment 12's "`ENTRYPOINT ["node","dist/migrate-and-seed.js"]`" wording is superseded. Amendment 14 (b) stays as written with "`migrate` image" read as "tooling image". (b) *Closure invariant (amends 12's invariant list).* The tooling image holds only the closure of the `prisma` workspace (dependencies and devDependencies: Prisma CLI with the verified schema engine, client, adapter, `pg`), `tsx` (+ `esbuild`) and the seed's `@platform/source` packages (`packages/{shared,authz,config}` `package.json` + `src/` and their dependencies). **`typescript` is absent from every image, the tooling image included**, as are `eslint*`, `prettier`, `@redocly/*`, `react*`, `@swc/core`, `@babel/*`, test frameworks and any other root devDependency outside that closure; the stack find check asserts `node_modules/typescript` for every image and the list above for `tooling`. The PR #39 head installed with `--include-workspace-root` and shipped the whole root devDependency closure (588.8 MiB, `typescript` 20 MiB): binding review requirement R1 of the ruling. The "no `src/*.ts` of workspace packages" clause of amendment 12 now applies to the **service** images only (api, worker, web, admin). (c) *Runtime base of the service images (D-ARCH-116, ADR-0001 amendment 2026-11-14).* `api`/`worker` `runtime` = `debian:trixie-slim` by digest + `/usr/local/bin/node` from the pinned node image; the tooling image may use the full node base (no size budget applies) or the same pattern (recommended: it removes the V8-header secret-scan allow-list D-TASK014-13). (d) *Probe paths (amends 13).* The preflight and the health probe are `tools/docker/preflight.mjs` and `tools/docker/healthcheck.mjs`, copied root-owned to `/app/` (`RUN node /app/preflight.mjs /app/apps/<app>/dist`; `HEALTHCHECK … node /app/healthcheck.mjs <app>`), not `dist/preflight.js` / `dist/healthcheck.js`: they are build and health tools outside the app's source and lint scopes (D-TASK014-14). (e) *Size (D-ARCH-118).* The api/worker budget is 300 MiB as the sum of uncompressed layer sizes (platform.md §3.4); the tooling image is reported, not gated.

## Reversibility

Medium (task definitions and CodeDeploy wiring are AWS-specific; images and config are not).
