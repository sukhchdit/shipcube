# ADR-0016: API conventions — OpenAPI 3.1 contract-first, RFC 9457 errors, pagination, idempotency, ETags, rate limiting, SSE, SSRF-safe egress

- **Status:** Accepted
- **Date:** 2026-11-12
- **Deciders:** principal-architect, api-designer
- **Related:** brief §4.8, §4.11; REQ-API-001..020, REQ-PLAT-009..011, REQ-SEC-001..016, DR-A08, DR-A20..A22, DR-A26; NFR-SEC-005..010, NFR-MAINT-004, NFR-QUAL-004; `docs/03-architecture/api/README.md`

## Decision

1. **Contract-first.** `docs/03-architecture/api/openapi.yaml` (OpenAPI 3.1) is the source of truth, linted with `@redocly/cli` in CI; a drift test compares the route registry (ADR-0003) with the document (method/path sets, `x-permission`, `x-audit`, `x-idempotency`); every operation has request/response examples and `x-error-codes`; frontend types are generated with `openapi-typescript` into `packages/shared/src/api/types.gen.ts` and checked for staleness in CI (REQ-API-002/019). Swagger UI (`swagger-ui-dist`) at `/api/docs`, enabled by config (REQ-API-003). Breaking-change detection with `oasdiff` against the previous tag (NFR-MAINT-004).
2. **Paths.** `/api/v1` prefix (unknown version → 404 `NOT_FOUND`); kebab-case, plural nouns, actions as POST sub-resources; health outside the prefix.
3. **Errors.** One error handler → `application/problem+json` `{ type: "https://docs.<domain>/problems/<CODE>", title, status, detail, instance, code, correlation_id, errors?: [{ pointer, code, message }] }` (REQ-PLAT-009, REQ-API-005/006); the code catalogue (DR-A26 + Part B) lives in `packages/shared/errors` with HTTP status and a test that every thrown `AppError` has a catalogue entry; 5xx bodies carry a generic detail; framework failures map per REQ-PLAT-010 (404/405 + `Allow`/400/413/415/500).
4. **Validation.** Joi schemas from route metadata, `allowUnknown: false` everywhere (REQ-SEC-007), `abortEarly: false` (up to 50 errors), pointers `/body/...`, `/query/...`, `/params/...`; shared constants/regexes/enums in `packages/shared` and a Zod/Joi parity test for address, parcel, customs item (REQ-SEC-008, NFR-MAINT-003). Body limit 1 MB (route-configurable), content-type allow-list, 30 s request timeout except event streams (REQ-SEC-015).
5. **Pagination/filtering/sorting.** Opaque cursors = base64url(HMAC-signed `{ sortKey, id }`), `limit` default 25 / max 100 (audit 50/200), `next_cursor`, `has_more`, stable sort with id tie-breaker, tampered/expired cursor → 400 `INVALID_CURSOR`; `filter[field]=value` with per-route operator allow-list, `sort=field,-field` from indexed fields only (REQ-API-007/008, DR-A21). A contract test fails a list route without pagination parameters.
6. **Idempotency.** `Idempotency-Key` per ADR-0014 (DR-A20 semantics; header documented per operation via `x-idempotency`).
7. **Concurrency.** Strong `ETag: "<id>:<version>"` on single-resource GETs, `If-None-Match` → 304; `If-Match` required on PUT/PATCH/DELETE of versioned resources (428 `PRECONDITION_REQUIRED`, 412 `CONCURRENCY_CONFLICT` with current ETag) (REQ-API-012/013). *Amended 2026-11-20 (ADR-0014 amendment 7; D-ARCH-193): pipeline step 7b checks only that `If-Match` is present and well formed and never reads a row. The comparison with the row version is the conditional write of the handler transaction, after the idempotency claim, so a retry of a request that already committed gets its replay and not a 412.*
8. **Rate limiting.** *(Amended 2026-11-20 by amendment 12: the engine is the platform's own, step 0 is route-agnostic, and the outage and client-IP rules are restated there.)* `express-rate-limit` 8 + `rate-limit-redis` 6 (shared counters); classes declared in route metadata (values per DR-A22 and D-035): `auth` (10/min/IP + 5/min/account identifier), `public` (120/min/IP), `public-quote` (20/min and 100/h per IP), `public-tracking` (30/min and 300/h per IP, 10/min failed lookups), `authenticated` (600/min/user), `email-send` (3/h per account identifier + 10/h per IP), `csp-report` (20/min/IP), `webhook` (per source IP range). Headers `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` (the three separate headers REQ-API-014 requires = express-rate-limit `standardHeaders: 'draft-6'`; `'draft-7'` would emit one combined `RateLimit` header) + `Retry-After` on 429 `RATE_LIMITED`. Redis outage: auth routes fall back to in-memory per-instance counters + ERROR security event; others fail open (REQ-SEC-006, A-053). Client IP from the trusted proxy chain only (`trust proxy` set to the configured hop count; EC-A12).
9. **Representations.** ISO 8601 UTC `Z`; local dates `YYYY-MM-DD` + `time_zone`; UUID strings; `Money {amount:int, currency}`; decimals as strings; ISO 3166-1 alpha-2 (REQ-API-016). `ApiMode` `test|live` on the request context (`test` in all non-production environments) as the M3 key-prefix seam (REQ-API-020).
10. **SSE.** `text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`, increasing `id`, named events with JSON `data`, 15 s heartbeat comment, `complete`/`error` then close ≤ 1 s, 30 s cap, disconnect cancels upstream work (REQ-API-017/018). Guest auth via `X-Quote-Token`; authenticated via `Authorization` header using `fetch` streaming (no `EventSource`, which cannot set headers).
11. **Security headers and CORS.** Helmet 8: `X-Content-Type-Options`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`, `COOP: same-origin`, `X-Frame-Options: DENY`, no `X-Powered-By`; HSTS ≥ 1 y incl. subdomains outside local; API CSP `default-src 'none'; frame-ancestors 'none'`. Frontends: CSP with hash-based `script-src` for pre-rendered HTML (no inline scripts except hashed loader), `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`, `connect-src` API + Stripe hosts, `frame-src` Stripe; CSP reports to `POST /security/csp-report` (REQ-SEC-001..003). CORS exact-origin allow-list with credentials, preflight max-age 600 s (REQ-SEC-014).
12. **CSRF.** Per ADR-0006 (cookie routes only).
13. **Outbound HTTP.** One `OutboundHttpClient` (undici-based, Node 24 global `fetch` with a custom dispatcher): https only, host allow-list per environment (carriers, Stripe), DNS resolution checked against private/loopback/link-local/ULA/metadata ranges **after** resolution with pinning, redirects re-validated against the allow-list, per-request timeout and response-size cap, `SSRF_BLOCKED` error + security event (REQ-SEC-010). Internal services (mail catcher, object storage, Redis) use dedicated clients with their own configured hosts. Lint forbids `fetch`/`axios`/`http` elsewhere.
14. **Deprecation.** `Deprecation`, `Sunset`, `Link rel="deprecation"` headers for operations marked `deprecated: true` with `x-sunset`; contract test requires a sunset date (REQ-API-015; mechanism only this run).
15. **Correlation.** `X-Correlation-Id` accepted if `^[A-Za-z0-9-]{8,64}$`, else generated UUID; echoed; propagated to logs, audit, outbox, jobs and outbound calls (REQ-PLAT-011).

## Alternatives considered

- **Generating OpenAPI from Joi schemas.** Convenient but inverts contract-first and loses examples/extensions; the drift test reconciles both directions instead.
- **Offset pagination.** Rejected (brief: cursor pagination; unstable under inserts).
- **GraphQL.** Not in the fixed stack; REST + OpenAPI serves frontends and the M3 public API.
- **`EventSource` for SSE.** Cannot send `Authorization`; `fetch` streaming works in all supported browsers.

## Consequences

- Positive: one contract for frontends, tests and the future developer portal; errors are stable and machine-readable; abuse controls are declarative per route.
- Negative: the drift test adds friction when adding routes (intended); HMAC cursors need a key in config.
- Verification: Redocly lint, drift test, API test classes per route (NFR-QUAL-004), rate-limit tests on 2 replicas (NFR-SEC-005), SSRF tests (NFR-SEC-010), header tests (NFR-SEC-006).

## Amendments after the threat model and platform review (2026-11-12, threat-model.md R-13, R-14; platform.md OI-14..OI-16)

1. **Two-stage rate limiting (R-13).** *(Amended 2026-11-20 by amendment 12 items 2 to 5 and 9: the clause "class `public`/`auth` as declared per route" is withdrawn, and "explicit CIDRs/hop count" is narrowed to a hop count.)* A coarse **per-IP pre-authentication limiter** (class `public`/`auth` as declared per route) runs before authentication so unauthenticated floods never reach bcrypt/JWT verification; the per-user limiter keeps its DR-A08 position after authorisation. IPv6 keys use the /64 prefix; `trust proxy` is configured as explicit CIDRs/hop count of the edge (CloudFront/ALB or the local `edge` proxy, EC-A12); the query-string parser is hardened (`qs` depth/array limits); default `Cache-Control: no-store` on authenticated responses. D-ARCH-006 asks product-manager to reflect the pre-auth limiter in DR-A08.
2. **Secrets out of URLs (R-14).** One-time tokens never appear in request paths or query strings: e-mail links point at frontend routes with the token in the **URL fragment** (`/{lang}/auth/verify#t=…`), the SPA posts it in a body (`POST /auth/verify-email`, `POST /auth/password/reset`, `POST /invitations/accept {token}` replaces `POST /invitations/{token}/accept`); shared quotes resolve via `POST /public/shared-quotes/resolve {token}` from a fragment-carrying link; the public tracking variant that needs a postcode uses `POST /public/tracking/lookup` (tracking-number / order-number lookups stay `GET`, they carry no personal data). Correspondingly the access log never records fragments and `Referrer-Policy` is `strict-origin-when-cross-origin`.
3. **SSE resume across replicas (OI-14).** Results are persisted to `quote_options` as they arrive, so a client reconnecting with `Last-Event-ID` to any replica receives the missing `carrier_result` events replayed from the database before live events; the stream `id` is the option sequence number.
4. **Redis policy (OI-15).** BullMQ requires `maxmemory-policy noeviction`; application caches set explicit TTLs and use a separate logical database/prefix so eviction pressure never affects queues; documented in platform.md and asserted by a start-up check (`CONFIG GET maxmemory-policy`, warning in local, failure in staging/production).
5. **Contract decisions accepted from api-designer (2026-11-12; `api/README.md`).** (a) `webhook` rate-limit class = 600/min per source IP; `POST /auth/refresh`, `/auth/logout` and `GET /auth/csrf` use the `public` class (DR-A22 does not list them as auth routes; 10/min/IP would block shared-NAT users — product-manager informed). (b) New error code `WEBHOOK_SIGNATURE_INVALID` (400) for gateway signature/timestamp failures (REQ-PAY-011 names the status only); carrier push signature failures stay 401 `AUTH_REQUIRED` (REQ-TRACK-006). (c) Audit descriptor `NONE` is additionally justified for `GET /auth/csrf`, `POST /security/csp-report` and the pure calculators (`GET /reference/volumetric`, `GET /reference/fx-rates/convert`) — REQ-AUDIT-006 list extension for product-manager. (d) Bounded reference lists (countries, subdivisions, currencies, Incoterms, export reasons, holidays) may declare a route-specific `x-max-limit` (≤ 300) so a full set fits one page; REQ-API-007's 100 cap stays the default for business lists. (e) Order status enum: `OPEN | PENDING_PAYMENT | PAID | BOOKING | BOOKED | PARTIALLY_BOOKED | FAILED | CANCELLED` (requirements define none; data-model.md aligns). (f) Status conflicts resolved toward DR-A26: `LAST_OWNER` 422, `LIMIT_EXCEEDED` 422, `REAUTH_REQUIRED` 401; `ACCOUNT_HAS_ACTIVE_SHIPMENTS` 409 (product-manager to confirm). (g) Path parameters use descriptive names (`{shipmentId}`); the drift test normalises parameter names. (h) `Last-Event-ID` resume on the quote stream exceeds REQ-CARR-009 deliberately (multi-replica correctness, amendment 3).

6. **UX reconciliation (2026-11-12, `docs/02-ux/README.md` §5 items 1, 2, 6).** (a) The fragment parameter in e-mail and share links is **`#token=`** (`/verify-email#token=…`, `/reset-password#token=…`, `/invitations/accept#token=…`, `/q#token=…`), fixed in ADR-0006 amendment 8; the `/{lang}/auth/verify#t=…` example in amendment 2 is superseded (app routes are unprefixed, D-UX-005). (b) **`X-Robots-Tag: noindex`** is sent on every API response (Helmet custom header), on every admin-app response and on the public tracking shell when a `number` query parameter is present (ADR-0026 amendments 4–5); the header test suite asserts all three. (c) The guest `X-Quote-Token` stays a header; its browser-side persistence is a `localStorage` map with TTL (ADR-0026 amendment 1) — no contract change, no cookie, no URL.

## Amendments after the P3 security review (2026-11-12, `docs/05-quality/security/P3-architecture-security-review.md` SEC-P3-01, SEC-P3-02, SEC-P3-21, SEC-P3-25; D-ARCH-017, D-ARCH-018)

7. **RateLimit headers are `draft-6` (SEC-P3-25; amends §8).** *(Amended 2026-11-20 by amendment 12 item 1: the platform's own engine sets the same three headers.)* express-rate-limit 8 runs with `standardHeaders: 'draft-6'`, which emits the three separate headers `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` that REQ-API-014 names (D-052 g); `draft-7` (single combined `RateLimit` header) is not used. `api/README.md` §7 is the authoritative description.
8. **Step-up metadata (SEC-P3-01).** Route metadata gains `reauth: { scope, maxAge? }` mirrored by the contract extensions `x-reauth-scope` and `x-reauth-max-age` (ADR-0006 amendment 12); the drift test compares both. Semantics: without `maxAge` a proof is always required (header parameter `ReauthProof`, `required: true`); with `maxAge` a token whose `now − auth_time ≤ maxAge` suffices and the header is optional (parameter `ReauthProofConditional`, `required: false`), so Joi parity and the response validator do not demand it. `ReauthRequest.action_scope` accepts every scope in the ADR-0006 amendment 12 list.
9. **SSE caps and subscribe-only streams (SEC-P3-02 item 5; amends §10).** Concurrent event streams are capped at `SSE_MAX_STREAMS_PER_IP=2` and `SSE_MAX_STREAMS_PER_USER=5` (429 `RATE_LIMITED`, declared in `x-rate-limit-route`); a stream never triggers upstream work (fan-out happens once in the creating POST; amendment 3's replay covers reconnects).
10. **SDK egress exception register (SEC-P3-21 item 3; amends §13).** Every outbound call goes through `OutboundHttpClient`; SDKs that cannot be bound to it are listed here with their configured hosts and are the only exceptions the lint rule allows: `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner` (`STORAGE_ENDPOINT` locally; the regional S3 endpoint in AWS), `@aws-sdk/client-ses` (regional SES endpoint, M5), `nodemailer` (`MAIL_HOST`, Mailpit locally). The Stripe SDK is **not** an exception (`createFetchHttpClient` on the dispatcher, ADR-0012 amendment 3). Each exception's host list is asserted by a config test and the `SSRF_BLOCKED` rule does not apply to them because the hosts are fixed by configuration, never by request data.
11. **`quote-create` rate class and the share mint cap (SEC-P3-29, SEC-P3-32; amends §8 and amendment 9; D-ARCH-031, D-ARCH-032).** (a) New class **`quote-create`**, keyed by user **and** organisation: `RATE_QUOTE_CREATE_PER_USER_PER_MIN=30`, `RATE_QUOTE_CREATE_PER_USER_PER_HOUR=300`, `RATE_QUOTE_CREATE_PER_ORG_PER_HOUR=1000` (429 `RATE_LIMITED`, `draft-6` headers). It applies to `createQuote` for authenticated callers whose e-mail is verified; `createQuote` keeps `x-rate-limit-class: public-quote` for the anonymous path and declares the authenticated class in `x-rate-limit-route` as api/README.md §7 documents, and the route-metadata drift test compares both. Users in `PENDING_VERIFICATION` are treated as anonymous (per-IP `public-quote` limits and the anonymous carrier budget, ADR-0010 amendment 10), so `createQuote` on a bearer route no longer counts in the 600/min `authenticated` class. (b) `createQuoteShare` gains a route-specific cap of **10 mints per quote per rolling hour** (`QUOTE_SHARE_MINTS_PER_HOUR=10`, the REQ-QUOTE-015 / D-055 key; `x-rate-limit-route`, 429 `RATE_LIMITED`; a refused mint revokes nothing; counted in PostgreSQL inside the minting transaction over `ix_quote_shares__quote_created`, serialised by `ux_quote_shares__quote_active`, data-model §3.10), because mint-and-revoke (ADR-0014 amendment 4) would otherwise let the 600/min class write tens of thousands of revoked rows an hour; the implicit revocation is audited as `UPDATE quote_share` (reason `SUPERSEDED`) in the same transaction. To let the audit test generator assert a second entry on one operation, the contract gains the vendor-extension member **`x-audit.additional[]`** (`{action, entity, sensitivity, when}`), documented in api/README.md §10 and deep-compared by the §15 drift test; `checkoutOrder` uses it for the `UPDATE payment` of a failed CVC check (ADR-0012 amendment 4). (c) `resolveSharedQuote` returns **one byte-identical 404 `NOT_FOUND`** for unknown, revoked, superseded and expired tokens (D-055; REQUIREMENTS.md v1.4 EC-B29/EC-B53): `quote_share_resolve` adds `AND expires_at > now()`, and the former "expired quote with inputs prefilled" shared view is dropped in favour of a generic "this shared quote is no longer available" page with a link to a new quote (D-UX-034). An earlier draft of this amendment kept the v1.3 EC-B29 expired view as a reconciliation with SEC-TC-53; it was withdrawn the same day when product-manager's D-055 aligned the requirement with the review's condition. Verification: SEC-TC-62, SEC-TC-53 (as amended in review §14.5).

## Amendment (2026-11-20, TASK-041 code review round 1, merge condition C1, and security review D-SECPR041-01: developer decisions D-TASK041-01, -03 and -05; R1-m1, R1-m2, R1-m4, R1-m8; PR041-SEC-02, -03, -05; D-ARCH-173..179)

12. **The rate limiter as TASK-041 built it, and what changes (amends §8, amendment 1 and amendment 7).** Exact change lists, the api/README §7 text and the card lines are in `rulings/wave-1-task-041-rulings.md`.
    1. **Engine (D-TASK041-01, accepted; D-ARCH-173).** The limiter is the platform's own engine in `apps/api/src/platform/rate-limit`, not `express-rate-limit` + `rate-limit-redis`.
       - It counts in fixed windows. One atomic Lua script per rule does `INCR`, sets the TTL on the first hit and returns the count and the remaining TTL. The window is anchored by the key's own TTL in Valkey, so replicas never split a window.
       - A request may consume several rules (a class with a minute and an hour window). Every store call is bounded by 250 ms.
       - The engine sets the three draft-06 headers and `Retry-After` itself. `standardHeaders: 'draft-6'` in §8 and amendment 7 is history; the header names are unchanged.
       - Why not the two libraries: they cover one rule per middleware instance. They do not give the headers of the window closest to exhaustion across two rules, a per-class choice between a per-instance fallback and failing open, the TTL-anchored atomic script D-SECT39-01 item 3 requires for the denial budget, or the stream slots. The engine would have been split between a library and scripts of our own.
       - Accepted cost: a fixed window lets a client send up to twice the limit across a window boundary. A sliding window is not needed for these limits.
       - **Against the brief and the fixed-stack rule (QG-041-C3 (a); D-ARCH-181).** Brief §3.2 lists "`express-rate-limit` with a Redis store" among the sanctioned additions. Those are SHOULD items, which the brief defines as "a strong default that needs an ADR to change"; this amendment and the ADR-0025 entry are that record. CLAUDE.md §2 calls the stack of brief §3 fixed and says the architect does not re-select it. Nothing of §3.1 changes: the limiter runs in the Express API on the Redis-compatible store, and `express-rate-limit` remains a dependency. What is not used is its middleware and a Redis store adapter for it. The rule is the user's, so the deviation was put to the user; the orchestrator reports the user's acceptance on 2026-11-20.
       - `rate-limit-redis` is removed from `apps/api/package.json` and the lockfile in the TASK-041 pull request. `express-rate-limit` stays for one function, `ipKeyGenerator` (the IPv6 /64 key and the unmapping of IPv4-mapped addresses); no middleware of it is created and nothing else is imported from it.
    2. **Step 0 does not know the route (D-TASK041-03, accepted; D-ARCH-174).** The limiter that runs before authentication is mounted path-less before routing (D-ARCH-084, D-ORCH-024 (5)), so it cannot apply "class `public`/`auth` as declared per route". That clause of amendment 1 is withdrawn. Step 0 counts every request except `/health/live` and `/health/ready`, against one of two per-IP rules:
       - the **unauthenticated budget**, `RATE_LIMIT_PUBLIC_PER_MIN` (120/min);
       - the **credentialed ceiling**, ten times `RATE_LIMIT_AUTHENTICATED_PER_MIN` (6,000/min), so that users behind one NAT keep their per-user budgets (AT-US-040-11). The factor is a named constant, not configuration. The counter label `step0-credentialed` shows when a deployment needs to tune it.
    3. **Which rule a request takes (R1-m1 option (a), PR041-SEC-02 (a); D-ARCH-174).** The ceiling is chosen by the presence of a credential header, not by its validity, so it must not apply where no credential can matter. A request takes the credentialed rule only when it is under `/api/v1`, is not `OPTIONS` and presents a credential: an `Authorization` header, a refresh cookie *(from part 041-B only on the three routes that read it: amendment 13 item 1)*, an `X-Quote-Token` or, from part 041-B, a provider signature header (the `webhook` class allows 600/min per IP, above the unauthenticated budget). Every other request takes the unauthenticated budget: the API docs, `OPTIONS`, and any path outside `/api/v1`, whatever headers it carries. A path under `/api/v1` that no route serves still takes the credentialed rule when it carries a credential header, because step 0 runs before routing; its answer costs no more than a 429.
    4. **Failed-authentication budget (R1-m1 option (b), PR041-SEC-02 (b); D-ARCH-175).** Presence still lets a forged credential reach verification at the ceiling rate. So a credential that fails is charged as what it is, an unauthenticated request.
       - Key `rl:step0:authn-failed:<ip key>`, a fixed 60 s window, limit `RATE_LIMIT_PUBLIC_PER_MIN`.
       - One unit is spent when the authentication slot refuses a request that presents a credential of a kind the route declares. 401 `ACCESS_TOKEN_EXPIRED` spends nothing: the session authenticator answers it from the `exp` claim before it verifies the signature, so it costs no verification, and normal token expiry behind a large NAT must not spend the budget. *(Conditions E1 to E5: amendment 13 item 3.)*
       - A wrapper around the authentication slot records the spend. No authenticator calls the limiter, so none can forget.
       - Step 0 reads the budget in the same script call that counts the credentialed hit. While the budget is spent, every request from that IP that takes the credentialed rule is answered 429 `RATE_LIMITED` with `Retry-After`, before routing and authentication. Requests under the unauthenticated budget are not affected.
       - A separate key, not the unauthenticated key itself: otherwise the anonymous visitors of a NAT would lock out its signed-in users.
       - Rules for the authenticators, so that a forged credential costs one bounded verification: no Valkey or database call before the signature of a bearer or a webhook has verified; a refused refresh cookie is a 401 from the authentication slot; the guest authenticator does no I/O and leaves the row match to the handler, behind the class limit.
       - Accepted property: one client that sends 120 bad credentials a minute stops every credentialed request from its IP for the rest of the window. This is wider than the `auth` class, which at 10 a minute stops only the authentication routes of an IP. What bounds it: the stop lasts 60 s at most, the answer is 429 with `Retry-After`, and requests without a credential header still pass. security-analyst rates it in the 041-B round (QG-041-C4). *(Restated 2026-11-20 by amendment 13 items 1 and 2, PR041-SEC-09: a returning browser sends its refresh cookie on every request, so "without a credential header" did not cover its sign-in; the cookie now selects the lock only on its own routes, and the scope of the lock is stated there.)*
    5. **Class rules run at pipeline step 5, for every class (D-TASK041-05, accepted; D-ARCH-176).** After authorisation and before validation and the handler: the per-IP rules of `auth`, `email-send`, `public`, `public-quote`, `public-tracking`, `csp-report` and `webhook`, and the per-user rule of `authenticated`. The per-account, per-address and `quote-create` rules are consumed by the owning service through the same engine. So the limiter has two stages, as amendment 1 says: step 0 protects authentication work, step 5 protects the handler (AT-US-040-06: the 11th login is refused before any password hash comparison). DR-A08, DR-A22, REQ-SEC-005 and NFR-SEC-005 still say "the per-IP limit of the route's class is applied before authentication"; the wording is routed to product-manager.
    6. **Security event (R1-m2).** `rate_limit_auth` is logged once per key and window, by the first refusal, for the `auth` and `email-send` classes and for the failed-authentication budget (class `authn-failed`). A counter counts every refusal. A flood therefore costs one line per IP, class and minute, whatever its rate.
    7. **Store calls and breaker (R1-m4, S4; D-ARCH-177).** One breaker per process covers the rate-limit store and is shared by the limiter and the denial budget. A failed or timed-out call opens it for 5 s; while it is open no call waits, each takes its fallback or fail-open path at once; then one probe call decides. A brownout therefore costs one 250 ms wait per instance and cool-down, not two or three per request. Required; delivered in part 041-B.
    8. **Store outage (amends "Redis outage" in §8; PR041-SEC-03; D-ARCH-178).** Per-instance in-memory counters with the same limits serve `auth`, `email-send` and the failed-authentication budget, and from part 041-B also `public-quote`, `public-tracking` and `quote-create`, because those drive carrier calls and unauthenticated writes. `public`, `authenticated`, `webhook`, `csp-report`, the step-0 hits and the stream slots fail open (REQ-SEC-006). The fallback store is bounded, with O(1) eviction (PR041-SEC-01). The event is `rate_limit_store_unavailable`, at most once a minute per scope. The carrier admission controls refuse instead of failing open (ADR-0010 amendment 13).
    9. **Client IP (S2, PR041-SEC-05; D-ARCH-179).** `trust proxy` is the hop count `TRUST_PROXY_HOPS`. Too many hops let the client choose `req.ip` silently; too few put every client in one bucket, which is loud. So the default is 0 (trust nothing), and in staging and production the API refuses to start unless the value is set and at least 1. Compose sets 1 for the `edge` proxy; the task definition sets 2 for CloudFront + ALB, pinned by a Terraform test together with the `sg-alb` prefix list and the `X-Origin-Verify` rule (TASK-215). `CloudFront-Viewer-Address` is not read: one mechanism decides the client IP.

## Amendment (2026-11-20, TASK-041 security round 2, D-SECPR041-02: PR041-SEC-09 and conditions E1 to E5; product position D-PM-073; D-ARCH-182)

13. **The scope of the failed-authentication lock (amends amendment 12 items 3 and 4).** Amendment 12 item 4 said that requests without a credential header still pass while an IP's budget is spent. That is wrong for a returning browser: `__Host-rt_web` has `Path=/` and the API shares the app's host, so a browser that has signed in once sends the cookie on every `/api/v1` request, sign-in included.
    1. **The refresh cookie selects the credentialed rule only on the routes that read it (R1).** At step 0 a refresh cookie counts as a presented credential only when the request path is exactly the path of a route that declares `refresh-cookie` (`getCsrfToken`, `refreshSession`, `logoutSession`). `createApp` derives that set from the route metadata and passes it to the limiter with the prefix; a `refresh-cookie` route with a path parameter is refused at boot. Everywhere else a request that carries only the cookie takes the unauthenticated budget and is never locked: sign-in, registration, password reset and public reads of a returning browser keep working. Another spelling of a cookie-route path takes the unauthenticated budget too, so a cookie that reaches the authenticator is always under one of the two bounds. `Authorization`, `X-Quote-Token` and the provider signature headers select the credentialed rule as before; they are sent on purpose, not by the browser on its own.
    2. **The lock stays for every credentialed request, and this is its scope (R2 (i)).** While an IP's budget is spent, step 0 answers 429 with `Retry-After` to every request from that IP that takes the credentialed rule: a bearer, a quote token, a provider signature, and the refresh cookie on its three routes. That includes the valid credentials of every signed-in user and every guest behind that address (an office NAT, a carrier-grade NAT, a VPN exit, an IPv6 /64), and it includes their token refresh. One client on the address keeps the lock with two refused credentials a second. The earlier comparison with the `auth` class is withdrawn. Accepted, because a forged credential must not reach verification at the ceiling rate, by security-analyst (LOW, their preference) and by product-manager (D-PM-073, PRD §9 R-16: likelihood low, impact medium, no data or money at risk). The window is 60 s and nothing is exposed before a production release.
    3. **Conditions on the `exp` pre-check (E1 to E5).** The session authenticator may refuse an expired token before it verifies the signature only under these rules. (E1) The unverified `exp` is used for that one refusal; every token that passes is verified in full with `algorithms: ['ES256']`, issuer, audience and the same clock tolerance, and nothing else of the unverified payload is read or logged. (E2) Only a well-formed token whose `exp` is a finite number in the past is expired; a missing, non-numeric, non-finite or out-of-range `exp`, or a malformed structure, is a refused credential and spends. (E3) The pre-check is bounded: a length cap, three base64url segments, and the header's `alg` equal to `ES256` before the payload is decoded. (E4) `ACCESS_TOKEN_EXPIRED` comes only from that pre-check or from the library's own expiry check inside the tolerance; it emits no security event; the wrapper's exemption keys on that code alone. (E5) The tests of TASK-052 pin it: 200 forged tokens with a past `exp` give 200 answers 401 `ACCESS_TOKEN_EXPIRED`, no signature verification, no store or database call, no security event and no 429; a forged token with a future `exp` costs one verification and spends one unit.
    4. **Signal and reopening.** `rate_limit_auth` with class `authn-failed` and the counter `step0-authn-failed` are exported and alerted on (TASK-214). After launch, an event that affected more than one user of an address reopens the lock (product-manager's trigger, A-112). The two narrower designs are ready: lock only the refresh cookie, whose refusal costs a lookup, and let bearers, quote tokens and signatures run under the ceiling (the security record's R2 (ii); the cost is one ES256 verification per forged bearer, measured at about 400 µs, at most about 4 % of a core per attacking address); or give the three cookie routes their own per-IP rule at step 0, which also bounds the lookups of a valid cookie (R-ARCH-36 (a)).
    5. **Clients.** A 429 is not an authentication failure. The web and admin clients wait for `Retry-After` and retry, also on `refreshSession`, and never sign the user out because of it.
