# ADR-0012: Payments gateway abstraction — Stripe test mode, Payment Element, manual capture, webhooks, Mock gateway

- **Status:** Accepted
- **Date:** 2026-11-12
- **Deciders:** principal-architect
- **Related:** brief §4.7, §4.11 (PCI SAQ A); REQ-PAY-001..019, DR-B27, DR-B03, DR-B04; D-011, D-017, D-030; NFR-SEC-013; ADR-0014 (saga)

## Context

Card data must never touch Platform servers (hosted fields; SAQ A). Stripe first (test mode only in this run; a live key refuses to start), PayPal and other gateways later via the same abstraction. The saga needs authorise → carrier booking → capture. Webhooks must be verified, idempotent and replayable. A deterministic Mock gateway drives M0 and failure paths. Verified today (docs.stripe.com, 2026-11-12): PaymentIntents with `capture_method=manual` authorise now and capture later (`POST /v1/payment_intents/{id}/capture`, optional `amount_to_capture` for partial capture; `POST …/cancel` releases); online card authorisations are valid **7 days** (Visa MIT 5 days); webhooks are signed in `Stripe-Signature` (`t=` timestamp, `v1=` HMAC-SHA256 over `t.rawBody`), the SDK's default tolerance is **300 s**, the raw body is required, duplicates must be de-duplicated by event ID, and ordering is not guaranteed.

## Decision

1. **Interface** `PaymentGateway` (REQ-PAY-001): `authorise({ orderId, amount: Money, customerRef?, paymentMethodToken?, idempotencyKey, returnUrl }) → { gatewayRef, status: AUTHORISED | REQUIRES_ACTION | FAILED, clientSecret?, declineCode? }`, `capture({ gatewayRef, amount?, idempotencyKey })`, `voidAuthorisation({ gatewayRef, idempotencyKey })`, `refund({ gatewayRef, amount, idempotencyKey, reason })`, `retrieve(gatewayRef)`, `verifyWebhook(rawBody, headers) → GatewayEvent`, optional `attachPaymentMethod`, `listPaymentMethods`, `detachPaymentMethod`, `createSetupSession`. Every state-changing call carries an idempotency key (Stripe `Idempotency-Key` header). Amounts are `Money` (minor units) computed **server-side** from stored price snapshots (REQ-PAY-006).
2. **Stripe adapter** (`stripe` 23, API version pinned by the SDK): PaymentIntent with `capture_method: 'manual'`, `automatic_payment_methods` restricted to card (REQ-PAY-019), `metadata { order_id, org_id }`; **Payment Element** in the web app (hosted iframe fields; `connect-src`/`frame-src` allow `js.stripe.com`, `api.stripe.com`, `hooks.stripe.com` exact hosts, REQ-SEC-002). 3-D Secure → `REQUIRES_ACTION` with `client_secret` → client `confirmPayment` → outcome via webhook and `POST /payments/{id}/confirm` reconciliation (REQ-PAY-009). Capture after carrier confirmation for the booked shipments' amount (partial capture releases the rest, DR-B33). Refund = full captured amount of the cancelled shipment after `VOIDED` (DR-B21). Start-up guard: key prefix must be `sk_test_`/`rk_test_` else `PAYMENT_LIVE_KEY_FORBIDDEN` (REQ-PAY-004) — *amended 2026-11-12 (amendment 2): `rk_test_` restricted key by default; `sk_test_` only with `PAYMENT_ALLOW_FULL_TEST_KEY=true`*. Without a key the adapter runs **fixture-backed** (recorded Stripe responses incl. 3DS test cards) and `STRIPE_TEST_LIVE=1` enables real test-mode calls (REQ-PAY-017, D-003).
3. **Webhooks** `POST /api/v1/webhooks/stripe`: raw body parser on this route only, `stripe.webhooks.constructEvent(raw, sig, secret, 300)`; invalid → 400 + audit `DENIED` + security event `webhook_signature_invalid`; valid → insert `gateway_webhook_events(gateway, event_id UNIQUE, type, received_at, payload_ref, processed_at)` **before** processing (duplicate → 200 immediately), enqueue to `payments` queue, respond 200 fast. The processor **retrieves the current PaymentIntent** and derives state (never from event order), applies DR-B27 transitions, and is replayable by event ID (worker command). Unknown event types stored + acknowledged (REQ-PAY-012). Local dev: Stripe CLI `stripe listen --forward-to` is documented; fixtures sign payloads with a test secret.
4. **Mock gateway** (REQ-PAY-002): outcome by reserved tokens `mock_ok | mock_decline | mock_3ds | mock_3ds_fail | mock_capture_fail | mock_refund_fail`; emits synthetic webhooks to `POST /webhooks/mock-gateway` (non-production only) so the same async path is exercised; rejected in production.
5. **Payment records** (REQ-PAY-003): `payments(order_id, gateway, gateway_ref, amount, currency, status, livemode=false, …)` + `payment_status_history` (append-only), `payment_attempts` (≤ 5/hour/order → 429 `PAYMENT_ATTEMPTS_EXCEEDED`), `refunds`, `saved_payment_methods` (token, brand, last4, exp month/year only; ≤ 10/user), redacted raw payloads in object storage (ADR-0021). Status machine DR-B27 enforced in the service. Decline mapping → `CARD_DECLINED | INSUFFICIENT_FUNDS | AUTHENTICATION_FAILED | EXPIRED_CARD | GATEWAY_UNAVAILABLE` (REQ-PAY-010).
6. **Authorisation lifecycle guards**: saga releases on abort or at its 30-min deadline; sweeper every 5 min cancels authorisations > 30 min without a booked shipment and repairs CAPTURED-without-BOOKED after 10 min (REQ-PAY-008/018). The 7-day Stripe validity is far above these windows; it is still asserted in config (`PAYMENT_AUTH_MAX_AGE_MINUTES ≤ 7 d`).
7. **Test-mode indicator**: `livemode: false` on payment responses and a visible, non-colour-only indicator in checkout/confirmation (REQ-PAY-016).
8. **Seams**: `payment_methods.type` enum includes `CARD | PAYPAL | WALLET | CREDIT_ACCOUNT | PAYMENT_LINK | OFFLINE | COD` (only `CARD` accepted now → 400 `PAYMENT_METHOD_NOT_AVAILABLE`); `ledger` is M4 (payments carry `ledger_posting_ref NULL`).

## Alternatives considered

- **Stripe Checkout (hosted page).** Also SAQ A, but a redirect breaks the "sticky price summary, one step per screen" wizard; Payment Element keeps the flow in-app with equal PCI scope.
- **Capture immediately.** Violates G1 (captured payment without shipment, DR-B04); manual capture is mandated by D-011/D-030.
- **Synchronous webhook processing.** Risk of timeouts and duplicate side effects; store-then-queue is Stripe's recommended pattern.
- **Processing from event payload instead of retrieving the object.** Out-of-order events would corrupt state; REQ-PAY-012 requires retrieval.

## Consequences

- Positive: SAQ A scope; saga guarantees implementable; gateway swap = new adapter + config; M0 runs without Stripe.
- Negative: webhooks need a public URL in staging (Stripe CLI locally); fixture realism until `STRIPE_TEST_LIVE=1` runs (COND-SANDBOX-DEMO).
- Verification: PAN scanner on bodies/logs, signature/tolerance/replay tests, saga fault matrix (NFR-SEC-013, NFR-RES-005).

## Amendment after the P3 security review (2026-11-12, `docs/05-quality/security/P3-architecture-security-review.md` SEC-P3-01 C2, SEC-P3-08 item 4; D-ARCH-017, D-ARCH-022)

1. **CVC recollection for saved cards (SEC-P3-01).** `PaymentGateway.authorise` gains `requireCvcRecollection?: boolean`; the Stripe adapter maps it to `payment_method_options.card.require_cvc_recollection = true`, the Mock gateway simulates it (token `mock_cvc_required` fails without the simulated CVC confirmation). `capabilities().cvcRecollection` must be `true` for any gateway that offers saved payment methods; config validation refuses `PAYMENT_SAVED_METHODS_ENABLED=true` for a gateway without it. The orders module sets the flag when `checkoutOrder` uses a saved payment method and the session's `auth_time` is older than 12 h (ADR-0006 amendment 12) and returns `cvc_recollection_required: true`. PCI scope is unchanged (the CVC is entered in the Stripe iframe).
2. **Restricted Stripe key (SEC-P3-08 item 4; amends §2 start-up guard).** The default `STRIPE_SECRET_KEY_REF` is a **restricted** `rk_test_` key with the minimum permissions: PaymentIntents, SetupIntents, PaymentMethods, Customers — write; Refunds — write; Events — read; nothing else. A full `sk_test_` key is accepted only with `PAYMENT_ALLOW_FULL_TEST_KEY=true` (start-up WARN); any live-mode prefix still fails with `PAYMENT_LIVE_KEY_FORBIDDEN`. **Each webhook endpoint has its own signing secret** (`STRIPE_WEBHOOK_SECRET_REF` per environment endpoint; never shared across environments). Both keys appear in the ADR-0018 key register.
3. **Webhook and SDK egress hygiene (SEC-P3-21 items 2–3, LOW; aligns with REQ-PAY-012 as reworded in D-052 e; amends §2–§3).** The Stripe webhook handler rejects any correctly signed event with `livemode: true` (400, audit `DENIED`, security event `webhook_livemode_rejected`) and processes only an **allow-listed set of event types** (`payment_intent.*`, `setup_intent.*`, `charge.refund*`, `payment_method.*`); unknown types are stored and acknowledged but never processed (REQ-PAY-012). The Stripe SDK is constructed with `Stripe.createFetchHttpClient()` bound to the `OutboundHttpClient` dispatcher (ADR-0016 §13), so gateway calls go through the SSRF-safe client with its host allow-list; the ADR-0016 SDK egress exception register lists every SDK that does not. Verification: SEC-TC-60.
4. **CVC recollection outcome is verified (SEC-P3-28, MEDIUM; condition of review ruling 1; completes amendment 1; D-ARCH-030).** Collecting the CVC is not enough: issuers may authorise despite a failed or unavailable CVC check, so the outcome is read and enforced.
   - **Rule.** When `requireCvcRecollection` was set on the PaymentIntent, one shared derivation function (`derivePaymentState`, used by `confirmPayment` and by the webhook processor alike, never duplicated) treats the authorisation as `AUTHORISED` only if the retrieved charge has `payment_method_details.card.checks.cvc_check = 'pass'`. Any other value (`fail`, `unavailable`, `unchecked`, absent) leads, in one transaction, to `voidAuthorisation` (manual capture, so no money moves), payment `FAILED` with the existing `failure_code = AUTHENTICATION_FAILED`, an audited `UPDATE payment`, the security event `cvc_recollection_failed` (api/README.md §13), the order's shipments back to `QUOTED`, and the attempt counted against the 5/hour cap (`PAYMENT_ATTEMPTS_EXCEEDED`). No saga starts.
   - **Recovery path.** The client offers "use another card" (hosted fields) or "confirm it's you" (`createReauthProof`, which advances `auth_time`, so the retried checkout needs no CVC). No new header or vendor extension: the single-mechanism decision of ADR-0006 amendment 12 stands.
   - **Mock gateway (amends §4 and amendment 1).** `CheckoutRequest.test_token` gains `mock_cvc_pass | mock_cvc_fail | mock_cvc_unavailable`, which set the simulated `cvc_check` when recollection was required and behave as `mock_ok` otherwise; the never-implemented `mock_cvc_required` token of amendment 1 is withdrawn. The Mock emits the same synthetic webhook, so the webhook derivation path is exercised in e2e.
   - **Defence in depth.** The Stripe **test** account has the Radar rule "Block if CVC verification fails" enabled (recorded here as configuration, not code). Radar ignores `unavailable`/`unchecked`, which is why the application rule above is the control and Radar only the backstop.
   - Verification: SEC-TC-37 (amended, review §14.5): `fail`/`unavailable` → `FAILED/AUTHENTICATION_FAILED`, authorisation voided, no saga, `cvc_recollection_failed`; `pass` → `AUTHORISED`; after `createReauthProof` the retry has `cvc_recollection_required=false`; same outcome on the webhook path. Requirement side: REQ-PAY-010 already lists `AUTHENTICATION_FAILED`; no new REQ.

## Amendment (2026-11-20, what the checkout does before its write, and the client secret in a stored response: QG-040-C2 of D-QG-003, D-PM-083, PR040-SEC-03 and PR040-SEC-08; ADR-0003 amendment of this date; ADR-0014 amendments 13 and 15; D-ARCH-202, D-ARCH-204)

5. **Gateway calls of an API request.**
   - **`checkoutOrder` creates the intent and does not confirm it.** Its `call` phase runs before the transaction that writes the payment row. If that transaction does not commit, no row names the intent, so the intent must bind nobody: no hold is placed there, with the Mock gateway as with Stripe (ADR-0003 rule (j)). §1 lets `authorise` return `AUTHORISED`; in this phase the intent is returned unconfirmed, with its client secret, and never as `AUTHORISED`. The hold comes with the confirmation, which acts on an intent that a committed payment row names: the browser's, with the client secret of the committed response, or a server-side one, in `confirmPayment` or in a worker step that follows `order.checkout_started`. ~~TASK-085 gives the interface and the Mock gateway the two steps; TASK-092 and TASK-170 use them.~~ *(Narrowed 2026-11-20 by amendment 6, QG-040-C7 of D-QG-004: this bullet binds a gateway that reaches a provider. The Mock gateway authorises inside the request, as the contract says, and the interface of §1 keeps its one `authorise`.)*
   - **The key of the checkout call is `auth:<order_id>:<order_version>:<attempt>`** (ADR-0003 rule (k)). Stripe compares the parameters of a repeated key with those of the first request and refuses the request when they differ. A key without the order version would therefore refuse the checkout of an order whose amount changed after an earlier call that never got its payment row.
   - **`confirmPayment`** retrieves the intent and voids the authorisation when amendment 4 requires it. Both act on an intent that a committed row names, and the state is derived from the gateway again by the next confirmation, webhook or sweep.
   - **Every state-changing call carries its key** (§1), in the API and in the worker. A 5xx of the API releases the request's idempotency key, so the same call can be made again; the key is what makes that one effect (PR040-SEC-08).
   - **Stored client secrets.** The responses of `checkoutOrder`, `confirmPayment` and `createPaymentMethodSetup` carry the client secret of the intent, and the idempotency store keeps them for a replay: encrypted, bound to the caller's scope, at most 25 h (ADR-0014 amendment 15; PR040-SEC-03 accepted). Nothing else stores or logs a client secret.

## Amendment (2026-11-20, condition QG-040-C7 of D-QG-004: the Mock gateway authorises in the request; who establishes an authorisation; the payment-method operations; D-ARCH-205, D-ARCH-206; narrows amendment 5)

6. **Amendment 5 binds a gateway that reaches a provider. The Mock gateway authorises inside the request, as the contract says.**
   - **What was wrong.** Amendment 5 said that `checkoutOrder` does not confirm an intent "with the Mock gateway as with Stripe" and never returns `AUTHORISED`. The contract says the opposite for the Mock in four places: the description of `checkoutOrder` ("On AUTHORISED the booking saga starts"; "Mock gateway, which authorises synchronously"), its 201 response ("AUTHORISED starts the saga"), its `x-audit.additional` entry for a voided synchronous Mock authorisation, and api/README §8. The contract decides (ADR-0016 §1), and it is right. None of the four places changes.
   - **Why the rule does not reach the Mock.** ADR-0003 rule (j) limits what a `call` may do outside the process, because nothing can undo it when the write that follows does not commit. The Mock gateway is inside the process. It calls nothing, holds no funds and no card, and is refused in production (REQ-PAY-002; ADR-0018 amendment 8). When the write after a Mock authorisation does not commit, nothing is left anywhere, and the same key gives the same Mock answer again (US-199).
   - **The rule, with its control.** An adapter declares `capabilities().simulated`. It is `true` for the Mock gateway and for nothing else. An adapter that is not simulated never returns `AUTHORISED` from `authorise` and creates its intent without confirming it. The gateway contract suite of US-199 asserts that for every adapter that is not simulated, the Stripe fixtures first (TASK-167).
   - **Who establishes an authorisation.**

     | Gateway and case | Where |
     |---|---|
     | Mock: `mock_ok`, `mock_decline`, `mock_cvc_pass`, `mock_cvc_fail`, `mock_cvc_unavailable`, `mock_capture_fail`, `mock_refund_fail` | In the `call` of `checkoutOrder`. The Mock answers `AUTHORISED` or `FAILED`. The handler writes the payment in that state in its one transaction and, on `AUTHORISED`, moves the shipments to `PAID` and publishes `payment.authorised`. No further step confirms anything. This is the M0 path of AT-US-202-01 |
     | Mock: `mock_3ds`, `mock_3ds_fail` | `REQUIRES_ACTION` with a client secret from the checkout. Then `confirmPayment`, which retrieves the Mock object and derives the state. From TASK-171 the Mock's synthetic webhook does the same, and whichever arrives first applies the outcome |
     | Stripe | The checkout creates the PaymentIntent unconfirmed. The browser confirms it with the client secret of the committed response (Payment Element, saved cards and CVC recollection included). The state comes from the webhook or from `confirmPayment`, both of which retrieve the intent |

   - **No server-side confirmation of a Stripe intent exists in this run.** If one is added, it is a worker step that follows `order.checkout_started`, never the `call` of the checkout. Amendment 5 named "`confirmPayment` or a worker step" as if both existed; `confirmPayment` retrieves and derives, it does not confirm.
   - **SEC-P3-28 and SEC-TC-37 run where they ran:** on the synchronous Mock path of `checkoutOrder`, with its `x-audit.additional` entry, on `confirmPayment`, and on the webhook path. The void of amendment 4 on the Mock path is a call of the simulator.
   - **The other parts of amendment 5 stand:** the key `auth:<order_id>:<order_version>:<attempt>`, `confirmPayment` as a `reachable` call, a key on every state-changing call, and the stored client secrets.
7. **Saved payment methods (ADR-0003 rule (j); observation of D-QG-004).**

   | Operation | `call` | Class |
   |---|---|---|
   | `createPaymentMethodSetup` | creates the setup session and returns its client secret | `inert`: nothing is attached before the browser completes the setup |
   | `createPaymentMethod` | retrieves the completed setup, and attaches the method where a gateway does not attach it on completion | `reachable`: the setup is named by the row that `createPaymentMethodSetup` committed, and a repeat finds the same method |
   | `updatePaymentMethod` | none | the default is Platform state |
   | `deletePaymentMethod` | none | the detach is a worker step after the commit |

   - **`deletePaymentMethod` does not detach in a `call`.** A detach is right only if the delete commits: the operation takes `If-Match`, and when a concurrent change wins at the conditional write, the method must still work. The handler marks the method removed under the version check, so that it is no longer listed or usable, and publishes its event. A worker step detaches at the gateway with its own key and then deletes the row; a method that is already detached counts as done.
   - **Contract.** The description of `deletePaymentMethod` says "Detaches at the gateway, then removes". It becomes "Removes the saved method; the gateway detach follows after the commit". This is a change request to api-designer and rides the pull request of the task that builds the route.
   - **A completed setup that never becomes a saved method** leaves a method attached at the gateway: the tab was closed, or the save was refused. That is independent of the `call`: a setup that is created for a gateway customer attaches the method when the browser completes it. The task that builds these routes detaches such methods in its housekeeping, with security-analyst.
