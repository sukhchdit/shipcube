# ADR-0018: Typed configuration (`packages/config`) and secrets handling

- **Status:** Accepted
- **Date:** 2026-11-12
- **Deciders:** principal-architect
- **Related:** brief §4.1 (`packages/config`), §4.11, §13 rule 7; CLAUDE.md §5 (secrets), §9; REQ-PLAT-004, REQ-SEC-011, REQ-CARR-015, REQ-PAY-004, REQ-DATA-002; NFR-OPS-005, NFR-SEC-007; D-022

## Decision

1. **One schema, three consumers.** `packages/config` exports a Joi schema (backend convention) of every runtime variable with type, default, `required` per environment, `secret: true` flag, and documentation; `loadConfig(env)` validates at process start and aborts with the list of **names** of missing/invalid keys (never values) within 5 s (REQ-PLAT-004, NFR-OPS-005). Frontend build-time config (`VITE_*`: API base URL, Stripe publishable key, brand, locales, feature flags endpoint) is a Zod schema in the same package (`config/web`) consumed by Vite's `define` — only non-secret keys are allowed by a test.
2. **Namespaces.** `APP_*` (env, port, base URLs, brand `BRAND_*`), `DB_*` (URL for `platform_app`, migrator URL used only by the migrate job, pool size, `sslmode`), `REDIS_*`, `AUTH_*` (token lifetimes, bcrypt cost ≥ 12 floor, cookie names, CSRF), `AUDIT_*` (verification schedule, partition horizon), `RATE_LIMIT_*`, `CARRIER_*` (per account: enabled, environment, `SECRET_REF`), `PAYMENT_*` (`STRIPE_SECRET_KEY_REF`, webhook secret ref, test-live flag), `STORAGE_*` (S3 endpoint, buckets, path style, presign TTL 300), `MAIL_*` (provider `smtp|ses`, host, from), `OTEL_*`, `FEATURE_*`, `SEED_*` (demo passwords, local-only defaults), `REGION` (brief §10 multi-region seam), `LOCALE_DEFAULT`.
3. **Secrets.** Code holds **references** (`*_REF`), resolved at start by a `SecretProvider`: `env` (local/CI: the reference is the variable name holding the value), `aws-secrets-manager` (ARN/name; cached; rotation-aware). Secret values live only in process memory; Pino redacts by key; `.env.example` lists every key with placeholders; a CI script compares `.env.example` with the schema (0 undocumented keys, 0 secret-looking example values) and Gitleaks scans history and diffs (REQ-SEC-011). Production start-up fails if a secret equals its placeholder, if a Stripe key is live-mode (`PAYMENT_LIVE_KEY_FORBIDDEN`), if ~~`NODE_ENV=production`~~ **`APP_ENV=production`** (*corrected 2026-11-12, amendment 8*) and the Mock carrier/gateway is enabled, or if DB/Redis TLS is disabled outside local (NFR-SEC-007).
4. **Environment matrix.** `local` (compose defaults, Secure cookie relaxed on localhost, Mock enabled, Swagger on), `test` (CI), `staging`, `production` (Swagger off unless configured, Mock disabled, `sslmode=verify-full`). `NODE_ENV` ∈ {development, test, production}; `APP_ENV` carries the finer environment.
5. **Feature flags** are **not** config: DB-backed with Redis cache (ADR-0027); config holds only the flag defaults file path.
6. **Configuration over hard-coding** (brief DoD): token lifetimes, rate limits, deadlines, retry/breaker values, polling intervals, limits (packages, addresses, saved cards), brand strings are schema keys with defaults equal to the REQ values; a lint rule flags magic numbers in services for these concerns (advisory).

## Alternatives considered

- **Zod for the backend schema.** Fixed stack says Joi on the backend; one Joi schema with a generated TypeScript type (`Joi.ObjectSchema` + hand-maintained interface checked by a test) keeps the rule.
- **dotenv-vault / SOPS.** Encrypted env files in repo are still secrets at rest in git; Secrets Manager references satisfy the guardrail.
- **Reading secrets lazily per call.** Simpler start-up but delays failures to runtime; fail-fast start is required (NFR-OPS-005).

## Consequences

- Positive: fail-fast start with actionable names; no secret in code, tests, fixtures or images; environment differences are explicit.
- Negative: adding a variable means schema + `.env.example` + docs (test-enforced).

## Amendment after the P3 security review (2026-11-12, `docs/05-quality/security/P3-architecture-security-review.md` SEC-P3-08; threat-model T-89, R-11, R-16, R-22, T-103; D-ARCH-022)

1. **Key and secret register (SEC-P3-08 item 1).** One key per purpose; the config schema rejects identical values across any two key-type secrets and any symmetric key shorter than 32 bytes. Every key variable holds `<key_id>:<base64>` with `key_id = <purpose>-v<n>`; an optional `<NAME>_PREVIOUS` holds the retired key for dual reads during rotation. **Every ciphertext and HMAC lookup value is stored with its `key_id`** (sibling `<col>_key_id` column, data-model.md §10.4), so reads are dual during rotation and writes use the current key. **AES-256-GCM** uses a 96-bit random nonce, a 128-bit tag and **AAD = table ‖ column ‖ row id or token ‖ key_id**, which stops ciphertext swapping between rows (T-89). At M5 symmetric keys become KMS envelope keys (`GenerateDataKey`, DEK cached ≤ 5 min; `kms:Decrypt` per task role) and the anchor signing key a non-exportable KMS asymmetric key.

2. **Stripe and carrier secrets in CI (item 3).** They are **environment secrets** of the GitHub Environment `carrier-sandbox` (branch policy `main` only; `workflow_dispatch`), consumed only by the `contract-live` job; a lane A policy test fails any `pull_request`/`push` job that references that environment or `secrets.CARRIER_*`/`secrets.STRIPE_*` (ADR-0023 amendment H).
3. **Refusals widen (items 5–6; amends §3).** Placeholder and `local-only-*` values are refused when `APP_ENV ∈ {staging, production}` (was production only). The schema refuses `NODE_DEBUG`, `DEBUG` and `NODE_OPTIONS` containing `--inspect*` outside `local`; nodemailer runs with `logger: false, debug: false` and the AWS SDK logger is unset (R-22).
4. **Developer host (item 7).** Sandbox and Stripe test credentials live only in user-scoped environment variables or a git-ignored `.env.local`; they never enter `compose*.yaml` or `compose.env` (which hold only `local-only-*` values). `npm run hooks:install` (in-house Node script, no new dependency) installs a pre-commit hook that runs Gitleaks in its pinned container on staged files (NFR-SEC-002). Verification: SEC-TC-49, SEC-TC-50, SEC-TC-51.

## Amendment (2026-11-12, batch 0.2): the register has 25 rows (TASK-005, PR #3; D-ARCH-051)

5. **Row count and the code register.** The table in amendment 1 is the authoritative key and secret register and has **25 rows** (`JWT_SIGNING_KEYS` … `STORAGE_*_KEY_REF`/`MAIL_*`). The security review's SEC-P3-08 line and the batch-0.2 dispatch brief said "24 entries": the review counted the table before the four data-model keys named in data-model.md §12 ("ADR-0018 register gaps": `IDENTIFIER_ENCRYPTION_KEY`, `AUDIT_VAULT_HMAC_KEY`, `MFA_CHALLENGE_BIND_KEY`, `MFA_ENROLMENT_CODE_KEY`) were folded in, and `PASSWORD_PEPPER` was reserved for SEC-P3-16. `packages/config/src/keys.ts` (TASK-005) mirrors this table one-to-one with a unique `key_id` per row (25 ids); its `keys.test.ts` asserts the 25-row count, the uniqueness of the ids, and two-way parity between the register's variables and the Joi schema's secret keys (`[SEC-TC-49]`), so a key variable added to the schema without a register row — or a row without a variable — fails the build. Keeping the row *names* of this table and `keys.ts` aligned is a review item whenever either changes (the count assertion is the tripwire). Rows whose "Holder" is a *reference* to an external credential (`STRIPE_*_REF`, `CARRIER_<ACCOUNT>_SECRET_REF`, `DB_*`, `REDIS_URL`, `STORAGE_*`/`MAIL_*`) are register entries for rotation and blast-radius tracking only; the `<key_id>:<base64>` format and the ≥ 32-byte rule apply to the key-type rows.

## Amendment (2026-11-12, batch 0.2 part 2): two secret delivery forms; the tooling set's `_FILE` idiom (TASK-003 PR #5 @4574a14, TASK-005 PR #3 @875409d; PR #5 code review §4 item 3, PR #3 code review §4; `rulings/batch-0.2-rulings.md` Part 2 item 9; D-ARCH-052; clarifies §3 and amendment 1)

6. **Two delivery forms, one rule each.** §3 "Code holds references (`*_REF`)" applies to **external credentials** — values that live in a third-party or platform secret store and rotate independently of our deployment: `STRIPE_SECRET_KEY_REF`, `STRIPE_WEBHOOK_SECRET_REF`, `CARRIER_<ACCOUNT>_SECRET_REF`, `STORAGE_*_KEY_REF`, `MAIL_SMTP_PASSWORD_REF` (schema sensitivity `secret-ref`; resolved once at start by a `SecretProvider`: `env:`, `file:` confined to `/run/secrets`, `aws-secrets-manager:`). **Platform-held material** — the `<key_id>:<base64>` key rows of amendment 1, `DATABASE_URL`, `REDIS_URL`, `SEED_*` — is delivered as a **direct value** in the process environment (schema sensitivity `secret`), injected by Compose locally and by the ECS task definition's `secrets:` from Secrets Manager at M5; this is what amendment 1 already prescribes ("every key variable holds `<key_id>:<base64>`"). The two forms coexist by design; a direct-value key is never also offered as `*_REF`, and Pino redaction, the placeholder refusals (amendment 3) and the `.env.example` parity test cover both.
   **The tooling set.** The keys read only by the one-shot tools — `DATABASE_MIGRATOR_URL`, `SHADOW_DATABASE_URL` (holder `migrate`), `DATABASE_BOOTSTRAP_URL`, `BOOTSTRAP_MIGRATOR_PASSWORD`, `BOOTSTRAP_APP_PASSWORD` (holder `bootstrap`); `packages/config/src/tooling-keys.ts`, outside `CONFIG_SCHEMA`, refused by api/worker in hardened environments — are direct values of the second form. For the two bootstrap passwords the Docker **`<NAME>_FILE`** idiom (`BOOTSTRAP_{MIGRATOR,APP}_PASSWORD_FILE=/run/secrets/<name>`) is admitted as a **register exception, holder `bootstrap` only**: Compose delivers secrets as files; the PostgreSQL image the bootstrap targets uses `POSTGRES_PASSWORD_FILE`; and the tool that holds the cluster-admin credential keeps the smallest import closure (`pg` and `node:*` only — no `@platform/config` graph, no Joi/Zod, no AWS SDK adapter), the same isolation that keeps the ORM out of it. No runtime key gets a `_FILE` variant; `*_REF` with `file:` stays the form for runtime consumers. The bootstrap passwords are the values embedded in `DATABASE_URL` / `DATABASE_MIGRATOR_URL`, so their class follows those keys.
   **Parity requirement (binding; TASK-016, before TASK-014 mounts Compose secrets).** `tools/db/bootstrap.ts#readSecret` meets the `file` provider's bar (PR3-SEC-07): the `_FILE` path is lexically under `/run/secrets` (the `FILE_PATH` rule of `secret-refs.ts`; root injectable for tests), `realpath` confinement, regular file, ≤ 64 KiB, one trailing newline stripped, empty = unset, **exactly one** of `NAME` / `NAME_FILE` set (both set → error), and every error names the variable, never the path or the value. TASK-014 references only `/run/secrets/<name>` paths (one Compose secret per role; the `compose.env` URLs' passwords equal what the bootstrap feeds `00-roles.sql`, PR #5 code review §4 item 5).
   **Register row.** `DB_URL`, `DB_MIGRATOR_URL`, bootstrap credential — Storage column now reads: "direct value in the environment (Compose `environment:`; the two bootstrap passwords also as Compose secret files via `_FILE`) → Secrets Manager-injected environment (ECS `secrets:`; RDS master = break-glass, ADR-0007 am. 7)".

8. **One environment switch for security decisions.**
   - **§3 corrected.** Every refusal in `packages/config` keys on `APP_ENV`: placeholders and `local-only-*` values, debug flags, insecure DB/Valkey transport and tooling keys are refused when `APP_ENV ∈ {staging, production}` (amendment 3); the Mock carrier and the Mock payment gateway (`MOCK_CARRIER_ENABLED`, `MOCK_SCENARIOS_ENABLED`, the Mock gateway webhook route) are refused when **`APP_ENV = production`** and allowed in `staging` behind the gateway's HMAC (ADR-0010 amendment 9; SEC-TC-24; `guards.ts`). `NODE_ENV` is read by **no** guard, so a wrong `NODE_ENV` can never weaken a refusal.
   - **§4 completed.** `NODE_ENV ∈ {development, test, production}` is the library-behaviour switch (Express, React, Prisma and logger defaults). **Staging and production require `NODE_ENV=production`:** the runtime images set it (`ENV NODE_ENV=production`, platform.md image table) and the TASK-014 entrypoint preflight (D-ORCH-007 item 2; PR3-SEC-13/-11) refuses `NODE_ENV ≠ production` when `APP_ENV ∈ {staging, production}`, next to its `NODE_OPTIONS` allow-list and `PG*` refusals (exit 78 within 5 s; container test).
