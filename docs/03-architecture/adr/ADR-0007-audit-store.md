# ADR-0007: Immutable audit store — partitions, triggers, roles, hash chain scope, same-transaction writes, redaction and privacy erasure

- **Status:** Accepted
- **Date:** 2026-11-12
- **Deciders:** principal-architect, data-architect (security-analyst and compliance review at P6)
- **Related:** brief §4.9, §4.12; REQ-AUDIT-001..025, DR-A09..A13; NFR-AUDIT-001..007, NFR-PRIV-002/003; A-043 (chain scope), A-044, A-045 (erasure mechanism), A-046; ADR-0005 (RLS), ADR-0003 (route metadata)

## Context

The audit trail is a standing obligation: automatic capture via route metadata, a fixed entry schema, DB-enforced immutability (app role INSERT/SELECT only; triggers for every role), SHA-256 hash chain with scheduled verification, monthly range partitions with later S3 Object Lock archive, same-transaction writes for mutations, fail-closed sensitive reads, redaction, and a privacy-erasure mechanism that "works without breaking the chain" — the brief leaves two choices to this ADR: the **hash-chain scope** (A-043 proposes per-organisation streams) and the **erasure mechanism** (per-subject key shredding vs tokenised identifiers, A-045).

## Decision

### Storage

- `audit_entries` **range-partitioned by month on `occurred_at`** (PK `(occurred_at, id)`; `id` UUIDv7). Partitions `audit_entries_YYYY_MM` created by the initial migration (current + 3) and by the daily `audit-maintenance` job (REQ-AUDIT-017); **no default partition**, so an insert with no partition fails and the business transaction rolls back (fail closed). `audit_partitions(name, from, to, created_at, archived_at NULL, archive_manifest_sha256 NULL)` records metadata and the M5 archive marker (REQ-AUDIT-018).
- Columns per REQ-AUDIT-003 plus `stream_id uuid NOT NULL`, `target_org_id uuid NULL` (operator cross-tenant), `prev_hash bytea(32)`, `entry_hash bytea(32) UNIQUE` (per partition; uniqueness across partitions is enforced by the chain itself), `pii_token_count int`. Indexes: `(stream_id, occurred_at DESC)`, `(org_id, occurred_at DESC)`, `(user_id, occurred_at DESC)`, `(entity_name, entity_id, occurred_at DESC)`, `(action, occurred_at DESC)`, `(correlation_id)`, `(outcome, occurred_at DESC)`; `ip` filter uses `(ip, occurred_at DESC)`. Query-plan tests prove a one-day filter prunes to one partition (REQ-AUDIT-016).
- **Immutability:** `platform_app` has `INSERT, SELECT` only; `BEFORE UPDATE OR DELETE` row trigger and `BEFORE TRUNCATE` statement trigger on the parent and every partition raise `audit_entries are append-only` for every role including the owner; partitions are never dropped or detached in this run (REQ-AUDIT-014/018). Tests attempt UPDATE/DELETE/TRUNCATE/DROP TRIGGER as `platform_app`, `platform_migrator` and the owner (REQ-AUDIT-015). *Amended 2026-11-12 (amendment 7): the owner is the `NOLOGIN` role `platform_audit_owner`, never `platform_migrator`; DDL is guarded by an identity-based event trigger.*

### Capture

`packages/audit` middleware, driven by `defineRoute().audit` (ADR-0003): for mutations it computes the field-level diff (RFC 8785 canonical, deterministic key order; `CREATE` = full new value, `UPDATE` = changed fields only, `DELETE` = last old value; no-op updates write nothing unless `audit_noop`), redacts, tokenises PII, computes the chain hash and inserts **inside the business transaction** (`withTenantTx`), so neither exists without the other (REQ-AUDIT-004; failure → 500 `AUDIT_WRITE_FAILED`; *amended 2026-11-13, amendment 10 item 2: a lock-wait timeout on the stream lock → 503 `AUDIT_LOCK_TIMEOUT`, retryable — the business transaction rolls back in both cases*). `STATE_TRANSITION` entries are written by the state machine through the same writer. For `VIEW`/`DOWNLOAD` of `SENSITIVE` entities (DR-A12) the entry is written before the response is released and the request fails closed with 503 `AUDIT_UNAVAILABLE` (REQ-AUDIT-005); `NORMAL` reads are best-effort. `FAILED` outcomes (409/422/5xx after authorisation) are written in a separate transaction; 400 validation failures are logged only (REQ-AUDIT-010). Actor types `USER | API_KEY | SYSTEM_JOB | ANONYMOUS`; sources `web | admin | api | worker` (from `X-Client-App`/process). Allow-listed direct callers of the writer: identity events (login/logout/failures/MFA), permission denials, config changes, system jobs, state machine — enforced by lint (REQ-AUDIT-001).

### Hash chain — scope decision (A-043 accepted, refined)

**One chain per audit stream**, `stream_id = org_id` for tenant entries and the all-zero UUID for the `SYSTEM` stream (entries without an organisation: anonymous logins, system jobs, config changes). Inside the business transaction the writer takes `pg_advisory_xact_lock(hashtext('audit:' || stream_id))`, reads the stream head (`audit_stream_heads(stream_id, head_hash, head_entry_id, entry_count)` — updated in the same transaction), computes `entry_hash = SHA-256(JCS(entry without prev_hash/entry_hash) || prev_hash)` (first `prev_hash` = 32 zero bytes), inserts the entry and updates the head. *Amended 2026-11-13 (amendment 10, SPK-04): the advisory lock is replaced by the row lock on the stream's head row (`SELECT … FOR UPDATE`), which is lock acquisition and head read in one round trip; the PII vault is written in one multi-row statement before the lock; at most two round trips (one CTE append + COMMIT) run under the lock. The chain definition is unchanged.* The per-stream lock serialises only writers of the same organisation (REQ-AUDIT-012: 50 parallel writers → distinct predecessors), never the whole platform. **Global anchoring without global serialisation:** the nightly job writes a `SYSTEM`-stream `CHAIN_CHECKPOINT` entry whose value lists every stream's `(stream_id, head_hash, entry_count)`, so a deleted-and-rebuilt tenant stream would contradict a checkpoint. Trade-off accepted: a break can only be localised per stream (which is also how auditors query). Verification job (REQ-AUDIT-013): hourly incremental from `audit_chain_verifications.last_verified_entry` per stream, nightly full; result rows store `ok`, `first_broken_entry_id`; a break logs ERROR, increments `audit_chain_broken_total`, emits security event `audit_chain_broken`, marks readiness degraded. Budget: 1 M entries ≤ 5 min (NFR-AUDIT-003) — streaming SHA-256 in the worker, ordered scan per stream by `(stream_id, occurred_at, id)`.

### Redaction and classification

`packages/audit/classification.ts` registers, per audited entity, every field's class `PUBLIC | INTERNAL | PERSONAL | SENSITIVE_PERSONAL | SECRET`; a build-time test fails for an audited entity with an unclassified field (REQ-AUDIT-009, NFR-PRIV-003) and feeds the Pino redaction list (NFR-PRIV-001). `SECRET` values (passwords, hashes, tokens, TOTP secrets, recovery codes, authorisation headers, card/gateway fields) become the literal `[REDACTED]` **before hashing**, so the hash is stable and the secret never exists in the row (REQ-AUDIT-008).

### Privacy erasure — mechanism decision (A-045): **tokenised identifiers with an encrypted vault**

`PERSONAL`/`SENSITIVE_PERSONAL` values in `old_value`/`new_value` are replaced by `{"$pii": "<token>"}` (token = UUIDv7). The value is stored in `audit_pii_vault(token PK, subject_id → data_subjects, entity_name, field, classification, ciphertext bytea, created_at)` encrypted with AES-256-GCM under a per-environment data key wrapped by KMS (local: config key). `data_subjects(id, kind USER | CONTACT, ref_id)` identifies the natural person (the user, or a sender/receiver contact). The chain hashes the **token**, never the value. Erasure (M4/M5 jobs) hard-deletes vault rows of a subject (allow-listed hard delete); the viewer renders `[ERASED]` for a missing token; the chain still verifies; closed partitions exported to S3 Object Lock contain no personal data, which is the decisive argument against key shredding (whose ciphertext would sit forever in an un-deletable compliance-mode object and would still be *personal data* under GDPR Art. 4(1) until the key is destroyed, requiring proof of key destruction). Vault reads are themselves `SENSITIVE` views (audited) and allowed only to `audit:read` holders; vault rows are never exported with partitions. Cost: one extra insert per PII field per entry (batched in the same transaction) and a join on viewer reads (paginated, ≤ 200 rows).

### Viewer (D-008 scope)

`GET /audit/entries` (keyset pagination on `(occurred_at, id)`, required date range ≤ 31 d, filters per REQ-AUDIT-019 mapped to the indexes above), `GET /audit/entries/{id}`, `GET /audit/entities/{entity}/{id}/history`, `GET /audit/chain/status`. Each viewer request writes its own `VIEW` entry (filter summary + count) **after** the result set is fixed, fail-closed (REQ-AUDIT-022); operator cross-tenant scope applies (ADR-0005). Exports, regulator report and signed actions are M2 (`reasonRequired` and `EXPORT` action exist now).

### Archive seam (M5)

`AuditArchiver` interface (`exportPartition(name) → {objectKey, manifestSha256}`) + `archived_at` marker; the S3 Object Lock bucket and job are M5 (NFR-AUDIT-007 DEFERRED). PII vault is excluded from archives by design.

## Alternatives considered

- **Single global chain.** Simplest verification but every write on the platform serialises on one lock (REQ-AUDIT-012 explicitly rejects; ~300 rps would be bound by one row lock).
- **Chain per partition/month.** Avoids locks only if writes are single-threaded per month — same problem.
- **Per-subject key shredding (A-045 option 1).** Keeps values inline (simpler reads) but the ciphertext lands in immutable archives; erasure then depends on key destruction evidence and per-subject key management (tens of thousands of keys). Rejected for the archive reason above.
- **Hashing/pseudonymising PII inline (HMAC).** Irreversible for the viewer; auditors need the values.
- **Application-level immutability only.** Rejected by brief §4.9 ("enforced in the database").

## Consequences

- Positive: DB-enforced append-only; chain verification is parallel per stream; erasure is a delete of vault rows; archives are PII-free; one writer code path.
- Negative: two inserts per PII-bearing entry; the viewer joins the vault; checkpoint entries add a few rows per night; partition maintenance is a hard dependency (readiness degraded < 2 future months).
- Verification: audit test generator (REQ-AUDIT-024, NFR-AUDIT-001/006), immutability tests for every role (NFR-AUDIT-002), chain corruption detection test (NFR-AUDIT-003), classification completeness test (NFR-PRIV-003), redaction property test (NFR-PRIV-002), overhead benchmark (NFR-AUDIT-005).

## Amendments after the threat model (2026-11-12, threat-model.md R-09..R-12, T-84, T-85, T-88)

1. **SYSTEM stream is sharded (R-10, T-85).** Entries without an organisation use `stream_id = SYSTEM_SHARD[n]` with `n = hash(correlation_id) mod 16` (UUIDs `00000000-0000-0000-0000-0000000000NN`), so anonymous logins, public lookups and webhooks do not serialise on one lock. Verification and the nightly checkpoint cover all 16 shards; the viewer treats them as one logical SYSTEM stream.
2. **Personal data never enters the chain in clear (R-11).** `ip`, `user_agent_raw`, `reason`, list-filter values and `target_org_id`-related free text are classified `PERSONAL` and tokenised through the vault like other PII; filtering by IP uses `ip_hash = HMAC-SHA256(AUDIT_INDEX_KEY, ip)` and `ip_coarse` (/24 or /48, not personal data at that granularity) which stay in clear and indexed. The viewer resolves tokens for `audit:read` holders and shows `[ERASED]` after erasure.
3. **Signed, externally anchored checkpoints (R-09, T-84 — P2, designed now, enforced at M5).** *Superseded 2026-11-12 by amendment 7: hourly cadence, ECDSA P-256 instead of HMAC, mandatory sink, `audit_anchors` sequence.* The nightly `CHAIN_CHECKPOINT` is additionally signed with an HMAC key the database never holds (`AUDIT_CHECKPOINT_KEY` from Secrets Manager/KMS) and its hash is written to an append-only external location (CloudWatch Logs with retention lock / the Object Lock bucket at M5; a local file in Compose), so a database superuser cannot recompute the chain undetected.
4. **No runtime audit-off switch (R-12, T-88).** The NFR-AUDIT-005 A/B benchmark uses a **build-time** profile (`BENCHMARK_AUDIT_OFF=1` at image build producing a separately tagged `-bench` image that refuses to start when `APP_ENV` is `staging` or `production`); there is no runtime flag that disables audit.
5. **Denied/failed floods.** `PERMISSION_DENIED` and `webhook_signature_invalid` entries remain one per event (REQ-RBAC-007, REQ-PAY-011) but are written to the SYSTEM shards or the actor's stream under the per-IP rate limits of DR-A22, which bound their rate; aggregation is revisited if P6 benchmarks show pressure.
6. **Physical refinements (data-model.md §5/§12).** `entry_hash` is `UNIQUE (entry_hash, occurred_at)` per partition (a partitioned table cannot carry a global unique without the partition key); a dense `stream_seq bigint` per stream gives explicit chain order and gap detection; the verifier checks global hash uniqueness and gap-free sequences. The nightly checkpoint stores the SHA-256 digest of the ordered `(stream_id, head_hash, stream_seq)` list (full list in `audit_checkpoint_heads`), and the external anchor signs that digest. Append-only tables are exempt from `updated_at/updated_by/version` (NFR-DATA-003 exemption for product-manager). Vault deletions use the `platform_erasure` role (ADR-0005 amendment 6).

## Amendment after the P3 security review (2026-11-12, `docs/05-quality/security/P3-architecture-security-review.md` SEC-P3-03, T-84; D-ARCH-019)

7. **Tamper evidence against the DB owner and superuser (SEC-P3-03, HIGH; supersedes amendment 3's HMAC anchor and the "nightly" cadence, and the owner statement in §Storage).** Physical detail in `data-model.md` §4.4, §5.2, §5.5, §5.6.
   1. **Ownership separation.** A new `NOLOGIN NOINHERIT` role **`platform_audit_owner`** owns `audit_entries` and all partitions, `audit_stream_heads`, `audit_checkpoint_heads`, `audit_chain_verifications`, `audit_partitions`, `audit_anchors` (new), `audit_pii_vault`, `data_subjects`, and the functions `platform.audit_forbid_mutation`, `platform.audit_vault_guard` and `platform.ensure_audit_partitions` (`SECURITY DEFINER`; EXECUTE granted to `platform_app` for the daily job; the only code path that performs DDL on audit objects). `platform_migrator` is **not** a member and owns nothing in the audit module. Audit DDL runs only in the **bootstrap lane** (cluster-admin credential, `prisma/bootstrap/*.sql`); the migration linter rejects audit DDL in regular migrations unless the file carries `-- @audit-ddl security-approved: <reviewer> <date>` and sits in the bootstrap lane. Effect: `ALTER TABLE … DISABLE TRIGGER`, `DROP TRIGGER`, `DETACH PARTITION` or `NO FORCE ROW LEVEL SECURITY` by whoever holds the migrator login fails with "must be owner"; tampering needs the cluster superuser. One privilege path remains: `platform_migrator` owns schema `public`, so it could `DROP TABLE` an audit table by schema ownership — the `sql_drop` event trigger of item 2 closes it, SEC-TC-43 includes those statements, and moving the audit objects into a dedicated `audit` schema owned by `platform_audit_owner` (closing it by privilege alone) is recorded as an M5 option.
   2. **Event trigger by object identity.** `platform.audit_ddl_guard()` fires on `ddl_command_end` (iterating `pg_event_trigger_ddl_commands()`) and `sql_drop` (iterating `pg_event_trigger_dropped_objects()`) and raises for any command whose object identity is an audit object or an `audit_entries_%` partition unless `current_user = 'platform_audit_owner'` (true only inside `ensure_audit_partitions`). No statement-text matching, so dynamic SQL (`DO $$ EXECUTE 'ALTER TABLE audit_' || 'entries …' $$`) is caught. The row and statement triggers of §Storage stay.
   3. **Hourly anchors.** After every **hourly** incremental verification (not only nightly) the worker writes the SYSTEM-stream `CHAIN_CHECKPOINT` entry, the `audit_checkpoint_heads` rows and one **anchor** record; the window in which a rewrite can go undetected is therefore ≤ 1 h.
   4. **Asymmetric signature.** Anchors are signed with **ECDSA P-256 / SHA-256** under a private key only the worker can use (`AUDIT_ANCHOR_SIGNING_KEY_REF`: Secrets Manager, or KMS `Sign` with a non-exportable `ECC_NIST_P256` key at M5; a key file locally). Verifiers (API `GET /audit/chain/status`, the worker verifier, third parties such as a regulator at M2) hold only the public keys (`AUDIT_ANCHOR_PUBLIC_KEYS`, `key_id → PEM`). The HMAC `AUDIT_CHECKPOINT_KEY` is dropped. Decided variant: ECDSA P-256 rather than Ed25519 because AWS KMS offers no Ed25519 signing and one algorithm keeps a single verifier for local and M5.
   5. **Anchor log integrity.** `audit_anchors(anchor_seq, checkpoint_entry_id, created_at, heads_digest, prev_anchor_hash, anchor_hash, algorithm, key_id, signature)`: `anchor_seq` is dense, `prev_anchor_hash` chains the records, `anchor_hash = SHA-256(anchor_seq ‖ created_at ‖ heads_digest ‖ prev_anchor_hash)`, `signature = ECDSA(anchor_hash)`. The same record is appended to the external sink `AUDIT_ANCHOR_SINK`, which is **mandatory in every environment** (`file:` path in local/test/CI; S3 Object Lock compliance mode or a retention-locked CloudWatch Logs group at M5). "When configured" is removed.
   6. **Verifier scope.** Every hourly run fails with `ANCHOR_MISSING` (security event `audit_anchor_missing`, readiness degraded) on a gap, duplicate, out-of-order record or a sink/table disagreement; `CHECKPOINT_SIGNATURE_INVALID` on a bad signature; and recomputes every stream at the anchored `(stream_id, stream_seq)` of the latest anchor, comparing heads (`CHECKPOINT_HEAD_MISMATCH`; a break inside a stream stays `audit_chain_broken`). `audit_chain_verifications` records the failure kind and the anchor range checked. The nightly run checks all anchors since the previous nightly run.
   7. **M5 precondition (platform-architect; G4 for any production release; risks.md R-ARCH-18).** The anchor sink is S3 Object Lock in compliance mode (worker role `s3:PutObject` only *— amended 2026-11-13, D-ARCH-094, ADR-0021 amendment 2: plus `s3:GetObject` and `s3:ListBucket` on the `anchors/` prefix for the verifier's hourly sink read and the writer's retry comparison; still no delete and no bypass*) or CloudWatch Logs with no delete or put-retention permission for any app or CI role; RDS master credentials are break-glass only; `pgaudit` DDL and role logging go to CloudWatch (platform.md §4.3, §4.8).
   - **Residual after this amendment:** MEDIUM — a cluster superuser can rewrite at most the last hour of entries undetected. Accepted for this run (no production data, AS-2); closed by item 7 at M5. Verification: SEC-TC-17 (extended), SEC-TC-43, SEC-TC-44; NFR-AUDIT-002/003; Wave-0 spike SPK-08.

## Amendment after the remediation verification (2026-11-12, review §14.4 SEC-P3-27 and SEC-P3-33 items 1 and 10; D-ARCH-029, D-ARCH-033)

8. **Search-path hardening of the audit owner's functions; schema ownership by privilege (SEC-P3-27, MEDIUM; completes amendment 7 and makes its item 1 true).** Physical detail in `data-model.md` §4.2, §4.4 (amendment), §4.5, §4.6 C11/C13/C14, §5.2, §5.3, §5.7, §8.3 rule 13 and §12 A13.
   1. **Fixed search path.** `platform.ensure_audit_partitions`, `audit_forbid_mutation`, `audit_vault_guard` and `audit_ddl_guard` declare `SET search_path = pg_catalog, pg_temp` (`pg_temp` explicitly last, `public` absent), so functions and operators resolve in `pg_catalog` only and a `public.pg_advisory_xact_lock(integer)` or `public.to_char(date, text)` planted by the migrator (CVE-2018-1058 class, CWE-426) is never called. Relations stay `public.`-qualified; built-ins are qualified with explicit casts (`pg_catalog.pg_advisory_xact_lock(pg_catalog.hashtext('audit:partitions')::bigint)`, `pg_catalog.to_char(v_month::timestamp, 'YYYY_MM')`, `pg_catalog.format(…)`, `pg_catalog.uuidv7()`). The same rule applies uniformly to every `SECURITY DEFINER` function (the §4.5 `platform_definer` functions, `app_is_operator`, `job_context`; ADR-0005 amendment 7), and every bootstrap-lane script starts with `SET search_path = pg_catalog, pg_temp;` before `SET ROLE`. The application-side advisory-lock calls of §5.4/§5.5 are qualified as defence in depth.
   2. **The guard matches schemas by OID, derived at call time.** `audit_ddl_guard` qualifies `pg_catalog.pg_class`, `pg_index` and `pg_namespace`, collects on each call the namespaces of every relation and function owned by `platform_audit_owner` (an empty set fails closed) and refuses `ALTER SCHEMA … RENAME`, `… OWNER TO`, `COMMENT ON SCHEMA` and `DROP SCHEMA` for them. OIDs are not baked into the function body because every `pg_restore` (including the §8.6 rehearsal) and every RDS snapshot restore assigns new OIDs. `sql_drop` matches by OID, with the (rename-proof) schema name as fallback for a schema dropped in the same command. Replacing the guard later is `ALTER EVENT TRIGGER … DISABLE` → replace → re-enable in one transaction.
   3. **Schema ownership by privilege (review item 6, adopted).** A new `NOLOGIN NOINHERIT` no-member role **`platform_schema_owner`** owns schemas `public` and `platform`; `platform_migrator` holds `USAGE, CREATE` (all Prisma Migrate needs) and `platform_definer` gains `CREATE` on `platform` (required for `ALTER FUNCTION … OWNER TO`). Schema rename, `DROP SCHEMA … CASCADE`, `DROP FUNCTION platform.audit_ddl_guard() CASCADE` and `DROP TABLE` by schema ownership are now closed by privilege as well as by the guard, which retires the caveat in amendment 7 item 1 ("`platform_migrator` owns schema `public`, so it could `DROP TABLE` …"); a dedicated `audit` schema stays an M5 option. C13 covers both no-member roles. On RDS (PostgreSQL 16+ `CREATEROLE` self-grant) exactly one `pg_auth_members` row per role for the bootstrap master with `admin_option = true`, `set_option = false`, `inherit_option = false` is allowed and treated as break-glass like the master secret (SEC-P3-33 item 10; platform.md §4.3; SPK-08 verifies).
   4. **Catalog tests and linter.** C11: every `SECURITY DEFINER` function has exactly one `search_path` entry in `proconfig` and it equals `search_path=pg_catalog, pg_temp`. C14: the three audit trigger/guard functions (not `SECURITY DEFINER`) carry the same entry, and `ALTER SCHEMA public|platform RENAME` raises 42501 even for the test superuser, which proves the OID match independently of privilege. Migration-linter rule 13 is the text-level early warning. Negative test SEC-TC-61: as the migrator, plant the two overloads, attempt `ALTER SCHEMA … RENAME` and `DROP … CASCADE` (all raise); as `platform_app`, `ensure_audit_partitions(3)` still succeeds with no marker row and every trigger enabled.
   5. **Corrected rationale for ECDSA P-256 (SEC-P3-33 item 1; corrects amendment 7 item 4 and D-ARCH-019; D-ARCH-029).** AWS KMS has signed with Ed25519 (`ECC_NIST_EDWARDS25519`) since 2025-11-07, so "KMS offers no Ed25519 signing" is withdrawn. The choice stands (review ruling 2) because P-256/SHA-256 is FIPS 186-5 approved and is the one signature algorithm every target verifier already supports without new code or library versions: `openssl dgst -sha256 -verify` for regulators and auditors, WebCrypto `ECDSA` in every browser of the ADR-0026 §11 matrix for an in-browser verifier, Node 24 `crypto.verify`, and every KMS/HSM the platform may move to (Azure Key Vault has no Ed25519). KMS `ECDSA_SHA_256` with `MessageType = RAW` signs the same SHA-256 digest Node signs, so one verifier serves local and M5. ECDSA's signature malleability is harmless because the verifier compares the sink record with the table record byte for byte (SEC-TC-44). The `algorithm` column is a CHECK-constrained enum, so `ED25519` can be added later by extending the CHECK and the verifier.
   - **Effect on the residual.** With items 1–3 in place, amendment 7's statement "tampering needs the cluster superuser" holds: RR-04 returns to the superuser-only actor with the ≤ 1 h window, and the migrator credential no longer reaches it. SEC-COND-05 is closed at design level; SEC-COND-03 closes with it except item 7 (locked sink, G4-production precondition). Verification: SEC-TC-61 (new), C11/C14 as amended, SPK-08 extended (risks.md).

## Amendment 9 (2026-11-13, SPK-08 TASK-012 PR #12 A-1..A-7, PR12-SEC-04/-05; D-ARCH-076, D-ARCH-077)

1. **Digest definition pointer (A-2).** Amendment 6's "SHA-256 digest of the ordered `(stream_id, head_hash, stream_seq)` list" is superseded: the heads digest is **defined in data-model.md §5.5** — items `stream_id (16 B) ‖ be64(entry_count) ‖ head_hash (32 B)`, sorted ascending by the 16 raw UUID bytes, empty set = SHA-256 of the empty string. The spike prototype and TASK-116 follow §5.5; this ADR no longer restates the layout.
2. **Sink line and timestamp (A-3, A-4).** The sink record is the RFC 8785 (JCS) line of data-model §5.5, compared byte-for-byte as a string; `created_at` is `clock_timestamp()` rendered by PostgreSQL in the hashed text form. Both are hash/sink inputs and are frozen before the first anchor is written.
3. **Verifier (A-1, A-5, A-6, A-7; AF-9/AF-12).** Step precedence with every event emitted and `failure_kinds[]`; strict DER parsing (WebCrypto verifiers convert DER → P1363 — amendment 8 item 5's "without new code" holds for OpenSSL/Node only); the sink retry window is clamped to [now − 15 min, now + 2 min]; step (iii) runs on the latest anchor that passed (i) and (ii); the latest-anchor check is sound only together with the nightly full walk from seq 1 that ignores `last_verified_*` — behind-head rewrites with an intact head row are detected within 24 h, which is the bound amendment 7 claims (data-model §5.6).
4. **Guard and triggers `ENABLE ALWAYS`; name squatting (PR12-SEC-02/-03/-04).** Both event triggers and every audit trigger are created `ENABLE ALWAYS` (closes the replica-mode bypass for non-superusers; stated limits in data-model §5.2); the guard matches the object's own name for every relation and type kind; `ensure_audit_partitions` fails loudly on a foreign object under a partition name; readiness is contiguity from the catalogue. The RDS master's `SET ROLE` path remains undetectable by event triggers and is covered at M5 by `pgaudit.log = 'ddl, role, misc_set'` with the PR12-SEC-04 filters (COND-G4-PROD).

## Amendment 10 (2026-11-13, SPK-04 TASK-018 PR #27 FALLBACK — `docs/04-plan/spikes/SPK-04.md`, evidence `docs/05-quality/performance/spikes/SPK-04/`; D-ORCH-031; D-ARCH-085..089; `rulings/wave-0-spk04-rulings.md`)

**Evidence.** On the shared Windows 11 / Docker Desktop reference host the §5.4 procedure as written (`on`) did not hold 300 req/s with a 20 % hot-tenant share (60 req/s on one stream): the hot stream queued on its advisory lock (lock-wait p95 229–603 ms), the waiters held their pool connections, and every tenant then hit the 2 s pool-checkout `maxWait` (`SERVICE_UNAVAILABLE`). Δp95 vs audit-off was +1 042 ms as written and +217 ms for the batched-vault candidate; at 150 req/s `on` passed (pooled Δp95 +9.9 ms). All 300 req/s repetitions are INCONCLUSIVE under TEST-STRATEGY §7.10 (host saturated), but the failure mode is structural: lock-hold time = round trips under the lock × client–server RTT (1.1–1.7 ms p50 on this host, ≈ 5 round trips under the lock as written), and stream utilisation = hot-stream rate × hold time. Integrity held throughout (223 118 entries recomputed, 0 chain faults; every immutability layer answered 42501). R-ARCH-04 is confirmed; this amendment is the FALLBACK of PLAN.md §spikes ("multi-row vault insert") plus the levers the spike asked this ADR to decide.

1. **Write path = batched vault + head-row lock (lever (a) adopted; supersedes the lock sentence of §Hash chain and data-model §5.4 as written).** Per entry, in this order: (i) *before the lock*, one multi-row `INSERT INTO audit_pii_vault … SELECT … FROM unnest($arrays…) ON CONFLICT DO NOTHING`, then one multi-row token lookup as a **separate** statement (a new snapshot is required to see a concurrent writer's winning row; `ON CONFLICT DO UPDATE … RETURNING` is not available because the vault's `BEFORE UPDATE` guard raises); (ii) the stream is serialised by the **row lock on its `audit_stream_heads` row** — `SELECT entry_count, head_hash, head_occurred_at, clock_timestamp() … WHERE stream_id = $1 FOR UPDATE` — which is lock acquisition, head read and database clock in **one** round trip (under `READ COMMITTED` a `FOR UPDATE` that waited returns the latest committed row version); the advisory lock is dropped, and with it the `hashtext` slot-sharing caveat (OI-21 closed); a missing head row (first entry of a stream) is created with `INSERT … ON CONFLICT DO NOTHING` and the lock statement repeated (+2 round trips once per stream); (iii) the hash is computed in the application; (iv) **one** CTE statement appends the entry and advances the head (`WITH appended AS (INSERT INTO audit_entries …) UPDATE audit_stream_heads … WHERE stream_id = $1 AND entry_count = $seq − 1`, `expectAffected(1)`); (v) COMMIT releases the lock. **Design rule: at most two round trips from lock grant to COMMIT inclusive (the CTE and COMMIT); nothing else executes under the lock and no other lock is taken after the head lock** (the deadlock-freedom argument is unchanged: the audit append is the last database work of the transaction). Round trips per audited request become create (3 PII) 8, update 9, fail-closed VIEW 9, SYSTEM 6 (as written: 15 / 12 / 12 / 9; batched spike variant: 9 / 10 / 10 / 7). The grant `UPDATE` on `audit_stream_heads` for `platform_app` (data-model §4.4) is now load-bearing for the lock; no foreign key may ever reference `audit_stream_heads`.
2. **Fail fast under the lock (lever (c) adopted).** The head-row lock is acquired under a short `lock_timeout` — `DB_AUDIT_LOCK_TIMEOUT_MS`, default **250 ms**, validated below `DB_TX_LOCK_TIMEOUT_MS` — set inside the lock statement itself (`WITH lt AS MATERIALIZED (SELECT set_config('lock_timeout', $2, true)) SELECT … FROM audit_stream_heads h CROSS JOIN lt … FOR UPDATE OF h`: the CTE is evaluated before the `LockRows` node; TASK-030 proves the bound with a held-row test, and falls back to a separate `SET LOCAL lock_timeout` round trip if it does not hold). SQLSTATE 55P03 from this statement maps to **503 `AUDIT_LOCK_TIMEOUT`** (retryable, `Retry-After: 1`, metric `audit_lock_timeout_total{stream_kind}`), distinct from **500 `AUDIT_WRITE_FAILED`** (non-retryable: head moved, partition missing, integrity). In both cases the business transaction rolls back — nothing is ever captured without its audit entry (REQ-AUDIT-004, O4); clients retry with their Idempotency-Key, webhooks and job steps retry under their own at-least-once semantics. The short `lock_timeout` stays in force for the CTE and COMMIT; the only lock those can wait on is the partition's `RowExclusiveLock` behind `ensure_audit_partitions` DDL (daily, off-peak) — a retryable 503 in that window is accepted.
3. **Pool protection = per-tenant admission bulkhead (D-ARCH-086; TASK-025; data-model §7.7).** A lock waiter holds its pool connection, so without a bound one hot stream drains the pool for every tenant (SPK-04 §5 finding 3 — a cross-tenant availability effect, not only latency). `withTenantTx` admits at most **`DB_TENANT_MAX_CONCURRENT_TX`** concurrent transactions per admission key per process (default `max(2, floor(DB_POOL_MAX / 2))`; key = `orgId`, `anonymous` for `''`, `operator` for OPERATOR scope), FIFO wait at most **`DB_TENANT_ADMISSION_WAIT_MS`** (default 250 ms, ≤ `maxWait`), queue depth ≤ 2 × cap; overflow → 503 `SERVICE_UNAVAILABLE` with reason `TENANT_CONCURRENCY_LIMIT` (retryable, `Retry-After: 1`), metrics `db_tenant_admission_rejected_total{reason}` and `db_tenant_admission_inflight`. Admission precedes pool checkout and is released in `finally`. The cap bounds a tenant's share of the pool to one half; item 2 bounds how long it holds that share. The worker twin applies the same bulkhead per job organisation (TASK-047). It is a noisy-neighbour control, not a fairness scheduler: two simultaneously hot tenants can still fill a pool — accepted; per-organisation request rate limits are DR-A22/M2 territory.
4. **Deferred lever: hot-tenant sub-streams (lever (b)) — not adopted now.** It changes chain semantics (`stream_id ≠ org_id`), the verifier, the checkpoint heads and the viewer, and the measured need vanishes once round trips under the lock fall from 5 to 2 and RTT is Linux-class. **Trigger:** the clean 300 req/s run of item 6 still shows hot-stream lock-wait p95 > 5 ms or Δp95 over budget with the 20 % hot share. Design sketch for that case: `stream_id = uuid5(org_id, n)`, `n = hash(correlation_id) mod audit_stream_shards(org_id)` (default 1), viewer and verifier treat an organisation's shards as one logical stream like the 16 SYSTEM shards, a shard-count change starts new streams (no re-chaining) and is itself a `CONFIG_CHANGE` entry. Adoption requires a superseding amendment.
5. **Round trips under the lock are the design budget, not a latency number.** "≤ 2 round trips from lock grant to COMMIT" is host-independent and testable (statement-sequence test with a query spy, TASK-030 exit E1); the latency budget of NFR-AUDIT-005 is then a property of the host's RTT and is measured by item 6.
6. **Measurement (lever (d) adopted; NFR-AUDIT-005 / NFR-PERF-001 method wording with product-manager, D-ARCH-088).** The build-time `-bench` image stays the only audit-off (amendment 4). The `audit-ab` scenario runs the NFR-PERF-001 mix with a **20 % hot-tenant share** on one stream, the fail-closed VIEW second transaction inside the route latency, ≥ 2 repetitions per rate with **randomised arm order**, the delta computed **per repetition**; pass = mean of valid per-repetition deltas within budget and no valid repetition over twice the budget; the §7.10 validity rule applies per repetition. The gating run is **TASK-280**'s clean 300 req/s `audit-ab` on a quiet or native-Linux Docker host, due before G3 (D-ORCH-031 (2)); A-029 is re-baselined to 150 req/s clean with audit on for the shared Windows host.
7. **SQL rules for the writer (TASK-030; data-model §5.4, §8.3).** (a) Multi-argument `unnest(a, b, …)` stays **unqualified** — `pg_catalog.unnest(a, b)` does not exist (42883) — the recorded exception to the qualified-built-ins rule, alongside (b) `extract`, which is keyword syntax: `extract(epoch FROM x)` unqualified or `pg_catalog.extract('epoch', x)`; (c) the CTE insert carries **no `RETURNING`** (nothing is needed back; the statement stays independent of any policy ever placed on `audit_entries`); (d) arrays are bound as typed parameters (`$n::uuid[]`, `$n::bytea[]`) — `TenantDb` refuses `Prisma.join`/`Prisma.sql` fragments; (e) the token lookup is `unnest(…) WITH ORDINALITY … CROSS JOIN LATERAL (SELECT token … LIMIT 1)` or any shape whose `EXPLAIN` against a ≥ 100 k-row vault is an index lookup per key on `ux_audit_pii_vault__subject_field_value` with no Seq Scan or Hash Join over the vault (asserted by an integration test — the spike's batched arms showed PostgreSQL CPU at 95–114 % with an unchanged median, unattributed); (f) the zero hash is `decode(repeat('00', 32), 'hex')` or a 32-zero-byte parameter — `'\x' || repeat('00', 32)` is `text` and fails with 42804 against `bytea` (D-ARCH-087; data-model §5.4 step 3 corrected; PR #24's bootstrap `DEFAULT`s already use the correct form).
8. **Harness lifecycle (D-ARCH-089).** The SPK-04 harness merges as **executable evidence** under `prisma/tests/spikes/spk04/**` and `tests/load/spikes/**` only, with the SPK-04 §8 port-then-delete table naming the deleting PR per file (SPK-03 / PR #7 m7 and SPK-08 §8.1 precedent): `chain.ts`/`canonical.ts` and their tests → TASK-030 (after porting the pinned chain vector); `server.ts`, `runner.ts`, `verdict.ts`, fixtures and the k6 script → TASK-280 (after porting the arm loop, CPU sampler, verdict and evidence writer into `tests/load/lib` and the script to `tests/load/audit-ab.js`). Conditions: no product code imports from either tree (boundaries), not counted in coverage, not in any image, the `SPK04_AUDIT` runtime switch stays harness-only (amendment 4).
