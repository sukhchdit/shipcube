# ADR-0009: Identifiers (UUIDv7), human-readable numbering, money and units

- **Status:** Accepted
- **Date:** 2026-11-12
- **Deciders:** principal-architect, data-architect
- **Related:** brief §4.4, §4.10; REQ-RLS-009/012, REQ-DATA-006/015, REQ-API-016, REQ-PRICE-002/004, DR-A24, DR-B05, DR-B06, DR-B11, DR-B22; D-032; NFR-DATA-001/002; A-050, A-059

## Context

The brief requires UUID primary keys (UUIDv7 for index locality), per-country human-readable sequences for orders/invoices/credit notes, integer minor-unit money with ISO 4217 codes and no floating point, metric and imperial entry with a configurable volumetric divisor, and `timestamptz` UTC storage with local dates kept as date + IANA zone.

## Decision

1. **Identifiers.** All PKs are UUIDv7 generated **in the application** with `uuid` 14 `v7()` (so the ID exists before the insert for outbox/audit/idempotency correlation) and PostgreSQL 18 `uuidv7()` as the column default for rows created by SQL (seed, triggers). A schema test asserts every `id` column is `uuid`. Public identifiers in URLs are the UUIDs; order numbers are display/lookup keys, never PKs.
2. **Number sequences (DR-A24, D-032).** `number_sequences(scope ORDER|INVOICE|CREDIT_NOTE, country char(2), next_value bigint, PK(scope,country))`. Allocation inside the checkout transaction: `UPDATE number_sequences SET next_value = next_value + 1 WHERE scope = $1 AND country = $2 RETURNING next_value - 1` (row lock → monotonic, unique, gaps allowed on rollback). Format `<alpha-2 origin>-<8-digit zero-padded><Luhn mod-10 check digit>` (e.g. `US-000012345X`); the public tracking lookup validates the check digit before any query (A-050). Invoice/credit-note scopes are defined, not allocated, before M2.
3. **Money.** `Money = { amount: bigint-safe integer (minor units), currency: ISO 4217 }` in `packages/shared/money` with `add/sub/mulRatio/allocate/convert/format`; **branded type** `Minor` prevents mixing with plain numbers; arithmetic uses integers only, percentage and FX multiplication round once, half away from zero at line level (DR-B11); `currencies(code, exponent)` from reference data (REQ-DATA-006) drives exponents; unknown codes throw. *Amended 2026-11-20 by amendment 2 item 3: the code computes with the static table `CURRENCY_EXPONENTS`; the reference table is its database copy, kept equal by a parity test.* Storage: `BIGINT` + `CHAR(3)` pairs (column naming `<name>_amount`, `<name>_currency`); API: `{ "amount": 1234, "currency": "USD" }` (REQ-API-016); FX rates `NUMERIC(18,6)` in DB, strings in the API. Lint forbids `number` arithmetic on `Minor`, `parseFloat/toFixed` in money paths; property tests cover rounding invariants (NFR-QUAL-003).
4. **Units (DR-B05/B06).** Weights stored as integer **grams**, dimensions as integer **millimetres**; `packages/shared/units` converts entry values (kg/lb, cm/in) to internal integers (halves up) and back for display (1 decimal). Volumetric weight = L×W×H / divisor computed on internal integers, rounded up to the next gram; billable weight per package = max(actual, volumetric) rounded up to the service increment (default 500 g / 1 lb), summed per shipment. Divisors (default 5000 cm³/kg, 139 in³/lb) come from `carrier_services` per unit system. *2026-11-20, amendment 2 item 4: the unit system is that of the origin country, never the unit of entry.*
5. **Time.** `timestamptz` everywhere (schema test rejects `timestamp`); local-by-nature dates (pickup date, holidays) as `date` + `tz text` (IANA). API: ISO 8601 `Z`; local dates `YYYY-MM-DD` + `time_zone`. DST-boundary unit tests for date helpers (NFR-DATA-002).
6. **Standard columns.** `id, created_at, updated_at, created_by, updated_by, version` on every table; soft-deletable tables add `deleted_at, deleted_by`; server-stamped by the Prisma extension; `version` incremented in a conditional update (`WHERE version = $expected`), 0 rows → 409/412 (REQ-RLS-011). Reserved system user ID for seed/jobs.

## Alternatives considered

- **`dinero.js`/`currency.js`.** Good libraries, but a 150-line integer helper with a branded type is simpler to audit at ≥ 95 % coverage and avoids a dependency on the critical path.
- **Postgres `SEQUENCE` per country.** Dynamic sequence creation per new country complicates migrations; a row-locked table is sufficient at launch volume and is portable.
- **`NUMERIC` money columns.** Rejected by the brief (integer minor units).
- **Decimal libraries for money.** Rejected: integer arithmetic is exact and faster.

## Consequences

- Positive: index-friendly IDs, exact money, deterministic rounding, one place for units.
- Negative: branded types add ceremony; per-country sequence rows are a (tiny) hotspot at very high checkout rates — acceptable for 10× launch volume (NFR-SCALE-001).

## Amendment 1 (2026-11-13, PR #26 / TASK-032 reviews — security PR26-SEC-03 and PR26-SEC-05, code review n7 and n8; D-ARCH-091, D-ARCH-092; `docs/03-architecture/rulings/wave-0-sheet-fold-3.md`)

1. **Standard columns are enforced twice (amends decision 6).** The Prisma extension stamps the columns and refuses forged input with a 400: the ergonomic control, ORM path only. A **database guard**, `platform.std_columns_guard()` — an assertion-only `BEFORE INSERT OR UPDATE FOR EACH ROW` trigger on every runtime-writable table that carries the full standard-column set — makes the database reject a write, raw SQL included, whose `created_by`/`updated_by` are not the context actor (the reserved ANONYMOUS id when the context has none), whose `version` is not 1 on insert and `OLD.version + 1` on update, or that changes `id`, `created_at` or `created_by`. `platform_migrator` (the migration lane and the reference seed) is exempt. Specification, scope, cost, residuals and tests: data-model §7.6 (amendment of 2026-11-13) and catalog row C15; owners TASK-024 (template, renderer, C15) and TASK-037 (first application), due before TASK-037 merges. Consequence for decision 2: the number-allocation statement also sets `updated_by`, `updated_at` and `version = version + 1` (data-model §6.4; the column grant already lists them). Alternatives rejected: a raw-DML lint in `db-raw-sql` (text-level, evaded by definer functions and migrations, needs a reviewed-writers manifest and the lint lock); documented acceptance alone (leaves attribution and the optimistic-lock counter forgeable by one developer error); a guard that fills the columns (hides defects and overrides the `NOT NULL`-without-default contract); an `AFTER STATEMENT` trigger on transition tables (the rows are already written, it needs one trigger per event, and it gains nothing at 1–30 rows per ORM statement).
2. **UUIDv7 entropy and use (PR26-SEC-05; corrects the "74 random bits" comment of the first PR #26 head).** The application generator, `uuid` 14.0.3 `v7()`, writes a 48-bit millisecond timestamp, then a 31-bit counter that is re-seeded from the CSPRNG (`crypto.getRandomValues`, node and browser entries alike) at each new millisecond and incremented within it, then 42 fresh random bits per id. An id therefore carries **73 unpredictable bits at a new millisecond and 42 within the same millisecond**; it is strictly ascending per process (on counter overflow the millisecond advances, on clock regression the last millisecond is kept) and orders across processes by millisecond only. Rules that follow: (a) an id is an identifier, never a capability — guest access is a 256-bit token stored hashed (data-model P1) and RLS decides the rest — so no endpoint may treat knowing an id as authorisation; (b) a public id discloses its creation time to the millisecond (data-model P1; accepted); (c) the reserved actors (data-model §1.6, timestamp 0) are valid UUIDv7, so `isUuidV7` proves nothing about the origin of an externally supplied id and must not be used to authenticate one or to accept it as server-generated; (d) the `DEFAULT uuidv7()` safety net is PostgreSQL's, whose documentation states only "millisecond timestamp + sub-millisecond timestamp + random" (no bit counts and no cross-backend ordering guarantee), so nothing relies on it beyond uniqueness and rough time order.

## Amendment 2 (2026-11-20, TASK-076 code review round 1: R1-m4 (merge condition) and R1-m5; developer decisions D-TASK076-06 and D-TASK076-02; D-ARCH-169, D-ARCH-170)

3. **The code computes with a static exponent table; the `currencies` reference table is its database copy (amends decision 3; R1-m4).**
   - Decision 3 said the reference table drives the exponents. The pricing engine performs no I/O (REQ-PRICE-001), and the money helpers also run in the browser, so neither can read a table.
   - `CURRENCY_EXPONENTS` in `packages/shared/src/money/currency.ts` is the authority for every computation: arithmetic, parsing, formatting and FX rounding in api, worker, web and `packages/pricing`. An unknown code throws `CURRENCY_UNKNOWN`. There is no default exponent.
   - `currencies` stays the seeded reference data that REQ-DATA-006 asks for. It is the foreign-key target of the currency columns and the source of names, symbols and the public currency list. It feeds no computation. Its column is `minor_unit` (data-model §3.6); decision 3 called it `exponent`.
   - **Both hold the same codes with the same exponents:** the ISO 4217 List One codes that have a numeric minor unit (data-model §9.2: "all with minor units"). A parity test fails on a code that is in one and not in the other, and on any different exponent. Owner: TASK-066, which writes the seed.
   - A change of the ISO list changes the table and the seed dataset in one PR, and the header of `currency.ts` records the date the list was checked. TASK-066 re-checks `ANG`, `CUC` and `SLL` against the list of that day (the review found `ANG` beside its successor `XCG`; the list itself was not consulted for this amendment).
   - The exponent of a code that already has stored amounts never changes in place, because stored minor units would change their meaning. It needs a data-changing migration under the backup guardrail (data-model §8.6).
   - Rejected: exponents as an input that the caller reads from the table (one more argument through every money helper, and the browser would need the list before it can format a price); generating the table from the seed dataset at build time (`packages/shared` would depend on the seed).
4. **The origin country decides which billable-weight rule applies, never the unit of entry (adds to decision 4; R1-m5).**
   - A service has two rules (`carrier_services`): METRIC with a divisor in cm³ per kg (default 5000) and an increment in grams (default 500), and IMPERIAL with a divisor in in³ per lb (default 139) and an increment in hundredths of a pound (default 100, which is 1 lb).
   - The caller chooses the rule by `countries.unit_system` of the quote's **origin country**: IMPERIAL for a US origin, METRIC for every other (the default of REQ-QUOTE-005). That value is what `billableWeightRule(terms, unitSystem)` of `packages/shared/units` takes.
   - The unit the user typed, or toggled to, plays no part. `quotes.entry_unit_system` is display data, and the canonical grams and millimetres are what is weighed.
   - Why: the two rules give different weights. The package of AT-US-139-04 (20 × 16 × 12 in, 5 lb) bills 12,701 g under the IMPERIAL rule and 13,000 g under the METRIC rule (code review probe on the TASK-076 head). A caller that chose by the unit of entry would let the units toggle change the price of the same parcel, against REQ-PRICE-004, AT-US-139-05 and REQ-QUOTE-005 ("the toggle changes entry and display").
   - The server and the browser choose alike. The quote widget's live billable weight (REQ-QUOTE-006: "the default for the origin unit system") uses the origin country's rule and shows the result in the unit the user selected.
   - Callers: the quote module where it builds the pricing input (TASK-093 or the task that builds `PricingRequest`) and the quote widget (TASK-201).

## Reversibility

Low for order-number format after the first production order (D-032); high for internals.
