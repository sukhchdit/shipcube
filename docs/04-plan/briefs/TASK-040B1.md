## Scope notes (lead)

- **Taken here (first pull request, D-ARCH-204):**
  - **Lease rule (PR040-SEC-04, R2-n1; amendment 10).** `idempotencyLeaseMs` = max(30 s, max(D + T, 3 × T + FAILED entry wait) + 5 s), T = admission wait + `maxWait` + `timeout`. The runner does not expose `DB_TENANT_ADMISSION_WAIT_MS`, so `ExecuteOptions.admissionWaitMs` is optional and defaults to `maxWait`, the validated upper bound of that wait (a longer lease, never a shorter one); the second pull request may pass the configured value from `createApp`. Table test over statement timeouts of 5, 8, 9, 12 and 120 s.
  - **Derived keys (PR040-SEC-01; amendment 15).** The configured material (a deployed key: exactly 32 bytes; a `local-only-*` marker: its SHA-256 digest as today) is HKDF-SHA256 input only, empty salt, 32 bytes: `platform-idempotency-body-v1` for the AES-256-GCM body key (current and `_PREVIOUS`), `platform-idempotency-scope-network-v1` for the client-network HMAC key (current only). Known-answer vectors, an independent RFC 5869 oracle, and the P1 probe ("the AES key is the material") turned into a failing assertion.
  - **Sealed envelope (PR040-SEC-02; amendment 15).** A completion seals `{v: 1, origin, status, headers, body?}`, with or without a body. A replay reads status, headers and body from the opened envelope only; the clear `response_status` and `response_headers` must equal it, else `IdempotencyReplayError('stored response mismatch')` (500, `api.idempotency_replay_unreadable`). `Content-Type` allow-list (`application/json` or `application/problem+json`, optional `charset=utf-8`): refused at completion (RangeError, so a 2xx rolls back and the key is released) and at replay. Migration `20261121000000_idempotency_keys_completed_body`: `ck_idempotency_keys__completed_body` `(status = 'COMPLETED') = (response_body IS NOT NULL)`, NOT VALID + VALIDATE under `lock_timeout` 3 s, expand, not data-changing (the table has never held a row).
  - **PR040-SEC-09.** The rendering of a thrown 4xx is guarded: a document that cannot be serialised releases the key and logs WARN `api.idempotency_problem_unrendered` (class only); the original failure goes on to the problem handler.
  - **Contract pins (PR040-SEC-07)** in `tests/contract/x-idempotency.test.ts`, each with planted negatives: public idempotent = {recordConsent}; VIEW/DOWNLOAD idempotent = {emailShipmentDocuments}; 2xx `client_secret` idempotent = {checkoutOrder, confirmPayment, createPaymentMethodSetup}.
