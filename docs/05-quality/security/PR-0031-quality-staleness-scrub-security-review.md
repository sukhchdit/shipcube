## 1. Summary

## 4. Finding details

### PR31-SEC-01: `.gitmodules` `ignore = all` hides a gitlink from the diff (LOW)

**Description.**
- `changedEntries` runs `git diff --raw -z --no-renames --no-abbrev <git_sha> <head> --`. Git omits a submodule change from a diff when the submodule is marked `ignore = all`, by `.gitmodules` in the work tree or by `diff.ignoreSubmodules`. The explicit option `--ignore-submodules=none` overrides both and is not passed.
- Probe (`gitmodules-scen.mjs`): scenario commit = PR head plus a `160000` entry named `.claude/agent-memory/qa-lead/zz.md`.
  - No `.gitmodules`: stale (guard works).
  - Work-tree `.gitmodules` with `ignore = all` for that path: **accepted**, `stale=0`, exit 0.
  - `.gitmodules` with `ignore = dirty`: stale.
  - Runner config `diff.ignoreSubmodules=all`: accepted.
- The changed-path list used for selection (`changedPaths`, `git diff --name-only -z`) has the same property: a gitlink at `apps/api/src/zz-sub` with `ignore = all` selects no suite (`gitmodules-select.mjs`, base and head copies alike). That part is not new.

**Exploitability and impact.**
- The attacker has to commit a `.gitmodules` that names the exact path before the evidence run (a later `.gitmodules` is itself a non-docs change and makes the evidence stale). The file is not owned, but it is visible in the diff of any review.
- A gitlink is never fetched in lane A (`actions/checkout` without submodules) and nothing reads a note as code. The result is an "unevidenced" entry named like a note, which is what the guard was meant to refuse. Likelihood low, impact low.

**Remediation (code level, `tools/quality/check-evidence.mjs`).**
1. Add `'--ignore-submodules=none'` to the argument list of the `git diff --raw` call in `changedEntries` and to the `git diff --name-only` call in `changedPaths`. Place it before the revisions.
2. Optionally also run both with `-c diff.ignoreSubmodules=none` so a future caller that omits the flag keeps the behaviour.

**Verification test.** In `check-evidence.test.ts`, extend the mode-guard table: write a `.gitmodules` with `ignore = all` for the note path into the commit that is the evidence commit (or an ancestor), then stage a `160000` entry at the note path after it; the result must be `stale: 1 path(s)`. A second case: a gitlink-only change at a code path with the same `.gitmodules` must still select `unit`.

### PR31-SEC-02: the mode guard does not cover a memory-only PR (LOW)

**Description.**
- The guard runs only when there is evidence to judge. A PR whose changed paths are all agent notes selects nothing (`docs-or-ci-only`), so `changedEntries` never runs on it.
- Selection and the lane A classifier look at names, not modes. Probe `select-scen.mjs` S8 to S10: a PR of one symlink, one `100755` file or one gitlink named `.claude/agent-memory/qa-lead/zz.md` gets `required=[]` and PASS. `ci.yml` classifies every `.claude/**` path except `settings.json` as docs-only, and CODEOWNERS has no `agent-memory` line.
- `MEMORY.md` of each agent is loaded into that agent's context by the harness. Whether the harness follows a symlink is not something this repository controls.
- The repository has no non-regular entry today besides two `100755` hook scripts under `tools/hooks/`: 0 symlinks and 0 gitlinks in 1517 tracked entries at the head. The note paths are all `100644` (79 at the head, 85 on `main`).
- Before this PR a memory-only PR required a `unit` run, but that run did not check modes either. The PR therefore does not make anything worse; it adds a guard that stops short of the one PR shape where it would matter.

**Exploitability and impact.**
- A symlink named `MEMORY.md` that points at a host file could pull that file into an agent's context and from there into model traffic, logs or a PR text. In practice the orchestrator commits the notes, batched with docs commits (D-ORCH-034 (3)), and the repository has a single maintainer, so the likelihood is low; the impact is a disclosure, so medium. LOW.

**Remediation (TASK-015, `tools/ci`, base-ref copy).** A lane A tree invariant on the head tree: `git ls-tree -r -z <head>` has no `120000` or `160000` entry, and `100755` appears only on an explicit allow-list (`tools/hooks/*`). Use plumbing (`git ls-tree -r -z`), which no `.gitmodules` or diff setting can filter. Wire it as a required gate step (`CI_REQUIRED_GATES`) so it cannot be dropped from `ci.yml`.

**Verification test.** Plumbing scenarios in the checker's test file: a tree with a symlink, with a gitlink, with an unlisted `100755` file, each FAIL; a tree with only the two hooks PASS.

### PR31-SEC-04: pending-case gate residuals (INFO)

The checkpoint map is as stated: `pr` reaches nothing, `wave` reaches `Wave-0 exit` only, `gate` reaches all three (16 variants, §5 (e)). Residuals:
1. The `decision` is checked by syntax (`D-[A-Z0-9][A-Z0-9-]*`), not for existence in `DECISIONS.md` (probe: `D-NOSUCHDECISION-1` is accepted). That is the same rule as `deferred_at_gate`. At `gate` it lets a parked case pass mechanically. Parking indefinitely therefore needs an edit of `required-suites.json`, which is code-owned and needs a record, and a G3 reader who accepts the decision. G3 checklist item for quality-gatekeeper: every `decision` of a pending entry resolves in `DECISIONS.md`, and the written rule "G3 fails on any non-empty pending list" is applied to entries without one.
2. The three `v0.1.0-m0` entries are mechanically enforced only by a `gate`-profile run, because `wave` does not reach that checkpoint and no `wave` or `gate` run is committed while D-SEC-PR23-02 holds. The `v0.1.0-m0` activation is a manifest-only `pr` PR, so the orchestrator's wave-exit checklist stays the control there.
3. Removing an entry from `required_cases_pending` (or misspelling the key, which parses as `{}`) without restoring the ID to `required_cases` is silent. It is a code-owned manifest edit that the record gate sees, and the G3 human check "SEC-TC 64/64" catches the missing ID. A mechanical check that the union of `required_cases` and `required_cases_pending` never loses an ID would close it; it belongs with the Wave-0-exit runner work.

### PR31-SEC-05: scrub belt residuals (INFO)

`scrubPaths` is a two-layer control, and only the list layer is required to be complete. On this host the list holds 6 entries (home, temp and repository root, long and 8.3 forms). All of these spellings of the home, temp and repository paths are scrubbed: plain, long form, forward slash, JSON-escaped, upper- and lower-case, Git Bash, WSL, `file:///` URL, `\\?\` extended-length, inside angle brackets or quotes, inside a long title. Four exotic spellings survive (`scrub-probe.mjs`):
- a doubly JSON-escaped path (four backslashes per separator);
- a percent-encoded drive (`C%3A`);
- a URL-encoded user directory;
- a bare 8.3 segment that is not preceded by a separator.

The generic belt also stops at white space, so a profile directory name containing a space becomes `<home> Surname` (synthetic example). On a real host the list handles that case, because it matches the full path literally.

Nothing leaks in practice (§5 (d)), because the titles are plain and the list is complete for this host. The weakness of the whole design is that the scrub runs on the developer host and its result is self-reported in the gate table; the base-ref verifier does not look. A cheap verifier-side belt would be an integrity rule in `check-evidence` for run files (the check runs in the base-ref copy): reject a run directory whose files match `[A-Za-z]:[\\/]Users[\\/]`, `/Users/`, `/home/<name>` (other than `<home>`), or an 8.3 `~<digit>` segment. Linear regexes, the same shapes as the belt. Optional; TASK-015.
